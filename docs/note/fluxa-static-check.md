# Fluxa 靜態檢查（`reda check`）

> 分支：`aitest`。方向 A：把規格 §3 的檢查從「模擬時才發現」移到「合成之前」。
> 相關：[ai-feedback.md](ai-feedback.md)（`--format json`）。

## 1. 為什麼

Fluxa 規格（`fluxa/docs/Fluxa語言規格v0.1.md`）定了不少靜態檢查（E0102、E0301、E0401、E0412、E0501…），但到這一步為止，合成器只實作了 E0412，其餘要嘛在模擬時才抓到，要嘛沒做。模擬只能看到**這一次**執行走過的值：

| | 模擬（`reda sim`） | 靜態（`reda check`） |
|---|---|---|
| `err_overflow.fx` 的 `carry acc: i24` | 第一次溢位時的值 32767²，推出「至少 i31」 | `len: u16` 最多 65535 次 × i16²，需要 **i47** |
| 沒被測試走到的路徑 | 看不到 | 看得到 |
| 需要可執行的 test | 是 | 否 |

對 AI agent 來說，這就是「判官」能不能在合成前給出**證據與修正**的差別。

## 2. 用法

```bash
reda check fluxa/examples/err_overflow.fx
```

```text
fluxa/examples/err_overflow.fx:3: warning[E0301] in `Mac`: carry `acc`: i24 is too small:
  init 0..=0 + 65535 × -1073709056..=1073741824 reaches -70365522984960..=70367670435840
    fix: declare it as i47 (or saturate: .sat::<i24>())
1 finding(s)
```

`--format json` 時每一筆是一個 `phase: "check"` 的 diagnostic，`data` 有 `range`、`type`、`accumulation`、`min_type`，`notes` 是修正建議。有發現時 exit code 為 1。

## 3. 檢查的項目

| 代碼 | 內容 | 規格 |
|---|---|---|
| E0301 | 值的範圍裝不進落點的型別：`let x: T = e`、賦值、`send`、函式引數、回傳值、陣列元素 | T-ASSIGN |
| E0301 | 累加器（`carry` 與有型別的 `let mut`）：初值 + Σ 迴圈次數上界 × 每次增量 | T-CARRY |
| E0301 | 非加法的自我更新（`x = x << 1`）一步就要裝得下 | §3.3 |
| E0102 | 除數的範圍包含 0 | T-DIV |
| E0703 | 索引的範圍超出陣列（暫定代碼） | — |
| E0501 | 一條通道整段執行送出與收到的 token 數不同：會死結 | §3.4 SDF |
| W0503 | 同上，但剩下的 token 放得進 FIFO：不會卡住，只是沒人收（暫定代碼） | — |
| E0702 | 端點交給 spawn 之後又被使用（暫定代碼，模擬時才抓得到的線性違規） | T-SPAWN |
| E0401 | `pipeline(ii = n)` 迴圈一輪裡對同一個通道或 mem 埠的使用超過 n 次 | §3.5 |

## 4. 方法：區間抽象解譯

在 AST 上對每個 `fn`、`comb fn`、`task`、`test` 做一次走訪（`fluxa/sim/src/check.rs`），每個值是一個整數區間 $[lo, hi]$，運算依規格 §3.2：

$$
[a,b]+[c,d]=[a+c,\ b+d],\qquad
[a,b]\cdot[c,d]=[\min P,\ \max P],\ P=\{ac,ad,bc,bd\}
$$

累加器的終值範圍（T-CARRY 的推廣，$N_s$ 是累加點 $s$ 外層迴圈次數上界的乘積）：

$$
R=\Big[a+\sum_s N_s\cdot\min(lo_s,0),\ \ b+\sum_s N_s\cdot\max(hi_s,0)\Big]
$$

精確度的來源：

- **迴圈次數**：`for i in a..b` 的次數上界由 `a`、`b` 的範圍算出；`for v in rx`（串流）是無界。
- **條件收窄**：`if x < c`、`x >= c`、`x == c`、`x != 0`（含 `&&`）收窄 `x`；收窄成空集合的分支視為走不到。
- **跨函式**：呼叫非泛型的 `fn` / `comb fn` 時，用引數的範圍分析它的本體（深度 4，有快取）。`csr_slot(0x300)` 因此得到確切的格子，而不是回傳型別 `u6` 的 0..=63。
- **`.wrap::<T>()` / `.sat::<T>()`**：值本來就裝得下時保留原範圍。
- **不為 0**：`if b != 0`（或 `if b == 0 {…} else {這裡}`）之後，`b` 和它同寬以上的 `.wrap()` 可以當除數。

保守的地方：被賦值過的變數取宣告型別的範圍；泛型、定點數、未支援的運算一律「未知」而**不檢查**。所以每一筆發現的意思是「無法證明裝得下」。

### 4.1 通道：token 守恆（E0501）

規格 §3.4 的 SDF 是穩態的平衡方程 $rate_p\cdot reps(p)=rate_q\cdot reps(q)$。Fluxa 的測試與網路是**有限次**執行，所以這裡檢查的是它在整段執行上的形式：每條通道 $c$

$$
\text{sent}(c) = \text{received}(c) = T(c)
$$

每個端點的次數是線性式 $c_0+\sum_i k_i\,T(ch_i)$：

- 常數迴圈：乘上次數（`for _ in 0..8`、`for v in xs`）；spawn 的常數引數會帶進任務裡。
- `for v in rx`：收完 rx 上所有的 token（$T(rx)$），本體跑 $T(rx)$ 次，所以 `for v in x { y.send(v) }` 在 y 上送 $T(x)$ 個。
- `broadcast(r, n)`：收完 r，每個輸出送 $T(r)$ 個。
- 條件分支：每個分支的次數相同才算得出來，否則是**動態速率**，不檢查（規格 §3.4 說的「速率動態的通道」）。

每個 `test` 與每個 spawn 其他任務的 `task` 是一個網路：每條區域通道列一條方程，一邊不含 $T(c)$ 時就代入求解，最後比對兩邊。任務的結果（參數上的次數）往上一層網路傳，所以 `Pipeline` 這種「會建網路的任務」也能檢查。

| 結果 | 意思 | 代碼 |
|---|---|---|
| 收 > 送 | 接收端永遠等不到 | E0501 |
| 送 − 收 > FIFO 深度 | 送出端卡住 | E0501 |
| 0 < 送 − 收 ≤ 深度 | 剩下的 token 沒人收 | W0503 |

### 4.2 埠：pipeline 迴圈的資源（E0401）

規格 §3.5 用「資源 × 埠類別 × 週期槽」的容量判定 bank 衝突。parser 目前會跳過 `@bram(...)` 的參數，語言還沒有分割的語法，所以這裡的模型是**一個 bank**：

- 每個通道端點：每個時脈一個 token；
- 每個 `mem`：一塊 block RAM，一個讀埠、一個寫埠。

在 `pipeline(ii = n)` 迴圈裡數一輪的使用次數（內層的常數迴圈會被合成器展開，所以乘上次數；條件分支兩邊都算，因為硬體兩邊都排），超過 $n$ 就是 E0401，修正建議是 `ii` 等於使用次數。合成器遇到同樣的情況會報 E0412（「one token a clock: use ii = 2」或「more than one state」），E0401 在合成前就說明是哪個資源、用了幾次、在哪幾行。

## 5. 實測

| 程式 | 行數 | 發現 | 說明 |
|---|---|---|---|
| `fluxa/examples/*.fx` | — | 11 | 全部是真的問題（見下） |
| `fluxa/rv32i`（含 tests_basic） | 729 | 6 | 計數器、記分板 |
| `fluxa/rv64`（含 FPU） | ~2300 | 54 | 從 117 降到 54，見 §5.2 |

### 5.1 範例裡的 11 筆

| 位置 | 問題 |
|---|---|
| `err_overflow.fx:3` | carry `acc: i24` 需要 i47 |
| `err_narrow.fx:6` | `let d: u8 = 300` |
| `fanout.fx:2` | `Gen` 把 `0..n`（`n: u32`）送進 `chan<u8>`，n > 256 就溢位 |
| `fanout.fx:5`、`pipeline.fx:6` | 在無界串流上累加（`u16`、`u8`） |
| `gemm.fx:21–22` | `FeedA(i: u32)` 用 `i` 索引 3 個元素的陣列；改成 `i: int<0..=N-1>` 就消失 |
| `err_deadlock.fx:8` | E0501：`tz→rz` 沒有人送，測試卻收 1 個（模擬時是「all 3 live tasks are blocked」） |
| `err_linear.fx:6` | E0702：`rx` 交給 `Sink` 之後又 `rx.recv()`；同一個錯也使 `tx→rx` 不守恆（E0501） |
| `fir.fx:25` | W0503：`fir_impulse` 送 1 + 16 = 17 個樣本，只收 16 個輸出，第 17 個沒被檢查 |

rv64、rv32i 的管線各階段都是資料相依的條件式 send / recv（動態速率），E0501 不檢查，所以沒有新增的發現。

### 5.2 rv64：精確度的改進

| 版本 | 發現 | 消掉的誤報 |
|---|---|---|
| 只有區間 + T-CARRY | 117 | — |
| + test 裡的 `let mut` 累加器當成 carry | 117 → 106 | 測試的累加 |
| + 跨函式、`wrap` 保留範圍、不為 0、不可能的分支 | 106 → 54 | `csr[csr_slot(…)]` 的 51 筆索引、`alu_m` 的除以零 |

剩下的 54 筆分成三類：

| 類別 | 例子 | 該怎麼處理 |
|---|---|---|
| 型別宣告得太寬 | `tlb_next: u32` 實際只到 TLBN-1；FPU 指數宣告成 i32，兩個相加就可能超出 | 規格的本意：收窄型別（`int<0..=TLBN-1>`），檢查就會通過 |
| 關係型不變量 | `r = t - uy` 只在 `t >= uy` 時；`pend[r] - 1` 依賴記分板 | 區間分析看不到變數之間的關係；需要更強的抽象域或 `assume`（規格 §8 的開放問題） |
| 規格要求顯式回繞 | 位址 `clr(tv, 3) + 4 * code`、`q = (q << 1) \| 1`、指令計數器 | 改寫成 `+%` / `.wrap::<T>()`，表明「這裡就是要回繞」 |

## 6. 還沒做

- **bank 分割**：語言加上 `@bram(cyclic = B, ports = …)` 的語法與合成後，E0401 才能照規格 §3.5 用 $\lceil k\cdot g/B\rceil \le p$ 判定。
- **含環的網路**：環上每個任務都先收後送、又沒有初始 token 就會死結（`err_deadlock.fx` 的 `A ↔ A`），規格要求檢查器驗證，還沒做。
- **`for v in rx` 裡又 `rx.recv()`**（一輪收好幾個）：迴圈次數是 $T(rx)/(1+k)$，不是 $T(rx)$，目前當作未知而不檢查。原本照 $T(rx)$ 算，在方向 C 的實驗裡被 AI 寫的 `dot8` 抓到誤報（模擬通過，卻報三筆死結）。
- **動態速率**：規格說要警告「無法證明無死結」；目前只是不報，避免 rv64 這類程式出現大量警告。
- 定點數的範圍（目前一律未知）。
- 欄位（col）：錯誤只有行號。
- 關係型不變量：可以考慮規格 §8 提到的 `assume x < 100;`。
- 嚴重度：目前全部是 warning。哪些該升成 error（例如常數就確定超出的 `let d: u8 = 300`），要等累積更多實例再定。
