# 6.8 硬體資源檢查：E0401 與 E0412

### 6.8.1 E0401：單一資源在一輪用得太快

`pipeline(ii = n)` 承諾每  $n$  個時脈啟動一次迭代。若一個迭代內對同一資源操作  $k$  次，而資源每  $n$  拍只能服務一次，就必須滿足：



$$
k \le n
$$



Fluxa v1.0 使用單一 bank 模型：

- 一條通道每時脈最多傳送一個 token；
- `mem<T, N>` 映射成一個讀埠、一個寫埠的 block RAM；
- 尚未實作手動 bank 分割。

例如下面每輪接收同一通道兩次：

```fluxa
task Pair(x: in chan<u8>, y: out chan<u9>) {
    pipeline(ii = 1) for _ in 0..8 {
        let a = x.recv();
        let b = x.recv();
        y.send(a + b);
    }
}
```

`ii = 1` 表示每拍啟動一輪，但同一通道每拍只能接收一個 token。靜態檢查以 E0401 報告：

```text
pipeline(ii = 1): channel `x` (1 token per clock) uses an iteration on
channel `x` (1 token per clock), more than 1
```

可把證據寫成：

```text
resource = x
uses    = 2
capacity= 1
```

若改成 `pipeline(ii = 2)`，每兩拍啟動一輪，兩次接收便可分配到不同時槽，通道用量檢查就會通過。

但這不表示吞吐量自動理想化。Fluxa v1.0 的目前後端對 `ii >= 2` 會退回一般 FSM；它保留行為語意，卻不保證迭代真的只需兩個時脈。第 8 章會專門討論排程與硬體代價。

### 6.8.2 記憶體埠也是同一類問題

```fluxa
task SumMem(y: out chan<u10>, n: u16) {
    let mut memory: mem<u8, 16> = [0; 16];
    pipeline(ii = 1) for i in 0..n {
        carry sum: u10 = 0;
        for k in 0..4 {
            sum += memory[k];
        }
        y.send(sum);
    }
}
```

單一 block RAM 每拍只有一個讀埠，但內層迴圈每輪讀 4 次。展開後，一個外層迭代需要 4 個讀，因此 E0401 會指出讀埠超用。

首選修法取決於演算法：

1. 把四個讀攤到 `ii = 4` 或更長的迭代間隔；
2. 複製資料到足以平行讀取的暫存器；
3. 改用四個獨立 bank——但 Fluxa v1.0 尚未提供這種語法；
4. 改用時間平衡的循序讀取，牺牲吞吐換較小面積。

### 6.8.3 E0412：不是單一資源超用，而是排程承諾不可達

E0401 問的是：「**某個資源**在一輪是否用得太多？」E0412 問的是更完整的問題：

> 能否形成一個符合 `pipeline(ii = n)` 承諾的模數排程？

例如：

```fluxa
task Conditional(x: in chan<i8>, y: out chan<i16>) {
    pipeline(ii = 1) for _ in 0..4 {
        let value = x.recv();
        if value > 0 {
            y.send(value);
        }
    }
}
```

每一輪不一定都有 `send`。模數排程要求每輪具有固定結構；若某輪送、某輪不送，控制狀態與資料路徑就不再是規則的模數排程。合成器會以 E0412 報告：

```text
line 2: error[E0412]: pipeline(ii = 1) cannot be met:
a channel operation under a condition
```

另一個例子是同一輪先送再收：

```fluxa
pipeline(ii = 1) for _ in 0..4 {
    y.send(value);
    let next = x.recv();
}
```

合成器目前要求接收在送出之前，因為送出結果的等待效果不能與同輪接收簡單重疊。診斷會指出：

```text
`y` is received after a send in the same iteration
```

因此：

- E0401：資源容量已足以解釋瓶頸，改 II 或資源結構即可；
- E0412：整個迭代的控制／資料相依無法形成所要求的模數排程，可能要重排操作、改拓樸、展開迴圈或放棄 `pipeline`。

### 6.8.4 `ii = 1` 是效能承諾，不是文件註解

`pipeline(ii = 1)` 表示「每一拍啟動一個迭代」。若結構無法做到，工具應讓承諾失敗，而不是悄悄產生一顆每數拍才處理一個樣本的電路。

這是硬體開發中非常重要的原則：**排程屬性是契約，不是最佳化提示。**如果產品真正需要每拍一筆，就應修正結構；若每兩拍一筆才能達成，則把 `ii = 2` 如實寫出，並接受目前後端的語意保留與實際排程差異。
