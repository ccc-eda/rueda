# 4.3 有界 FIFO：阻塞是語意，不是意外

### 4.3.1 建立通道

通道由 `chan::<T>(depth = d)` 建立。它回傳一對端點：傳送端與接收端。

```fluxa
let (tx, rx) = chan::<i8>(depth = 4);
```

此時：

- `tx` 只能用來 `send`；
- `rx` 只能用來 `recv`；
- FIFO 最多容納 4 個 `i8` token；
- 同一條通道只有一對端點，不能把 `rx` 複製給兩個程序。

容量是正整數；目前 Fluxa 沒有「零容量、直接交接」的 rendezvous 通道語意，不要把 `depth = 0` 當成硬體 handshake。

### 4.3.2 `send` 與 `recv` 都可能等待

通道操作只有三種主要形式：

| 操作 | 行為 | 等待條件 |
| --- | --- | --- |
| `tx.send(value)` | 將 `value` 放到 FIFO 尾端 | FIFO 已滿 |
| `rx.recv()` | 取出 FIFO 最前端的 token | FIFO 為空，且尚未關閉 |
| `tx.close()` | 宣告此傳送端不再產生 token | 不會因已滿而等待 |

阻塞不是額外的執行期機制，而是 KPN 的基本語意。假設深度為 2：

```text
tx.send(10)   FIFO: [10]
tx.send(20)   FIFO: [10, 20]
tx.send(30)   阻塞，等待空間
rx.recv()     FIFO: [20, 30]，喚醒前一個 send
```

`recv` 取得的永遠是 FIFO 最前端的 token，因此同一通道上的邏輯順序固定。排程器可以改變某個 task 何時執行，卻不能把 `20` 換到 `10` 前面。

這也導致 Fluxa 禁止 task 層使用 `rx.try_recv()`、`rx.empty()` 與 `rx.len()`。如果程式可以在「目前看起來是空的」時跳過接收，結果就會取決於排程：

- 執行緒 A 先檢查，FIFO 為空，於是跳過；
- 執行緒 B 先送出 token，執行緒 A 再檢查時又不會跳過。

兩種排程就會產生不同結果。Fluxa 選擇只保留阻塞式操作，讓邏輯 token 序列不依賴「誰剛好先跑」。`stage` 層雖保留非阻塞操作的設計位置，但目前尚未實作，不能拿來規避這項限制。

### 4.3.3 關閉不是丟棄資料

`close` 描述的是「從現在起不再有新 token」，不是「把 FIFO 裡的資料全部刪掉」。

```fluxa
let (tx, rx) = chan::<i8>(depth = 4);
tx.send(7);
tx.send(9);
tx.close();

let a = rx.recv();  // 7
let b = rx.recv();  // 9
```

只要 FIFO 中還有已送入的 token，接收端就必須先讀完它們。`for v in rx` 正好表達這個規則：

```fluxa
for v in rx {
    // 依序處理所有已送入的 token
}
// 通道已關閉，而且 FIFO 已清空，迴圈才結束
```

若對已關閉且為空的通道直接呼叫 `rx.recv()`，得到的不是 `None` 一般的值，而是一次錯誤；`for` 迴圈會把「讀完資料」與「觀察到結束」合併處理。

在目前的 Fluxa 語意中，task 結束時會自動關閉它仍擁有的傳送端，因此常見的元件模式十分自然：

```fluxa
task Forward(x: in chan<i8>, y: out chan<i8>) {
    for v in x {
        y.send(v);
    }
    // task 結束，y 的傳送端自動關閉
}
```

上游關閉後，`Forward` 的 `for` 迴圈會先讀完已送入的資料，再結束；它擁有的 `y` 也會隨 task 結束而關閉，於是 end-of-stream 可以沿著網路逐級傳遞。

這裡要分清楚兩種「關閉」：

1. **明確關閉**：`tx.close()`，用來在某個時刻宣告「我不會再送 token」。
2. **隱式關閉**：task 自然結束，工具關閉仍由它擁有的傳送端。

兩者都表示同一件事：從此不再有新的資料，但既有資料不可遺失。

### 4.3.4 同一通道有順序，不同通道沒有全域順序

Kahn 的確定性保證聚焦在**每條通道的 token 序列**。它不表示兩個不同通道上的事件可以跨通道比較。

假設 FIR 同時輸出：

- `result`：濾波結果；
- `status`：處理完成數量。

我們可以可靠地說 `result` 的第 3 個 token 一定是第 3 個輸入樣本的結果，卻不能只憑語意斷言 `status[3]` 與 `result[3]` 在所有排程下都具有哪一種跨通道先後關係。若跨通道順序很重要，就必須讓它成為同一通道內的 token 順序，或建立額外同步契約。
