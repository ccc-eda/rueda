# 11.8 完整 capstone 與練習

## 11.8.1 選擇你的 capstone

從下列兩條路線選一條：

- **路線 A：FIR + 影像視窗**：完成一個從樣本到影像的串流管線。
- **路線 B：小型矩陣乘法**：完成參數化的脈動陣列，並比較不同 `N` 的資源。

兩條路線都要求完整的交付物，而不是只有程式碼。

## 11.8.2 交付清單

| 項目 | 內容 |
| --- | --- |
| 需求 | 功能、介面、契約、錯誤行為 |
| 原始碼 | Fluxa 實作，含註解與參數說明 |
| 測試 | 正常、邊界、關閉、錯誤案例 |
| 靜態報告 | `reda check` 輸出 |
| 合成報告 | 資源摘要與時序結果 |
| 閘級證據 | 至少一層 `gatesim` 結果 |
| 限制 | 尚未覆蓋的行為與未實作功能 |

## 11.8.3 練習

1. **FIR 參數化**：把 4 階 FIR 擴充成 `FirN<const N: usize>`，並重新推導總和位寬。
2. **不同 N 的矩陣乘法**：比較 `N = 2, 4, 8` 的面積與時序，說明成長趨勢。
3. **邊界策略**：為 3×3 視窗設計兩種邊界策略（略過、補零），比較輸出數量與契約差異。
4. **架構比較**：用同一組測試比較循序 FIR 與平衡樹 FIR，記錄 II、延遲與資源。
5. **驗證矩陣**：為你的 capstone 建立第 10 章的驗證矩陣，並補上至少一個錯誤案例。

## 11.8.4 評分標準

一個好的 capstone 應該：

- 契約清楚，別人能只讀文件就使用你的元件；
- 測試能重現，命令與版本完整；
- 靜態檢查沒有未解釋的錯誤；
- 合成報告與設計意圖一致；
- 驗證結論有明確範圍，不誇大。

相反的，一個只有「程式能跑」的交付，通常在下一個人接手時就會暴露問題。

## 11.8.5 下一章

你現在已經完成一個可交付的硬體元件：有契約、有測試、有檢查、有網表與驗證。最後一章要把這套流程放進 AI 輔助開發的脈絡：當 agent 可以快速產生程式與測試時，哪些工作可以加速，哪些關卡絕不能自動跳過？
