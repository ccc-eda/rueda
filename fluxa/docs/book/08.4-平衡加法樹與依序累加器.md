# 8.4 平衡加法樹與依序累加器

## 8.4.1 兩種加法的硬體形狀

四階 FIR 的核心是四個乘積的總和：

$$
y = c_0x_0 + c_1x_1 + c_2x_2 + c_3x_3
$$

數學上，加法有結合律，所以只要順序不改變浮點誤差語意，硬體可以任意分組。但硬體上「怎麼分組」會直接改變延遲、面積與時序。

最直覺的寫法是依序累加：

```fluxa
let mut acc = 0;
for k in 0..4 {
    acc = acc + win[k] * COEF[k];
}
```

它需要一個乘加器重複使用四次，面積小，但四輪形成四段相依的加法鏈。平衡加法樹則先把乘積兩兩相加，再把兩個部分和相加：

```fluxa
let p0 = win[0] * COEF[0];
let p1 = win[1] * COEF[1];
let p2 = win[2] * COEF[2];
let p3 = win[3] * COEF[3];
let s01 = p0 + p1;
let s23 = p2 + p3;
let y = s01 + s23;
```

四個乘法可以平行，加法鏈深度從四降到二。代價是需要三個加法器同時存在，而不是一個加法器分時使用。

| 形式 | 乘法器 | 加法器 | 加法鏈深度 | 面積傾向 | II 傾向 |
| --- | ---: | ---: | ---: | --- | --- |
| 依序累加 | 1 | 1 | 4 | 小 | 大 |
| 平衡樹 | 4 | 3 | 2 | 大 | 可到 1 |

這張表只描述資料路徑的結構成本。實際是否能達成 `II = 1`，仍受通道操作數、記憶體埠與後端排程限制。

## 8.4.2 用 `.tree_sum()` 表達平衡樹

Fluxa 的範圍物件提供 `.unrolled()` 與 `.tree_sum()`，把「固定數量的乘積」寫成空間並行的意圖：

```fluxa
let acc = (0..4).unrolled()
                 .map(|k| win[k] * COEF[k])
                 .tree_sum();
```

這段程式在行為模擬時仍然得到同一個值；合成時，`.unrolled()` 要求四個迭代各有一份邏輯，`.tree_sum()` 則要求以樹狀方式合併。這正是把「數學上的結合律」轉成「硬體上的平行度」的例子：理論告訴我們可以先乘再兩兩相加，工程則決定這樣做值不值得多付兩個加法器。

## 8.4.3 累加器寬度是架構決策

無論用哪一種加法樹，下一個問題都是：總和的型別要多大？

對 $n$ 個 $w$ 位元有號整數相加，最壞情況的總和需要 $w + \lceil \log_2 n \rceil$ 位元。若每個乘積的範圍是 $[p_{\min}, p_{\max}]$，則總和範圍是：

$$
\left[\,n\cdot p_{\min},\ n\cdot p_{\max}\,\right]
$$

這個區間必須完整落進累加器的型別，否則 `reda check` 會以 E0301 報告。平衡樹不會讓位寬需求消失；它只是改變到達總和的時間順序。反過來說，先決定總和型別，再選加法樹的深度，才是可解釋的設計流程。

## 8.4.4 為什麼不自動選最好的樹

工具可以展開固定次數的迴圈，也可以依結合律重排加法，但「哪一種排程值得」牽涉產品目標：

- 需要每拍一個樣本，且時序有餘裕：平衡樹值得多付加法器。
- 面積受限，而吞吐量只要求每四拍一個樣本：依序累加更合適。
- 乘法器本身很貴：先考慮共享乘法器，再考慮加法樹深度。

因此，Fluxa 把 `.unrolled()`、`.tree_sum()`、`serial` 與 `pipeline` 留給設計者表達意圖，而不是替設計者猜一個全域最佳解。最佳解不是編譯器的屬性，而是產品規格、目標裝置與量測結果共同決定的。
