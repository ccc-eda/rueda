# 4.13 動手練習

### 練習 4.1：把廣播改成兩個完整消費者

以下程式建立了一個廣播：

```fluxa
let outs = broadcast(rx, 2);
```

請把它改成兩條各自擁有完整序列的分支，且不要使用 `broadcast`。你可能需要：

1. 為兩條分支各建一組通道端點；
2. 讓來源 task 知道兩條分支的存在；
3. 為每個輸入 token 明確送出兩份；
4. 證明兩個分支收到的 token 序列完全相同。

這題的關鍵不是找到最短語法，而是理解：若不用廣播，複製 token 的責任就會落到某個 task。

### 練習 4.2：畫出刻意死結程式的等待圖

以下程式形成等待環：

```fluxa
task A(i: in chan<u8>, o: out chan<u8>) {
    let v = i.recv();
    o.send(v);
}

let (t1, r1) = chan::<u8>(depth = 1);
let (t2, r2) = chan::<u8>(depth = 1);
spawn A(r1, t2);
spawn A(r2, t1);
```

請畫出：

- 兩個 task；
- 兩條通道；
- 每個 task 持有的端點；
- 每個 task 正在等待的操作；
- 等待環的方向。

接著提出至少兩種修正：一種讓 A 先送 seed token，另一種改成能持續運作的 ping-pong 協定。比較兩種修正的 token 數量與結束條件。

### 練習 4.3：完成 FIR 通道契約表

為 4.6 節的 `FirNetwork` 完成本章的章末產物。表格至少要包含：

| 通道 | 元素型別 | 方向 | 深度 | 順序／數量 | 關閉責任 |
| --- | --- | --- | --- | --- | --- |
| 外部 `x` |  |  |  |  |  |
| 內部 `result` |  |  |  |  |  |
| 外部 `y` |  |  |  |  |  |
| 外部 `count` |  |  |  |  |  |

再寫出三條網路不變量，並為每條不變量指定至少一個斷言。

### 練習 4.4：比較兩種 FIFO 深度

把 FIR 測試中的輸出 FIFO 深度分別設為 1 與 32，觀察：

1. token 序列是否相同；
2. 測試是否可能因容量不足而死結；
3. 合成報告中的 FIFO 面積如何變化。

若工具目前不能直接比較兩份設計，至少先從 token 守恆推論應該相同的部分，再執行合成報告比較面積。記得在報告中區分「邏輯正確性」與「資源成本」。
