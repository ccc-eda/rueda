# 8.8 資源模型與最佳化方向

## 8.8.1 先建立可比較的基準

最佳化最常見的錯誤，是在還沒有基準時就開始改架構。對硬體設計而言，基準至少要包含：

- 目標裝置與時脈頻率；
- 輸入與輸出速率；
- 目前達成的 II 與延遲；
- LUT、FF、DSP、BRAM 的使用量；
- 時序是否通過，以及最差路徑在哪裡。

沒有這些數字，「把加法樹改成更平行」或「把 FIFO 加深」都只是猜測。第 9、10 章會把這些量測接上 FPGA／ASIC 後端與閘級模擬；本章先建立語言層可表達的資源直覺。

## 8.8.2 四種常見瓶頸

同一個設計的資源問題，通常落在下列四類之一：

| 瓶頸 | 典型徵狀 | 優先修正 |
| --- | --- | --- |
| 通道速率 | 同一通道一輪用兩次、E0401 | 拆通道或改排程 |
| 記憶體埠 | 一輪多讀或多寫、E0401 | bank、分階段或改演算法 |
| 排程不可達 | `pipeline(ii = 1)` 報 E0412 | 改成固定形狀或循序 FSM |
| 面積／時序 | 資源超限、時序失敗 | 共享運算、縮位寬、改排程 |

先分類，再修一種，才不會同時改太多變數而失去因果關係。若一次同時改位寬、拓樸與排程，即使結果變好，也無法說明是哪個決策造成改善。

## 8.8.3 共享與平行化的取捨

硬體最佳化常在兩個方向之間移動：

- **共享（serial）**：用較少的運算器，分時處理更多工作。面積下降，II 上升。
- **平行（unroll）**：用更多運算器同時處理，面積上升，II 下降。

兩者都可能改善「每單位面積的吞吐量」，但方向相反。真正該問的是產品約束：

$$
\text{每單位面積吞吐量} = \frac{f_{\text{clk}} / II}{\text{面積}}
$$

若面積是硬上限，就必須提高 II 或降低功能；若吞吐量是硬需求，就必須付出面積，或提高時脈，或改演算法。這是一個帶約束的最佳化問題，不是單一按鈕。

## 8.8.4 位寬也是資源決策

乘法器面積大致隨位寬平方成長。把一個不必需的 $32\times32$ 乘法縮成 $16\times16$，省下的不只是乘法器，還包括後續加法樹、暫存器與繞線。

但縮位寬不能只看「目前測資剛好放得下」。正確做法是回到第 3 章的值域推導：

- 推導最壞情況範圍；
- 選擇能容納該範圍的最小型別；
- 若需要縮小輸出，使用明確的 `sat` 或 `wrap`，並把契約寫清楚。

這也說明了為什麼型別、靜態檢查與資源最佳化不能分開學：位寬是語意決策，也是面積決策。

## 8.8.5 最佳化的順序

一個可重複的最佳化流程如下：

1. **先讓語意正確**：行為模擬通過，token 序列與邊界案例一致。
2. **再讓靜態檢查通過**：值域、累加器、通道守恆與所有權沒有未解釋的錯誤。
3. **建立基準**：記錄目前 II、延遲與資源。
4. **只改一個變數**：例如只把依序累加改成平衡樹，其他不變。
5. **重新量測並比較**：用同一組測試與同一份報告格式。
6. **保留決策紀錄**：說明為何這個版本比上一個好，以及代價是什麼。

這個順序把「最佳化」從靈感變成實驗。沒有量測的改動，即使程式看起來更漂亮，也不能算是一個可驗證的工程決策。
