# 4.12 常見設計錯誤與正確做法

### 4.12.1 把廣播誤當成工作分配

錯誤的意圖：

```fluxa
// 想要讓兩個 worker 分工處理，實際上卻讓它們競爭同一批 token。
spawn Worker(rx);
spawn Worker(rx);
```

這個程式還會違反線性端點所有權。正確需求若是「兩個 worker 各看完整序列」，使用：

```fluxa
let outs = broadcast(rx, 2);
spawn Worker(outs[0]);
spawn Worker(outs[1]);
```

正確需求若是「每個 worker 處理一半」，就必須建立明確的靜態分配，例如兩條獨立通道分別送偶數位與奇數位序號的樣本，或由調度器依明確索引協定分配。不能讓排程器替設計者決定。

### 4.12.2 以增大 FIFO 代替修正協定

若 A 必須先收到 B 的 token才能送出自己的 token，增加 FIFO 深度無法解除等待環。應先修正資料流依賴，讓某個節點能產生起始 token 或調整操作順序。

FIFO 深度只適合處理**容量性阻塞**，不適合處理**迴圈式等待**或**拓樸缺少生產者**。

### 4.12.3 忘記關閉來源

若測試主體送完資料卻沒有 `tx.close()`，FIR 的 `for s in x` 不知道何時結束，因而不會產生最後幾個結束事件。測試可能看起來「已經收到預期數量的結果」，卻留下永遠存活的 task。

每一條會進入 `for` 迴圈的來源通道，都要有明確的結束策略：

- 來源 task 自然結束，讓其傳送端自動關閉；或
- 來源 task 明確呼叫 `tx.close()`；或
- 測試主體在送完所有 token 後明確關閉。

### 4.12.4 把元件狀態塞進通道

有時開發者會用通道代替內部暫存器，例如讓 FIR 每輪從通道讀回三個歷史值。這會讓元件契約依賴外部何時讀取，破壞元件邊界。

正確做法是讓 `hist` 留在 FIR 內，用 `@reg` 表達硬體歷史狀態；通道只攜帶元件介面所承諾的樣本與結果。

### 4.12.5 假設不同通道之間有全域順序

`result[0]` 與 `status[0]` 分別在兩條通道上，它們的跨通道事件順序不應被當成 KPN 契約。如果某個下游需要兩種資訊同時前進，應把它們封裝成同一個 tuple token，或建立明確同步點。

### 4.12.6 在 task 層使用非確定性查詢

`try_recv`、`empty`、`len` 會暴露「此刻」的 FIFO 狀態，破壞排程無關性。Fluxa v1.0 在 task 層禁止它們；`stage` 層尚未實作，不能在現有版本中用它們繞過阻塞式語意。
