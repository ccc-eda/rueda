# 3.1 為什麼「有型別」還不夠

前一章，我們用 `fn`、`comb fn` 與 `task` 認識了 Fluxa 的基本語法，也完成了一個可測試元件。本章要處理的是一個看似簡單、卻會決定元件是否正確的問題：**一個值究竟可以有多大？**

對軟體工程師而言，型別常被視為除錯工具：字串不能拿來加整數、整數不能拿來和布林值比較。對硬體工程師而言，型別還多了一層含義——它決定暫存器需要多少位元、加法器需要多少個進位、乘法器會產生多寬的結果，以及某次截斷究竟是有意的模運算，還是未被察覺的溢位。

Fluxa 的核心選擇是：**先宣告值域，再由值域推導位寬。** 這使「程式會做什麼」與「硬體需要多少資源」有了可檢查的橋梁。你不必先寫 Verilog 的位寬註記，也不必依賴工具猜測每個算子的上下文寬度；只要來源值域能完整放入目標值域，Fluxa 就允許無損轉換，否則它要求你明確決定要回繞、飽和，還是讓檢查失敗。

本章的核心案例是四階 FIR 濾波器。我們會從輸入樣本的 `i8` 開始，一路推導係數、乘積、加法樹與最終輸出的型別。沿途出現的每個位數，都將有清楚的數學理由，而不是「看起來 `i16` 比較安全」。

## 學習目標

完成本章後，你應能夠：

1. 將 `uN`、`iN` 與一般 `int<lo..=hi>` 對應起來。
2. 依加、減、乘、位移規則推導運算式的值域與實際硬體寬度。
3. 在型別化 `let`、賦值、通道傳送、引數與回傳值等「落點」辨認窄化。
4. 正確選擇 `as`、`.wrap::<T>()`、`.sat::<T>()` 與 `.to::<T>()`。
5. 說明定點數的整數位、小數位、捨入方式與溢出策略。
6. 完成一張可供實作與審查使用的 FIR 位寬推導表。

---

先看一段看似沒有問題的程式：

```fluxa
fn add_byte(a: u8, b: u8) -> u8 {
    a + b
}
```

若只看原始碼，它似乎只做一件事：把兩個位元組相加並回傳一個位元組。但 `200 + 100` 是 `300`，而 `u8` 只能表示到 `255`。這個函式在某些輸入下會溢出。

傳統語言常把問題留到執行期或交給隱含規則：

- C 的整數提升可能先把 `uint8_t` 提升成 `int`，所以運算本身不溢出，真正危險的是之後塞回 `uint8_t` 的轉換。
- Verilog 與 SystemVerilog 常由上下文決定運算寬度，再默默截去多餘位元；同一段算式放在不同運算元或不同位元組長度中，可能產生不同結果。
- HDL 中的整數並沒有像 `int8_t` 那樣普遍而一致的有號／無號規則，設計者常需手動延伸、截斷並註解。

Fluxa 不採任一種隱含規則。`u8` 的語意非常明確：



$$
u8 \equiv \operatorname{int}\langle 0..=255\rangle
$$



因此 `a + b` 的來源值域是 `[0,510]`，不能直接落在一個只能容納 `[0,255]` 的目標上。程式必須把「加法結果先擴寬，最後如何縮小到 8 位元」說清楚。

這不是要求所有設計都使用最大位寬，而是要求每一次資訊遺失都成為可見決策：

- 如果目標介面就是 8 位元，而且超過 `255` 時要停在 `255`，使用飽和。
- 如果協議規定模 `256`，使用回繞。
- 如果介面不可能收到這樣的值，則應由型別或上游契約證明它永遠不會發生。

換句話說，**型別不只是值的標籤，而是值域契約。**
