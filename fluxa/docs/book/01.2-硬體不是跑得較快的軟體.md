# 1.2 硬體不是跑得較快的軟體

把 C 迴圈交給高階合成（HLS，High-Level Synthesis）工具，工具可以把迴圈展開，也可以保留迴圈並在電路中重用乘法器。工程師若只寫：

```c
for (int k = 0; k < 4; ++k) {
    acc += h[k] * x[n-k];
}
```

工具通常能推斷出許多資訊，但它仍然必須猜測幾個關鍵問題：

- 這個迴圈是要完全展開，還是每個乘加順序重用硬體？
- `x[n-k]` 是小型移位暫存器，還是 RAM 讀取？
- 外部資料是否可以每拍送入一個元素，還是本來就有較長的外部延遲？
- `acc` 應該在每個樣本後重置，還是要跨越多個樣本累加？
- 這段程式最後要接到哪一種介面？

猜測本身不是罪惡。問題在於，猜測的結果只有在「後設資料、報告與驗證」都看得見時，才適合拿來做硬體產品。

### 1.2.1 先寫 RTL 與用 pragma 請 HLS 猜

傳統的 RTL-first 流程把資料路徑與控制狀態直接寫出來，因此工程師對電路形狀有很強的控制力；代價是類型、位寬、握手、狀態機與測試都要人工維護，一個簡單的資料路徑也可能迅速膨脹成大量容易出錯的布林細節。

HLS-first 流程則用接近 C 的語言快速描述演算法，再以 pragma 與介面指示表達排程意圖。它的優點是迭代快，缺點是同一份程式可能因工具版本、目標時鐘與周邊介面不同而產生不同的硬體。特別危險的情況是：模擬結果正確，合成後吞吐或資源卻不符合預期。

Fluxa 採取的是較嚴格的契約優先觀點。設計者仍然要決定拓樸與排程，但必須把決定表達成可檢查的語意：

- 值域讓「這個值需要多少位元」成為型別的一部分；
- task 讓「哪一段行為是獨立程序」變得明確；
- channel 讓「程序之間交換什麼 token」變成可檢查的邊界；
- 排程描述讓「一次迭代何時啟動、哪些操作形成時序邊界」可以被推導與驗證。

語言不會替你做出最佳拓樸，但它能把「我想要什麼」與「工具猜了什麼」分開，讓錯誤在合成前就有機會被看見。

### 1.2.2 硬體是一組同時存在的資源

軟體可以無限地呼叫函式，把暫存器交給執行環境管理；硬體卻只有有限的乘加器、暫存器、記憶體與互連。每一個設計決策都在分配資源：

- **模組化**把重複的資料路徑封裝起來，但也可能引入握手延遲；
- **重用**用較長的時間換較小的面積；
- **管線化**把長路徑切成多個階段，通常可提高吞吐，代價是更多暫存器與較複雜的控制；
- **暫存器**隔離時序路徑，但也增加延遲；
- **記憶體**提供容量，卻引入埠數、讀寫延遲與排程限制。

所以，硬體設計不是「把演算法翻成另一套語法」，而是回答一個資源受限的即時系統問題：每個單位時間要完成多少工作，完成一筆工作需要多少時間，以及為此願意使用多少空間。
