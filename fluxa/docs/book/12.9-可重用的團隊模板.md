# 12.9 可重用的團隊模板

## 12.9.1 四份治理文件

一個可重用的 AI 輔助硬體專案，至少可以包含四份文件：

| 文件 | 內容 |
| --- | --- |
| `SPEC.md` | 契約、介面、型別、錯誤行為與資源目標 |
| `TASKS.md` | 可獨立驗收的工作項目與順序 |
| `CHECKLIST.md` | 語意、資源、驗證與交付檢查清單 |
| `DECISIONS.md` | 位寬、拓樸、II、介面等決策紀錄 |

這四份文件不是額外負擔，而是讓 agent 與人都能引用同一套事實。

## 12.9.2 `SPEC.md`

`SPEC.md` 應該包含：

- 元件介面與通道契約；
- 型別與最壞情況值域；
- 排程與資源目標；
- 錯誤行為與關閉責任；
- 驗收命令。

它是唯一事實來源。其他文件與測試都應引用它，而不是各自複製一份。

## 12.9.3 `TASKS.md`

把工作拆成可獨立驗收的項目，例如：

1. 建立 FIR 的 token 契約與測試；
2. 實作 4 階 FIR；
3. 加入 `pipeline(ii = 1)` 與平衡樹；
4. 執行 `reda check` 與 `sim`；
5. 合成並跑 `gatesim`；
6. 整理交付摘要。

每個項目都應該有明確的完成條件，而不是「寫完為止」。

## 12.9.4 `CHECKLIST.md`

檢查清單可以分成四類：

- **語意**：測試、邊界、關閉、錯誤；
- **資源**：位寬、累加器、FIFO、記憶體；
- **驗證**：sim、emu、gatesim、CI；
- **交付**：命令、版本、產物、限制。

檢查清單的價值在於它把「我們通常會記得的事」變成「每次都會檢查的事」。

## 12.9.5 `DECISIONS.md`

決策紀錄應包含：

- 決策內容；
- 理由；
- 替代方案；
- 影響範圍；
- 驗證方式。

例如：

> 選擇 `sat` 而非 `wrap`，因為產品要求輸出不得回繞；以邊界向量驗證。

有了決策紀錄，未來的人（或 agent）才知道某個選擇是有意的，而不是偶然留下的。

## 12.9.6 模板不是流程

最後，模板不是為了增加文件數量，而是為了讓重要資訊有固定位置。若某份文件長期沒有被使用，就應該簡化或移除。好的治理模板應該降低溝通成本，而不是製造更多表格。
