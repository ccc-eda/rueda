# 12.7 自動化驗證閘門

## 12.7.1 閘門的順序

一個完整的硬體驗證閘門可以分成下列階段：

```mermaid
flowchart LR
  A["格式/建置"] --> B["reda check"]
  B --> C["reda sim"]
  C --> D["reda emu"]
  D --> E["reda synth"]
  E --> F["reda gatesim"]
  F --> G["FPGA/ASIC 產物檢查"]
```

每一階段都應該有明確的通過條件，而不是只看退出碼。

## 12.7.2 每一層的通過條件

| 階段 | 通過條件 |
| --- | --- |
| 建置 | 工具鏈可用，版本符合 |
| `check` | 沒有未解釋的 E0301/E0401/E0501 等 |
| `sim` | 所有測試通過，輸出符合 oracle |
| `emu` | 與 `sim` 的斷言與 token 序列一致 |
| `synth` | 網表產生成功，資源在預算內 |
| `gatesim` | 與 `sim` 的結果一致 |
| 後端 | 位元流／GDS 產生，時序與規則檢查通過 |

若某一層有已知例外，應明確記錄原因與範圍，而不是直接跳過。

## 12.7.3 讓 agent 能重跑

閘門的價值在於可重跑。每個階段都應該：

- 用命令列而非手動操作；
- 輸出穩定格式（優先 JSON）；
- 保存命令與版本；
- 能在乾淨環境執行。

這樣 agent 才能重新執行並比較，而不是只能相信上一次的摘要。

## 12.7.4 失敗的處置

失敗時，閘門應該回答三個問題：

1. 哪一層失敗？
2. 哪個案例或哪個欄位不同？
3. 最小重現命令是什麼？

如果 CI 只輸出「失敗」，審查者與 agent 都會被迫猜測。

## 12.7.5 不要讓閘門變成形式

最後，閘門不是為了讓流程看起來完整。若某個階段長期沒有實際內容（例如只檢查檔案存在），就應該重新設計它，而不是讓它繼續產生虛假的安心感。閘門的每個階段都應該能指出「這一步證明了什麼」。
