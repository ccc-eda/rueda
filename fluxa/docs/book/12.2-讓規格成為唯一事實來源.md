# 12.2 讓規格成為唯一事實來源

## 12.2.1 規格不是一段散文

對 AI 與人類都一樣，模糊的規格會產生模糊的實作。可用的規格至少要包含：

- 模組介面：有哪些通道、方向、元素型別；
- token 契約：順序、數量、關閉行為；
- 錯誤行為：非法輸入、資源不足、溢位時怎麼辦；
- 資源目標：面積、吞吐量、延遲上限；
- 驗收命令：如何證明它符合規格。

這些欄位與第 11 章的「六個欄位」一致。差別在於，本章要求把它們寫成機器也能引用的形式。

## 12.2.2 從自然語言到可檢查條款

例如，把「這個 FIR 要能處理雜訊」改寫成：

- 輸入：`chan<i8>`，每拍最多一個 token；
- 輸出：`chan<i16>`，每個輸入對應一個輸出；
- 溢位：飽和到 `i16`；
- 頻率：目標 50 MHz；
- 驗收：`reda check` 無 E0301，`reda sim` 與 `gatesim ice40` 的 token 序列一致。

後者不只是更精確，也可以直接對應到命令與報告。AI agent 若拿到後者，就比較不會自由發揮出錯。

## 12.2.3 版本界線也要寫進規格

Fluxa 有已實作與未實作的功能。規格應該明確標示：

- 以哪個語言版本與工具版本為準；
- 哪些功能只能模擬，不能合成；
- 哪些診斷是暫定或部分實作。

例如，`stage` 層與 type generic 合成在 v1.0 不是現成能力。若規格沒有寫清楚，agent 很可能把未來功能當成現在可用，產生看似合理但不可合成的程式。

## 12.2.4 規格與測試的關係

測試不是規格的替代品，而是規格的執行版本。每一條可檢查的規格，都應該有對應的測試或命令：

| 規格條款 | 驗證方式 |
| --- | --- |
| 每個輸入一個輸出 | 計數比較 |
| 飽和策略 | 邊界向量 |
| 通道關閉 | 關閉時序測試 |
| 資源上限 | 合成報告 |
| 頻率目標 | 後端時序報告 |

沒有對應驗證的條款，通常會在整合時被忽略。

## 12.2.5 單一事實來源

最後，規格應該只有一份。若 README、註解、測試與口頭說明各有一套版本，AI 與人都會無所適從。實務上可以把規格放在版本控制中，並讓測試與命令直接引用它，而不是複製貼上。
