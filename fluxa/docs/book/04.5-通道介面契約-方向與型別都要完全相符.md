# 4.5 通道介面契約：方向與型別都要完全相符

Fluxa 要求通道的實際元素型別與 task 參數宣告的 `chan<U>` **完全相符**。即使 `i8` 的所有值都能放進 `i16`，`chan<i8>` 仍然不能接到 `chan<i16>`。

原因是通道跨越元件邊界時，型別不是只表示「目前放得下」，還表示硬體資料線的固定格式。允許隱式加寬會讓下列問題變得模糊：

- token 在 FIFO 中究竟佔 8 還是 16 位元？
- 接收端是否要補位元？
- 送端與收端是否真的使用相同協定？
- 合成後的埠寬由誰決定？

因此 Fluxa 選擇讓變成顯式操作。若確實需要加寬，應在 task 內明確轉換，讓型別變化留在元件內部：

```fluxa
task Widen(x: in chan<i8>, y: out chan<i16>) {
    for v in x {
        y.send(v.to::<i16>());
    }
}
```

刻意失敗的範例如下：

```fluxa
task Wide(x: in chan<i16>, y: out chan<i16>) {
    for v in x {
        y.send(v);
    }
}

task Net(x: in chan<i16>, y: out chan<i16>) {
    let (t, r) = chan::<i8>(depth = 2);
    spawn Wide(x, t);
    spawn Wide(r, y);
}
```

`Net` 建立的是 `chan<i8>`，卻把它交給要求 `chan<i16>` 的 `Wide`。模擬器會在 `spawn` 連線時指出類似以下的證據：

```text
the channel `c` carries i8, the parameter is chan<i16>
```

這和上一章的落點窄化是不同層次的問題：

- **落點窄化**關心「某個值能不能放進目標值域」；
- **通道型別不相容**關心「兩端是否使用同一種 token 格式」。

前者是值的問題，後者是介面的問題。兩者都必須在使用前修正。
