# 2.1 先看地圖：一個 Fluxa 程式由哪些東西組成？

> **本章目標**：寫出一個有明確契約、可行為模擬、也能送進硬體流程的 8 位元飽和倍增元件。你會先認識 Fluxa 的語法地圖，再把普通函式改造成可與其他程序連接的 `task`，最後用 `test` 建立一份可重現的證據。

上一章我們從一段順序程式走向空間資料流，知道硬體設計不是「把同一段程式跑得更快」，而是決定哪些資料可以同時流動、哪些地方必須保存狀態，以及元件何時把結果交給下一位消費者。那是觀念上的轉換；本章要把它落到 Fluxa 的語法。

閱讀本章時，請先記住一條主線：**Fluxa 的值有型別，型別最終就是位寬；Fluxa 的程序有兩種互補形式，函式表達局部計算，`task` 表達可參與資料流的程序；Fluxa 的測試不只是檢查函式回傳值，還要檢查通道上的 token 序列與關閉行為。**

本章以 Fluxa 語言規格 v1.0（2026-11-21）與 `rueda 0.7.0` 為準。閱讀完後，你應能分辨 `fn`、`comb fn`、`comptime fn`、`task`、`test` 各自適合表達什麼，也能寫出含輸入、輸出、錯誤條件與硬體代價的最小元件。

Fluxa 表面上像 Rust：分號、大括號、`let`、型別註記與 `match` 都相當熟悉；但它不是把 Rust 編譯到另一塊晶片上的語法糖。Fluxa 的語言核心是四層。

1. **值與型別**：整數由封閉值域描述，例如 `i8` 與 `u8`。第 3 章會正式推導位寬。
2. **函式與常數**：描述沒有外部副作用的計算，以及編譯期才決定的值。
3. **程序**：`task` 透過通道傳遞 token，可以和別的 `task` 形成 Kahn 程序網路。
4. **測試**：`test` 建立通道、啟動程序並驗證可觀察結果。

這四層可以畫成下面的地圖：

```text
                       ┌─────────────────────┐
                       │       test          │
                       │ 建立通道、spawn、斷言 │
                       └──────────┬──────────┘
                                  │ 驗證
             ┌────────────────────┼────────────────────┐
             ▼                    ▼                    ▼
      ┌────────────┐      ┌────────────┐      ┌────────────┐
      │    task    │◄────►│   channel  │◄────►│    task    │
      │ 程序／元件 │      │ 有界 FIFO  │      │ 程序／元件 │
      └─────┬──────┘      └────────────┘      └─────┬──────┘
            │                                         │
            │ 呼叫局部計算                             │
            ▼                                         ▼
      ┌────────────┐      ┌─────────────┐     ┌────────────┐
      │ fn/comb fn │      │    const    │     │  comptime   │
      │ 值級計算   │      │ 編譯期常數  │     │    fn       │
      └────────────┘      └─────────────┘     └─────────────┘
```

這張圖也預告本章的寫作順序：先看最小檔案與命令，再看頂層項目，接著看值和控制流，然後把函式改成 `task`，最後處理泛型、專案組織與完整測試。

### 一個最小但不是玩具的 Fluxa 程式

先把語法骨架擺出來：

```fluxa
// 單行註解
/* 區塊註解可以巢狀：
   /* 內層註解 */
*/

const WIDTH: u8 = 8;

fn twice(x: u8) -> u9 {
    x * 2
}

test twice_works {
    assert twice(21) == 42;
}
```

這段程式有三個部分：

- `const WIDTH` 是編譯期常數。`u8` 不是「一個很大的整數」，而是 `0..=255` 的值域。
- `twice` 是具型別的一般函式；函式最後一個運算式是回傳值。
- `twice_works` 是獨立測試。測試失敗會讓 `reda sim` 以非零結束碼結束。

注意 `x * 2` 的結果值域可推導為 `0..=510`，所以回傳型別寫成 `u9`，而不是把結果硬塞回 `u8`。若元件最後真的只需要 8 位元，轉換策略就不能省略：

```fluxa
fn twice_wrap(x: u8) -> u8 {
    (x * 2).wrap::<u8>()
}
```

若你要的是「上限是 255」的縮放器，就應使用 `.sat::<u8>()`。本章先不深入窄化公式；第 3 章會完整說明為什麼不能把硬體位寬當成可隨意選擇的程式風格。

### `.fx` 檔與命令列

Fluxa 原始碼使用 `.fx` 副檔名。把上面的內容存成 `twice.fx`，可以執行：

```sh
reda sim twice.fx
reda sim twice.fx --test twice_works
reda list twice.fx
```

三個命令的責任不同：

- `reda sim` 執行檔案中的 `test`。
- `--test NAME` 只執行指定測試；同一參數可以重複使用。
- `reda list` 列出合併後程式裡有哪些測試，不執行它們。

`reda sim` 的輸出大致如下：

```text
fluxa: twice.fx — 1 task/function(s), 1 test(s)
[PASS] twice_works (0.001s)
1 passed, 0 failed
```

命令列選項還包括 `--coop`、`--trace` 與 `--stats`。本章只需要記住：`--coop` 是另一種排程器，第五章會證明它與預設排程器必須產生相同結果。`--trace` 顯示每次 `send`／`recv`，`--stats` 顯示各通道的 token 數、FIFO 深度與最大佔用。

> **版本提示**：本章的 `comb fn`、`comptime fn`、const generic 與 `test` 都以 v1.0 規格描述。早期 v0.1 是設計草案；不要把其中尚未實作的 `stage`、`iface`、`schedule` 或 Graph API 當成現有保證。
