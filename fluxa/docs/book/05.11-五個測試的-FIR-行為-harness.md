# 5.11 五個測試的 FIR 行為 harness

現在把本章方法付諸實作。我們沿用第 4 章的 `Fir4`，另外加一個「總增益大於 1」的變體來刻意產生飽和。為什麼需要變體？因為標準係數



$$
0.125 + 0.375 + 0.375 + 0.125 = 1
$$



且所有樣本都在 `i8` 範圍內。這個 FIR 的每個輸出是四個樣本的加權平均，在數學上不會超出樣本的最大值或最小值；因此標準 FIR 根本不會進入 `i8` 飽和分支。若測試宣稱「驗證飽和」卻永遠沒有可飽和的值，它其實沒有驗證到那條路徑。

下面的 harness 保留標準 FIR，另以總增益 1.5 的 `Fir4Gain` 測試飽和。這不是改變標準 FIR 的契約，而是明確建立一個有不同增益契約的測試元件。

### 5.11.1 被驗元件與觀察器

```fluxa
const COEF: [fixed<1, 7>; 4] = [0.125, 0.375, 0.375, 0.125];
const GAIN_COEF: [fixed<1, 7>; 4] = [0.25, 0.5, 0.5, 0.25];

task Fir4(x: in chan<i8>, y: out chan<i8>) {
    let mut hist: [i8; 3] @reg = [0; 3];

    pipeline(ii = 1) for s in x {
        let win: [i8; 4] = concat([s], hist);
        let acc = (0..4).unrolled()
                         .map(|k| win[k] * COEF[k])
                         .tree_sum();
        hist = win[0..3];
        y.send(acc.to::<i8>(round = nearest, ovf = sat));
    }
}

// 測試專用：總增益為 1.5，刻意讓大輸入飽和到 127。
task Fir4Gain(x: in chan<i8>, y: out chan<i8>) {
    let mut hist: [i8; 3] @reg = [0; 3];

    pipeline(ii = 1) for s in x {
        let win: [i8; 4] = concat([s], hist);
        let acc = (0..4).unrolled()
                         .map(|k| win[k] * GAIN_COEF[k])
                         .tree_sum();
        hist = win[0..3];
        y.send(acc.to::<i8>(round = nearest, ovf = sat));
    }
}

// Observe 轉發每個結果，並在輸入串流結束後回報總數。
// count 被送出，代表 Observe 已看見 FIR 輸出通道關閉。
task Observe(
    x: in chan<i8>,
    y: out chan<i8>,
    count: out chan<u8>
) {
    carry n: u8 = 0;
    for v in x {
        n += 1;
        y.send(v);
    }
    count.send(n);
}
```

`Observe` 同時提供兩類 oracle：

- `y` 上的每個 token 驗證值與順序；
- `count` 驗證 token 數量，並間接驗證 FIR 輸出已關閉。

注意 `count` 是在 `for v in x` 結束後才送出。`for` 只有在輸入通道已關閉且 FIFO 已清空時才結束，所以成功收到 `count` 是相當強的關閉證據。

### 5.11.2 零輸入

```fluxa
test fir4_zero {
    let (tx, rx) = chan::<i8>(depth = 4);
    let (tf, rf) = chan::<i8>(depth = 4);
    let (to, ro) = chan::<i8>(depth = 4);
    let (tc, rc) = chan::<u8>(depth = 1);

    spawn Fir4(rx, tf);
    spawn Observe(rf, to, tc);

    for _ in 0..4 {
        tx.send(0);
    }
    tx.close();

    for _ in 0..4 {
        assert ro.recv() == 0;
    }
    assert rc.recv() == 4;
}
```

零輸入同時確認初始三個歷史樣本為零，以及零 token 不會被漏掉。

### 5.11.3 最大值

```fluxa
test fir4_max {
    let (tx, rx) = chan::<i8>(depth = 4);
    let (tf, rf) = chan::<i8>(depth = 4);
    let (to, ro) = chan::<i8>(depth = 4);
    let (tc, rc) = chan::<u8>(depth = 1);

    spawn Fir4(rx, tf);
    spawn Observe(rf, to, tc);

    for _ in 0..4 {
        tx.send(127);
    }
    tx.close();

    assert ro.recv() == 16;
    assert ro.recv() == 64;
    assert ro.recv() == 111;
    assert ro.recv() == 127;
    assert rc.recv() == 4;
}
```

四個期望值分別來自加權和 `15.875`、`63.5`、`111.125`、`127`，經 `nearest` 捨入後得到整數結果。

### 5.11.4 最小值

```fluxa
test fir4_min {
    let (tx, rx) = chan::<i8>(depth = 4);

    assert ro.recv() == -64;
    assert ro.recv() == -112;
    assert ro.recv() == -128;
    assert rc.recv() == 4;
}
```

最小值案例同時確認有號乘法、負的定點乘積、負捨入與 `i8` 下邊界都沒有被誤判。

### 5.11.5 明確的飽和路徑

```fluxa
test fir4_saturation {
    let (tx, rx) = chan::<i8>(depth = 4);
    let (tf, rf) = chan::<i8>(depth = 4);
    let (to, ro) = chan::<i8>(depth = 4);
    let (tc, rc) = chan::<u8>(depth = 1);

    spawn Fir4Gain(rx, tf);
    spawn Observe(rf, to, tc);

    for _ in 0..4 {
        tx.send(127);
    }
    tx.close();

    assert ro.recv() == 32;
    assert ro.recv() == 95;
    assert ro.recv() == 127;  // 未飽和值為 158.75
    assert ro.recv() == 127;  // 未飽和值為 190.5
    assert rc.recv() == 4;
}
```

第三個輸出真正超過 `i8` 上界，因此這個測試有證據證明 `ovf = sat` 分支被執行，而不是只在程式中寫了一個永遠走不到的 `sat`。

### 5.11.6 關閉與空串流

```fluxa
test fir4_close {
    let (tx, rx) = chan::<i8>(depth = 4);
    let (tf, rf) = chan::<i8>(depth = 4);
    let (to, ro) = chan::<i8>(depth = 4);
    let (tc, rc) = chan::<u8>(depth = 1);

    spawn Fir4(rx, tf);
    spawn Observe(rf, to, tc);

    // 不送任何樣本，直接宣告輸入結束。
    tx.close();

    // Observe 只有在 FIR 輸出關閉後才能送出 count。
    assert rc.recv() == 0;
}
```

這個案例不斷言「通道中沒有某個值」，因為 task 層沒有 `try_recv` 或 `empty`。它改用一個可觀察的結束事件：收到 `count == 0`。若 FIR 因某種錯誤沒有關閉輸出，`Observe` 不會結束，測試會以等待停滯或死結診斷失敗。

這個例子顯示，驗證「沒有 token」不一定需要非阻塞查詢；常常可以設計一個由關閉事件觸發的完成通知。

### 5.11.7 執行完整 harness

把上述內容放在 `fir_behavior.fx`，執行：

```sh
reda sim fir_behavior.fx
reda sim --coop fir_behavior.fx
reda sim --test fir4_saturation --trace --stats fir_behavior.fx
```

第一條驗證全部案例，第二條驗證同一組案例在合作式排程下仍成立，第三條則把注意力集中到飽和案例。

CI 還可保存每個命令的退出碼與 `--stats`：

```text
native: 5 passed, 0 failed
coop:   5 passed, 0 failed
```

不要只比較這兩行總結；較好的做法是讓測試工具另外保存逐通道 token 投影。Fluxa v1.0 目前的 `--trace` 是診斷輸出，不是正式的 golden-file 比較介面。若團隊要把它納入自動差異測試，應在工具端把事件依通道分組，並只對有語意需求的通道順序做 golden comparison。
