# 3.3 值的落點：型別真正被檢查的地方

如果一個運算式產生 `300`，它並不會立刻因為「看起來像 8 位元」而壞掉。真正決定它能否存活的地方，是這個值要**落點**到何種型別。Fluxa 把下列位置視為型別範圍的落點：

| 落點 | 例子 |
|---|---|
| 型別化 `let` 的初始值 | `let x: u8 = expr;` |
| 賦值 | `x = expr;` |
| 複合賦值 | `x += expr;` |
| 通道傳送 | `tx.send(expr);` |
| 函式或任務引數 | `f(expr);` |
| 回傳值 | `return expr;` |
| 陣列元素 | `a[i] = expr;` |

判斷原則只有一條：

> 來源值域若完整包含於目標值域，便可無損落點；否則就是窄化，必須明確轉換。

例如：

```fluxa
fn widen_ok(x: i8) -> i16 {
    x                 // i8 ⊆ i16，安全
}

fn unsigned_is_not_widening(x: i8) -> u16 {
    x                 // 錯：-128..=127 不完整包含於 0..=65535
}
```

`i8` 到 `i16` 安全，是因為 `i16` 的兩補數可以容納全部 `i8` 值。`i8` 到 `u16` 卻不能直接做零延伸：負值沒有對應的無號表示，零延伸會把 `-1` 變成 `65535`。這正是「物理上放得下」與「語意上可無損轉換」不一定相同的地方。

同樣地，`u8` 的 `0..=255` 可以安全落點到 `i16`，因為 `i16` 仍能表示每個非負值；反方向的 `i8` 則不行。

### 一個刻意失敗的窄化案例

```fluxa
test implicit_narrowing {
    let a: u8 = 200;
    let b: u8 = 100;
    let c = a + b;     // c 的值域是 0..=510，需要 9 位元
    let d: u8 = c;     // E0301：0..=510 放不進 0..=255
}
```

`reda sim` 若真的執行到 `300`，會報告類似：

```text
E0301: value 300 does not fit u8 (range 0..=255)
```

`reda check` 則不必等測試執行：它以區間分析推導 `c` 的來源範圍，指出 `0..=510` 無法放入 `u8`，並建議使用至少 `u9`，或明確選擇 `.sat::<u8>()`、`.wrap::<u8>()`。

這個案例揭示了兩種互補的證明方式：

- 行為模擬證明「這個測試真的到達該值時會發生什麼」。
- 靜態檢查證明「在目前已知的所有可能輸入下，來源範圍無法容納於目標」。

靜態分析是保守的；分析無法證明安全，不代表一定會錯，只代表還需要更強的契約、測試或人工推理。
