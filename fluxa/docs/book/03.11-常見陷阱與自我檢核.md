# 3.11 常見陷阱與自我檢核

在提交 Fluxa 元件前，可以用下列問題快速檢查位寬設計。

### 檢查一：每個外部值都有明確界線嗎？

- 通道元素是 `u8`、`i16`，還是其實只允許 `0..=99`？
- 參數的範圍是否排除了不可能的值，例如除數是否排除零？
- 係數是小數嗎？若是，已經量化到多少小數位？

### 檢查二：每個運算結果都知道自己有多寬嗎？

- 加、減、乘之後是否用足夠寬的型別承接？
- 乘積是否保留完整結果，還是過早塞回窄暫存器？
- 移位後的範圍是否仍符合下一級契約？

### 檢查三：每一次資訊遺失都明確嗎？

- 超過上限時要飽和、回繞，還是讓模擬期 check 失敗？
- 捨去小數位時要截斷、最近捨入，還是 ties-to-even？
- 硬體是否需要主動回報 overflow？若需要，錯誤路徑在哪裡？

### 檢查四：位元與整數沒有混用嗎？

- `bit` 與 `bool` 是否用在正確的位置？
- 位元切片是否有清楚的端點與符號／零延伸規則？
- `bits<N>` 是否只承載位元資料，而沒有被當成整數做算術？

### 檢查五：推導表能否讓另一位工程師重做一次？

一張合格的 FIR 位寬表不應只有「輸入 `i8`、輸出 `i8`」。它至少要回答：

- 每個乘積與部分和的來源範圍是什麼？
- 為什麼需要這個位寬？
- 哪一個位置發生捨入？
- 哪一個位置發生飽和或回繞？
- 若改成另一種實作，哪些地方會增加面積或延遲？

能回答這些問題，位寬推導才不只是註解，而是一份可審查的硬體契約。

## 本章結論

Fluxa 的整數不是「先選一個位數，再祈祷值沒有太大」，而是「先宣告值域，再推導位寬」。這一個改變，將軟體式的型別檢查延伸成硬體的資源規格：

- `uN` 與 `iN` 是封閉整數值域的簡寫。
- 加、減、乘與移位都有明確的區間推導規則。
- 型別化 `let`、賦值、通道傳送、引數與回傳值是值的落點。
- 無損落點可以自動進行；窄化必須明示 `as`、`.wrap`、`.sat` 或 `.to` 的策略。
- `fixed<I,F>` 把小數尺度納入型別，捨入與溢出處理也成為可驗證契約。
- FIR 的乘積、加法樹與輸出寬度，都應能從資料流一路推導，而不是靠工程師猜測。

現在，每個 task 的介面不只說明「會收到什麼資料」，還能說明「資料可能有多大、允許做什麼運算、超界時怎麼辦」。下一章要解決另一個組合問題：如何把這些具有明確型別的元件接在一起。

第 4 章將引入 Kahn 通道。我們會把來源、FIR 與消費者組成程序網路，討論 token、FIFO、端點所有權、背壓與死結。屆時，型別不只是單一元件內的數學問題，也會成為元件之間可組合的介面契約。
