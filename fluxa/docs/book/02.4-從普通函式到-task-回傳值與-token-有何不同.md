# 2.4 從普通函式到 task：回傳值與 token 有何不同？

先看一個普通函式：

```fluxa
fn double(x: u8) -> u8 {
    (x * 2).sat::<u8>()
}
```

它接受一個值，回傳一個值。呼叫端必須同步取得結果：

```fluxa
let y = double(x);
```

現在把它改寫成 task：

```fluxa
task Double(x: in chan<u8>, y: out chan<u8>) {
    for v in x {
        y.send((v * 2).sat::<u8>());
    }
}
```

兩者計算的是同一件事，但介面模型完全不同。

| 比較 | `fn double(x)` | `task Double(x, y)` |
| --- | --- | --- |
| 資料量 | 每次一個值 | 一串 token |
| 等待方式 | 呼叫等到函式回傳 | `recv`／`send` 可阻塞 |
| 背壓 | 無 | FIFO 滿時 producer 阻塞 |
| 組合性 | 巢狀呼叫形成順序鏈 | 通道形成程序網路 |
| 輸出邊界 | 沒有串流結束概念 | `close` 表達 end-of-stream |
| 硬體意義 | 資料路徑中的一段計算 | 帶 handshake 的元件／程序 |

### 通道參數的方向

任務參數可以標示 `in` 或 `out`：

```fluxa
task Double(
    x: in chan<u8>,
    y: out chan<u8>
) { /* ... */ }
```

- `in chan<u8>` 參數需要一個 `chan<u8>` 的**接收端**。
- `out chan<u8>` 參數需要一個 `chan<u8>` 的**傳送端**。

方向不是由變數名稱猜測，而是元件契約的一部分。合成時，它也決定哪些埠是輸入、哪些是輸出。

通道元素型別必須完全相符。這個程式會失敗：

```fluxa
// 錯誤：x 實際攜帶 i8，參數卻要求 chan<i16>
task Wide(x: in chan<i16>) {
    for v in x {
        // v: i16
    }
}
```

如果呼叫端傳入 `chan<i8>`，模擬器會在 `spawn` 時報錯，而不是在 FIFO 裡默默截掉 8 位元。

### 為什麼一定要用通道，而不是 task 內部直接呼叫函式？

因為「程序」和「計算」處於不同抽象層：

- 一段乘法、加法、位元選擇，通常是函式。
- 一個滤波器、一個串流轉接器、一個仲裁器，通常是 task。
- 兩個 task 之間的邊界，是 token 契約與背壓機制。

如果把所有東西都寫成函式呼叫，資料流會退回單一時間線。如果把所有東西都寫成 task，即使只是一次加法，也會付出通道、FIFO 與 handshake 的成本。好的 Fluxa 設計要在這兩者之間清楚分界。

### `spawn` 移動端點，而不是複製端點

```fluxa
let (tx, rx) = chan::<u8>(depth = 4);
let (ty, ry) = chan::<u8>(depth = 4);
spawn Double(rx, ty);
```

`spawn Double(rx, ty)` 把 `rx` 與 `ty` 的所有權交給 `Double`。呼叫端之後不能再用 `rx` 或 `ty`。這是 Fluxa 的線性所有權規則：通道端點不是可以到處傳的普通值。

這個限制不是為了讓語言難用，而是防止兩個程序同時操作同一端點，破壞 FIFO 的邏輯順序。它也是第四章的主題；本章只需形成正確習慣：

> **建立通道 → 啟動 task → 保留自己仍擁有的端點。**

### 關閉語意

Task 結束時會自動關閉它仍擁有的輸出端點。測試仍可明確呼叫 `tx.close()` 說明「資料已送完」。關閉後，FIFO 中尚未接收的 token 仍然可以被取走；只有 FIFO 清空且通道已關閉時，`for v in rx` 才結束。

這讓「沒有更多資料」成為可驗證的契約，而不是靠猜測輸入長度。
