# 5.12 這個 harness 還沒有證明什麼？

五個測試通過，是良好的第一層證據，但不是完整證明。理解 oracle 的盲點，和理解它能證明什麼同樣重要。

### 5.12.1 它沒有證明所有輸入序列都正確

零、最大與最小只覆蓋三種常數序列。下列行為仍可能藏着錯誤：

- 非對稱序列，例如 `[127, -128, 127]`；
- 只送一個樣本後立即關閉；
- 很長串流造成累加器或位寬問題；
- 來源與 FIR 的速率差很大的情境。

至少還應加入一個脈衝輸入與一個交錯正負值案例。脈衝輸入尤其適合檢查係數順序：只送一個 `64`，標準 FIR 的第一個輸出應為 `8`，而不是 32 或 56。

### 5.12.2 它沒有證明實際硬體延遲與吞吐

行為模擬證明的是 token 對應與數值，不是 FSM 用了幾個狀態、資料路徑是否每拍可接受一個 token，或目標 FPGA 是否達到時序。第 7～9 章才處理這些問題。

### 5.12.3 它沒有證明所有未執行路徑安全

模擬器精確計算 120 位元整數，但一次執行只走過具體測試向量。例如某個只有 `x == 100` 時才執行的窄化，在其他測試中不會被碰到。第 6 章的靜態值域分析會把這類錯誤提前到執行前。

### 5.12.4 它沒有證明沒有資料競爭

Fluxa 的線性端點規則讓 task 層沒有競爭式接收；但若設計團隊繞過語言、在外部共享可變狀態，行為模擬器不會替你提供硬體級 race detector。測試仍應遵守語言提供的所有權邊界。

### 5.12.5 它不是形式驗證

一組測試只能證明被執行到的案例符合 oracle。形式驗證會對所有符合前提的輸入與狀態建立命題；本章建立的是可重現、可擴充的 oracle 基礎。若產品需要形式保證，仍應在適當層級加入 SVA/形式工具或等價驗證。

因此，「五個測試通過」的正確措辭是：

> 這五個已指定 token 情境，在原生與合作式排程下，皆產生預期的值、順序、數量與關閉結果。

而不是：

> 這個 FIR 已被證明永遠正確。
