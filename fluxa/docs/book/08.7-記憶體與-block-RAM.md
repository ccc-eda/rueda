# 8.7 記憶體與 block RAM

## 8.7.1 什麼時候該用 `mem`，而不是陣列

暫存器陣列在硬體中對應一排正反器。長度很小的表（例如四個 FIR 歷史樣本、八個係數）用正反器很合理；但長度一上千，正反器會消耗大量面積，而且多工器會形成又深又寬的選擇邏輯。

Fluxa 提供的記憶體型別是：

```text
mem<T, N>
```

其中 `T` 是元素型別，`N` 是元素數量，以 `m[i]` 形式存取。當記憶體只以簡單的索引讀寫形式使用時，合成器可以把它映射為 block RAM；其他較複雜的存取形式可能退回暫存器陣列，並產生警告。

判斷原則可以寫成一句話：

> 小的、需要同時多埠存取的狀態用正反器；大的、以單一讀寫埠為主的資料用 block RAM。

## 8.7.2 一個 BRAM 友善的形狀

最容易被映射成 block RAM 的形式，是把索引直接放在記憶體名稱後方，而且不要在一個迭代內對同一個記憶體做多次不相關的存取：

```fluxa
mem<i8, 1024> line;

for i in 0..1024 {
    line[i] = input.recv();
}

for i in 0..1024 {
    out.send(line[i]);
}
```

這種「一個位址、一次讀或一次寫」的規律，讓工具能把整個陣列放進一塊記憶體，而不是攤成上千顆正反器。

相對地，若位址是由複雜的資料相依運算決定，或在同一輪內同時讀多個不同位址，工具就必須提供更多埠；而一般 block RAM 的埠數有限，於是只能退回暫存器陣列或報資源錯誤。

## 8.7.3 讀寫埠的資源模型

Fluxa v1.0 的靜態資源模型把一個記憶體視為一個讀埠與一個寫埠。E0401 會檢查 `pipeline` 迴圈的一輪是否在同一記憶體上使用了超過可用埠數的存取：

$$
\text{reads}(m)\le ii,\qquad \text{writes}(m)\le ii
$$

這裡的 `ii` 是排程要求的啟動間隔。若一輪需要讀兩個不同位址，而模型只有一個讀埠，就可能被判定為資源超用。修正方向通常不是盲目加大記憶體，而是：

- 把兩個讀取拆到不同迭代或不同階段；
- 使用兩個獨立記憶體（bank）；
- 重新安排演算法，讓同一輪只需要一個讀取。

## 8.7.4 記憶體不是「免費的變數」

使用 `mem` 時，有幾個語意與成本必須一起考慮：

1. **讀取需要時間**：在硬體中，記憶體讀取通常佔一個時脈。因此把 `mem` 存取直接塞進單週期 `pipeline` body，可能無法形成合法的管線狀態。
2. **初值與參數化**：若記憶體內容是常數表（例如係數或程式碼），可以用 `--param` 把陣列固定成 ROM，讓它成為合成時的常數，而不是可寫記憶體。
3. **容量與深度**：FIFO 深度、記憶體深度與 bank 數量都會反映在面積報告中；「先開大一點」往往只是把問題延後到佈局繞線或時序階段。

## 8.7.5 從資源報告回推設計

合成報告通常會列出 LUT、FF、DSP、BRAM 與各 task 實例的閘數。若看到某個小陣列佔用了大量 FF，第一個問題應該是：

- 它是否被當成需要多埠同時存取的暫存器陣列？
- 它的索引形式是否讓工具無法推論成 block RAM？
- 它的深度是否真的需要這麼大？

反過來，若看到 BRAM 數量出乎意料地多，則要檢查是否把本可共享的儲存拆成多個獨立記憶體。資源報告不是成績單，而是提示你回去檢查程式形狀與架構決策的證據。
