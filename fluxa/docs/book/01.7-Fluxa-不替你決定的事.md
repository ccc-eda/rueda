# 1.7 Fluxa 不替你決定的事

契約優先不代表自動最佳化。Fluxa 能讓某些假設變得明確、能讓錯誤提早出現，但以下決定仍然屬於設計者。

### 1.7.1 拓樸與排程

四階 FIR 可以完全展開、部分展開、序列 MAC，也可以用 DSP block 的特定配置；這取決於目標頻率、資源、功耗與延遲要求。語言可以描述「我要每拍一個」或「我可以四拍一個」，卻不能從演算法名稱推斷你的產品目標。

### 1.7.2 位寬與累加策略

輸入是 16 位元，不代表乘積、累加與輸出也可以是 16 位元。你要決定係數格式、定點小數位、累加器是否比資料路徑更寬，以及最後是飽和、回繞還是報錯。第 3 章會用數學範圍把這些選項攤開。

### 1.7.3 介面與生命週期

外部交易單位是單一樣本、幀還是一整個區塊？來源關閉時要沖刷嗎？接收端停滯時資料停在哪裡？重置時正在處理的樣本怎麼辦？這些都是 token 契約的一部分，而不是工具可以從型別猜出的細節。

### 1.7.4 目標指標

「很快」不是可驗收的規格。至少要把它拆成：目標吞吐量、最大延遲、可用資源上限、允許的功耗或面積，以及在負載改變時的行為。沒有這些數字，合成報告只能描述結果，不能判斷結果是否合格。

可以把它整理成一張決策表：

| Fluxa 能表達或檢查的 | 設計者仍要決定的 |
| --- | --- |
| 值域與明確的窄化策略 | 實際的係數與樣本精度 |
| task 的責任與狀態邊界 | 要拆成幾個 task、哪些狀態共用 |
| token 型別、順序、關閉、背壓 | 通道深度與整體拓樸 |
| 排程意圖與可觀察的結果 | II、延遲、面積與時脈目標 |
| 行為與硬體的等價性要求 | 哪一組測試足以代表產品環境 |

語言提供的是**可檢查的表達方式**，不是自動產出最佳電路的魔法。Fluxa 的價值在於：每當你做出一個選擇，都可以把它放進契約裡，並讓後面的檢查與驗證去追問它。
