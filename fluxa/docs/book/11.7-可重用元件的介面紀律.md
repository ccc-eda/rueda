# 11.7 可重用元件的介面紀律

## 11.7.1 命名要說明契約

一個可重用元件的名字，應該讓人看出：

- 它做什麼；
- 它處理什麼型別；
- 它的資料流假設是什麼。

例如 `Fir4`、`Window3x3`、`SystolicMatmul` 比 `Core`、`Engine`、`Thing` 更能傳達資訊。參數名稱也一樣：`AW`、`CW`、`N` 應有文件說明，而不是留給讀者猜。

## 11.7.2 參數要有意義

參數不是越多越好。每個參數都應該回答一個問題：

- 這個參數改變什麼硬體結構？
- 它的合法範圍是什麼？
- 它對位寬、面積、吞吐量有什麼影響？
- 預設值是什麼，為什麼？

如果一個參數只影響內部常數，而不影響介面或契約，可能不需要暴露成參數。

## 11.7.3 關閉責任要明確

每個通道元件都要定義：

- 誰負責關閉輸出通道？
- 輸入關閉後，還有多少資料要處理？
- 若上游沒有關閉，元件會不會永遠等待？
- 若下游提前拒絕，元件如何回應？

關閉責任不清楚，是通道網路最常見的整合問題之一。

## 11.7.4 錯誤模式要可預測

錯誤模式應明確定義，例如：

| 情況 | 行為 |
| --- | --- |
| 輸入型別不符 | 編譯期拒絕 |
| 值域可能溢位 | `reda check` 報告 E0301 |
| 同一通道一輪用兩次 | E0401/E0412 |
| 資源不足 | 後端報告錯誤或降級 |
| 上游過早關閉 | 元件依契約結束或報錯 |

可預測的錯誤模式讓呼叫端能寫出正確的錯誤處理，而不是靠猜測。

## 11.7.5 文件與測試一起交付

一個可重用元件的交付物應包含：

- 介面與契約；
- 型別與資源假設；
- 至少一組正常與邊界測試；
- 已知限制；
- 版本與相容性說明。

只給程式碼而不給契約，等於要求下一位使用者重新推導你的假設。那會讓重用變成風險，而不是效率。

## 11.7.6 不要過早抽象

最後一個紀律是：不要為了「可能重用」而過早抽象。先把一個案例做對、做清楚，再從中提煉出真正重複的模式。過早的抽象通常會留下太多參數與太少驗證，最後比直接寫還難維護。
