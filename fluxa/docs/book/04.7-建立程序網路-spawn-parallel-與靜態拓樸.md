# 4.7 建立程序網路：`spawn`、`parallel` 與靜態拓樸

### 4.7.1 `spawn`：啟動但不等待

`spawn` 啟動一個 task，呼叫端不會等待它完成：

```fluxa
spawn Fir4(rx, ty);
// 這裡可以繼續做別的事
```

這表示 `spawn` 建立的是一條生命週期分支，而不是一條同步函式呼叫。若父 task 很快結束，它擁有的輸出端會被關閉；子 task 仍可繼續運作，直到自己的輸入、輸出與狀態都完成既定工作。

這種行為正適合資料流元件：啟動 FIR 後，測試主體可以立即送入樣本，並與 FIR 同時推進。

### 4.7.2 `parallel`：同時啟動並等待全部結束

若要明確表達「這幾個 task 要一起啟動，而且父 task 要等它們全部完成」，可以使用：

```fluxa
parallel {
    ProducerA(out_a);
    ProducerB(out_b);
}
```

`parallel` 區塊只允許 task 呼叫，而且會等待區塊內所有 task 結束才往下走。`spawn` 則只啟動、不等待。

這個差別看似只是控制流程上的便利，實際上卻會改變資料流的結束條件：

- 使用 `spawn` 後，父 task 可以繼續傳送資料，或在子 task 尚未完成時結束自己的其他工作。
- 使用 `parallel` 後，父 task 必須等到所有子 task 完成，才能執行下一段。

例如，一個測試主體需要同時啟動 FIR 與另一個分支，可以寫成：

```fluxa
parallel {
    Fir4(rx, ty);
    Monitor(status_rx);
}
```

但若 `Monitor` 等待一個永遠不會關閉的狀態通道，而 FIR 正在等待同一個有限 FIFO 的空間，這個 `parallel` 不會神奇地解決背壓；它只會讓父 task 等待得更久。`parallel` 是生命週期工具，不是死結修復器。

### 4.7.3 靜態迴圈建立固定數量的實例

Fluxa 的硬體網路必須能在編譯期展開。因此可以用固定次數的迴圈建立通道與 task 實例：

```fluxa
const N: u32 = 4;

let links = array(N, |_| chan::<i8>(depth = 2));

for i in 0..N {
    spawn Link(
        links[i].1,
        links[i + 1].0
    );
}
```

概念上，這會形成：

```mermaid
flowchart LR
    A["links[0]"] --> B["links[1]"] --> C["links[2]"] --> D["links[3]"]
```

這裡「固定形狀」是關鍵：編譯器知道要建立幾個 task、幾條 FIFO，以及每條 FIFO 的方向與深度。相反地，「執行期才決定 `spawn` 幾次」目前不受合成支援；硬體不能把一個未知的迴圈次數直接變成固定網路。

`array(N, |_| chan::<i8>(depth = 2))` 的每個元素都是一組通道端點。`links[i].0` 是傳送端，`links[i].1` 是接收端。把相鄰端點交給不同 task，就能在靜態拓樸中建立資料流鏈。

### 4.7.4 `spawn` 與 `parallel` 的選擇表

| 需求 | 應使用的語法 | 父 task 的行為 |
| --- | --- | --- |
| 啟動背景處理程序，繼續自己的流程 | `spawn Task(...)` | 不等待子 task |
| 同時啟動多個 task，並在後續工作前等齊 | `parallel { A(...); B(...); }` | 等全部完成 |
| 建立固定數量的鏈路或陣列 | 靜態迴圈加 `spawn` | 網路形狀在編譯期已知 |
| 把同一 token 交給多個分支 | `broadcast(rx, n)` | 每個分支收到完整序列 |
| 讓多個 worker 競爭工作 | 沒有安全的隱式做法 | 必須另訂靜態分配協定 |
