# 5.1 學習目標

第 4 章把演算法組成了 Kahn 程序網路：來源產生 token，FIR 與消費者透過有界 FIFO 交換資料。現在要回答一個看似簡單、卻決定整套硬體開發方法是否可靠的問題：

> 當多個 task 同時存在，而排程器可以選擇先執行誰時，我們究竟應該把「程式跑完」解讀成什麼？

如果答案只是「某次執行得到某個最後答案」，測試很容易把偶然的執行順序當成正確行為。更可靠的答案是：對同一份 token 輸入，所有合法排程都必須產生相同的**邏輯 token 序列**。排程可以改變等待多久、何時送達，卻不能改變資料的內容、順序、數量與關閉語意。

這一章會把行為模擬器拆成 AST 直譯器、共享世界狀態與排程器三層，比較原生執行緒排程與單執行緒合作式排程，建立以 `assert`、`--trace` 與 `--stats` 為核心的行為 oracle。最後，我們會把第 4 章的 FIR 網路擴充成五個可重現測試，涵蓋零、最大值、最小值、飽和與通道關閉。

完成本章後，你應該能夠：

1. 說明 AST 直譯器、共享世界狀態與排程器各自負責什麼。
2. 解釋預設原生排程器與 `--coop` 合作式排程器為何必須得到相同的邏輯結果。
3. 區分「同一通道的順序」與「不同通道之間沒有全域順序」。
4. 使用 `assert` 驗證值、順序、token 數量與通道關閉，而不只檢查最後一個答案。
5. 正確解讀 `--trace` 的通道事件，以及 `--stats` 的 token 計數與 FIFO 最大佔用。
6. 從 E0701 死結報告建立等待圖，找出循環等待。
7. 建立能同時在原生與合作式排程器上重現的最小測試程序。

> **版本界線**：本章以 Fluxa 語言規格 v1.0（2026-11-21）與 `rueda 0.7.0` 為準。`stage` 層尚未實作；task 層的 `try_recv`、`empty`、`len` 因為會破壞排程無關性而不允許使用。本章談的是行為直譯模擬；編譯後的 `reda emu` 與 `reda gatesim` 會在第 10 章專門比較。
