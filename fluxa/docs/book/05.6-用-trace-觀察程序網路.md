# 5.6 用 `--trace` 觀察程序網路

`assert` 告訴你「規格失敗了」，`--trace` 告訴你「網路實際做了什麼」。

```sh
reda sim --trace fluxa/examples/fir4.fx
```

追蹤會記錄每個成功的通道事件，格式類似：

```text
[     1] test:tx->rx              send 64
[     2] test:tx->rx              recv 64
[     3] test:ty->ry              send 8
[     4] test:ty->ry              recv 8
```

通道名稱由建立通道時的 task 與端點變數推導，適合閱讀，但不是穩定的硬體介面名稱。重構變數後名稱可能改變，測試不應依賴它。

### 5.6.1 trace 的三種用途

**第一，確認因果關係。** 當第  $n$  個輸入應該對應第  $n$  個輸出時，可以沿著通道追蹤兩端，而不只看最後結果。

**第二，找到第一個偏離點。** 假設期望 `[8, 32, 56]`，trace 卻顯示 `[8, 31, 56]`，第一個不同值把問題縮小到「第一次或第二次計算」，而不是整個 FIR。

**第三，理解等待與背壓。** 某個 task 長時間沒有後續事件，可能是在等空 FIFO；另一個 task 已送出許多 token，可能正在等待 FIFO 空間。

### 5.6.2 不要把跨通道 trace 順序當成契約

原生排程器把 trace 寫到標準錯誤，合作式排程器則先緩衝輸出；在不同排程器或不同執行中，獨立通道的事件可能交錯。比較兩次 trace 時，應先投影到各自通道：

```text
result: 8, 32, 56, 64
status: 1, 2, 3, 4
```

再比較這兩個投影，而不是要求整份全域事件清單逐行相同。若某個跨通道順序確實是規格，設計者必須把它表達成可檢查的同步關係。

### 5.6.3 trace 不等於 waveform

傳統 RTL 模擬常用波形查看「每個時脈發生什麼」。Fluxa 行為模擬沒有預先指定硬體時脈，因此 trace 顯示的是**通道事件**，不是合成後的時脈波形。它適合驗證資料流契約；真正的狀態機與資料路徑時序要到第 7、8 章降階後才能觀察。

同樣地，一次 `send` 在行為模型中可能只花「等待時間」，不代表實際硬體只需一個時脈；行為模型也不直接保證 II、延遲或資源用量。
