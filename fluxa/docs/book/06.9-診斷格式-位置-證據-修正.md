# 6.9 診斷格式：位置、證據、修正

### 6.9.1 文字診斷怎麼讀

Fluxa v1.0 要求每則診斷至少包含：

1. **位置**：檔案與行號；
2. **證據**：值域、通道差額、資源使用量等；
3. **可行修正**：足以讓檢查重新通過的修改方向。

以 E0301 為例：

```text
file.fx:12: warning[E0301] in `task Mac`:
the value's range 0..=8589934592 does not fit i24 (range -8388608..=8388607)
    fix: declare it as i34 or convert explicitly: .sat::<i24>() / .wrap::<i24>()
```

閱讀順序應該是：

1. 先看位置：問題究竟發生在計算、落點、通道還是排程？
2. 再看代碼：它屬於值域、資源還是所有權類別？
3. 核對證據：數字彼此是否一致？
4. 比較修正方案的語意代價。
5. 修正後重新執行 `reda check`，而不是只看訊息中的建議。

### 6.9.2 JSON 診斷：讓證據可被工具消費

```sh
reda check --format json design.fx
```

`rueda/1` schema 中，每則靜態 finding 至少包含：

| 欄位 | 意義 |
| --- | --- |
| `code` | 診斷代碼，例如 `E0301` |
| `severity` | 工具層級嚴重度；目前靜態 finding 統一為 `warning` |
| `phase` | 發生階段；靜態檢查為 `check` |
| `file` | 來源檔案 |
| `line` | 來源行號 |
| `context.function` | 發生問題的函式或 task |
| `data` | 結構化證據 |
| `notes` | 證據說明或修正建議 |

E0301 的 `data` 可能像：

```json
{
  "range": "0..=510",
  "type": "u8",
  "min_type": "u9"
}
```

通道守恆的 `data` 則可能是：

```json
{
  "sent": "10",
  "received": "11"
}
```

資源問題則會列出 `resource`、`uses` 與 `capacity`。這種結構讓 CI 不必用脆弱的正規表示式解析自然語言，也能讓編輯器直接標示行號。

### 6.9.3 位置很重要，但不要只修那一行

診斷指向的是「契約被違反的位置」，不一定是「根因所在的位置」。例如 E0301 指向 `let d: u8 = c;`，但根因可能是：

- 上游 `c` 的型別太寬；
- 介面規格本來只允許較小值；
- 計算結果應先飽和；
- 函式回傳型別宣告錯了。

同樣，E0412 指向 `pipeline` 行，但根因可能是同一通道每輪讀兩次，或把通道操作放在條件分支。把 `pipeline` 刪掉雖然能讓錯誤消失，卻也刪掉產品需要的吞吐承諾。

### 6.9.4 先修根因，再談抑制診斷

工程上最差的修法是「把型別加大到不出錯」四處套用：

- 會增加加法器、乘法器與暫存器寬度；
- 可能改變外部介面；
- 可能掩蓋真正的規格錯誤；
- 可能讓後續累加器成本連帶上升。

另一個壞習慣是無條件轉成 `wrap`。回繞是一種明確產品語意，不是萬用膠帶。

正確順序是：

1. 說明來源完整值域與目標契約；
2. 判斷超界是否合法；
3. 若合法，選擇飽和、回繞或明確檢查；
4. 若不合法，修正上游型別或規格；
5. 重新做靜態檢查與行為測試；
6. 比較位寬、面積、延遲與吞吐成本。
