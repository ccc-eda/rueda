# 6.2 為什麼需要兩層防線

行為模擬證明「這一次執行走到這條路徑時，結果是否正確」；靜態檢查則嘗試在已知的所有可能值與路徑下，證明契約能否成立。兩者互補，不能互相取代。

先看一段故意留下危險分支的程式：

```fluxa
fn average8(a: u8, b: u8) -> u8 {
    if b == 0 {
        0
    } else {
        (a + b) / b
    }
}
```

若測試只傳入 `a = 10`、`b = 2`，執行期完全正常。但靜態分析看見：`a + b` 的來源值域為 `0..=510`；`b` 的值域為 `0..=255`；`else` 分支的 `b != 0` 可把除數收窄為 `1..=255`。因此，它能證明這個版本不會除以零。

反之，若刪掉 `if`，即使所有既有測試都沒有選到 `b = 0`，檢查器仍能指出：**除數的完整值域包含 0，型別契約無法排除除零。**

| 防線 | 核心問題 | 強項 | 限制 |
| --- | --- | --- | --- |
| 行為模擬 | 這條執行路徑的結果對不對？ | 看見真實 token 順序、關閉與等待 | 未覆蓋的路徑可能漏掉錯誤 |
| 靜態檢查 | 所有已知可能值下，契約能否成立？ | 能在測試前涵蓋未測分支 | 保守近似；證明不了不等於一定有錯 |
| 合成期檢查 | 排程與資源能否形成承諾的硬體？ | 看見模數排程、依賴環與埠衝突 | 只能檢查已建模的硬體子集 |

三者互補：

```text
型別與值域契約 ──→ 靜態檢查 ──→ 行為模擬 ──→ 合成 ──→ 跨層等價驗證
     證明語意安全      證明執行結果      證明硬體結構與行為
```

### 6.2.1 `reda check` 的責任

```sh
reda check design.fx
reda check --format json design.fx
```

第一種形式逐則印出 finding；第二種輸出 `rueda/1` JSON，方便編輯器、CI 或 AI agent 消費。命令會合併所有 `.fx` 檔案，檢查每個 `fn`、`comb fn`、`task` 與 `test`。沒有 finding 時回傳 0；有 finding 時回傳 1。

目前文字格式會把 finding 標成 `warning[...]`，即使代碼以 `E` 開頭。判斷流程能否繼續，應看命令是否成功以及診斷的 `code`，不要只看 `severity` 文字。

### 6.2.2 靜態檢查不是形式驗證

Fluxa v1.0 的核心是區間分析與有限次數的通道計數模型。未知值域、某些固定點運算與泛型可能無法完整分析；`assume` 尚未實作；通道計數只在模型可求解時檢查；資源檢查使用單一 bank 模型。

正確的心態是：

> 靜態檢查證明的是「在分析模型內，程式沒有違反可檢查的契約」，不是整個硬體系統的完整數學證明。

這也解釋了診斷為何不能只寫「型別錯誤」。它必須告訴工程師：**問題在哪裡、根據什麼證據、可以怎麼修。**
