# 3.4 區間算術：從值域推導結果

現在假設：



$$
e_1 : \operatorname{int}\langle a..=b\rangle,\qquad
e_2 : \operatorname{int}\langle c..=d\rangle
$$



Fluxa 對四則運算使用下列規則。

### 加法：上下界相加



$$
\operatorname{range}(e_1+e_2)
=
[a+c..=b+d]
$$



例如：

```fluxa
let a: u8 = 200;
let b: u8 = 100;
let s = a + b;       // 0..=510
```

最小實體寬度是 9 位元。若寫成 `let s: u9 = a + b;`，來源範圍完整落在 `0..=511` 內，因此是安全的無損落點。

### 減法：交叉相減



$$
\operatorname{range}(e_1-e_2)
=
[a-d..=b-c]
$$



最小值出現在「小的減大的」，最大值則是「大的減小的」。例如 `i8 - i8` 的範圍是：



$$
-128-127=-255,\qquad 127-(-128)=255
$$



因此結果需要 9 個有號位元，而不是 8 個。`u8 - u8` 的範圍也是 `-255..=255`，同樣需要 `i9`。

### 乘法：檢查四個端點組合



$$
P=\{ac,ad,bc,bd\}
$$





$$
\operatorname{range}(e_1e_2)
=
[\min P..=\max P]
$$



乘法是雙線性函數；即使區間跨過零，四個端點組合仍足以找出最小與最大值。

```fluxa
let a: i8 = -128;
let b: i8 = -128;
let p = a * b;       // -16256..=16384，最小安全型別是 i16
```

這個例子也很適合說明「乘法結果不是任選型別」：`i8 × i8` 的完整乘積需要 16 位元。若最後要送進 `i8` 通道，就必須另外指定飽和或回繞，而不能期待乘法器自動截斷。

### 左移：值域乘以二的冪

對常數移位量  $k$ ：



$$
\operatorname{range}(e\ll k)
=
[a2^k..=b2^k]
$$



`e << 1` 的右界加倍，所以左移是擴寬操作。硬體上也常可直接接到匯流排較寬的下一級，不必先截斷。

### 右移：依算術右移規則縮窄

對常數移位量  $k$ ：



$$
\operatorname{range}(e\gg k)
=
\left[
\left\lfloor\frac{a}{2^k}\right\rfloor
..=
\left\lfloor\frac{b}{2^k}\right\rfloor
\right]
$$



有號負數使用算術右移，並以零填充高側位元。例如 `i8` 的 `-128..=127` 右移一位後是 `-64..=63`。

Fluxa v1.0 的值域推導要求移位量為常數。若移位量來自執行期輸入，就無法靜態知道結果可能跨越多少位數；此時應把可達的移位範圍寫進契約，或依不同移位量分支處理。

### 除法與取模：先排除零

除法與取模要求除數的推導範圍不包含零：



$$
0\notin[c,d]
$$



因此：

```fluxa
fn bad_divide(a: u8, b: u8) -> u8 {
    a / b              // E0102：u8 的範圍包含 0
}
```

即使呼叫者「從來不傳 0」，型別也沒有表達這個保證。較好的介面是直接排除零：

```fluxa
fn divide_nonzero(a: u8, b: int<1..=255>) -> u8 {
    a / b
}
```

若除數來自一般 `u8`，可用條件分支讓檢查器收窄範圍：

```fluxa
fn safe_divide(a: u8, b: u8) -> u8 {
    if b == 0 {
        0
    } else {
        a / b
    }
}
```

在 `else` 分支中，檢查器知道 `b` 不等於零，因此不會產生 E0102。執行期仍應防禦不合法呼叫，而不能把靜態收窄當成外部世界永遠正確。

### 比較與布林結果

比較結果是 `bool`，不會因比較兩個大整數而擴成大整數。布林運算 `&&`、`||` 與 `!` 也保留布林語意；它們和位元操作 `&`、`|`、`^` 不是同一回事。

### 累加器：單次安全不等於整段安全

一般的加法規則只描述「這一次」運算能產生什麼範圍；但具有型別的累加器會在每輪結束時回到同一個落點型別。即使每一次加法看似只增加一點，累積多次後仍可能越界。

例如：

```fluxa
task Count(x: in chan<u8>) {
    carry count: u8 = 0;

    for _ in 0..300 {
        count += 1;
    }
}
```

單看 `count += 1`，很多值仍可放在 `u8`；可是從初值 `0` 累加 300 次，終值範圍是 `0..=300`，需要至少 `u9`。`reda check` 會用迴圈次數上界推導累加器的終值範圍，因而在執行前指出 `u8` 太小；行為模擬則會在真的累加到 `256` 時，於型別化落點報 E0301。

Fluxa v1.0 也能對型別化的 `let mut` 累加器做相同形式的線性分析。它的核心不是替所有迴圈做形式化證明，而是讓常見的「固定次數加法」不必等到測試跑到邊界才發現問題。若更新包含乘法、移位或其他非線性運算，檢查器不會擅自把它展開成整段等價式；此時程式仍須選擇更寬的型別，或明確使用 `.sat`、`.wrap` 等策略。

本章只預告這個分析入口。第 6 章會說明累加值域分析與診斷證據，第 8 章則會回到硬體成本，比較循序累加器、平衡加法樹與管線化對面積和延遲的影響。
