# 10.3 為何需要編譯後模擬器

## 10.3.1 直譯器不夠快

行為直譯器每次執行都要解析 AST、維護環境與檢查型別。對小型測試很方便，但對長序列、多 task 網路或大量測試向量，速度會成為瓶頸。

編譯後執行器把直線程式碼轉成較低階的狀態機與暫存器操作，減少重複解析。它讓「跑完整回歸測試」變得可行，也讓 CI 能在合理時間內執行更多案例。

## 10.3.2 編譯後執行器驗證了什麼

它驗證的不是硬體時序，而是：

- 控制流被編譯成狀態後，分支與迴圈仍正確；
- 通道操作被編譯成環形緩衝區後，token 順序仍正確；
- 暫存器與累加器的更新順序仍符合語意；
- `@reg` 的迭代提交語意沒有被編譯改變。

這些都是硬體降階之前的必經步驟。若連編譯後執行器都與直譯器不一致，那麼後面合成出的網表也不可能可靠。

## 10.3.3 WebAssembly 與外部 harness

`reda emu -o fir.wasm` 可以把 task 或網路輸出成 WebAssembly 模組。這適合：

- 在瀏覽器或 Node.js 中建立互動式測試；
- 把硬體行為接到外部軟體模型；
- 用較快的執行環境跑大量向量。

WASM 模組的介面與通道埠仍對應原始設計。它不是另一個語意，而是同一份語意的另一種執行格式。

## 10.3.4 什麼時候可以直接跳到 gatesim

如果你只有很小的測試集，或許可以直接用 `reda gatesim` 驗證網表。但這通常不是好主意，因為：

- 閘級模擬較慢，失敗時較難定位；
- 若直譯器與編譯器都不一致，先修語意比先修網表更有效；
- 分層驗證可以告訴你問題出在「編譯」還是「合成」。

建議順序是：`sim` → `emu` → `synth` → `gatesim`。每一層都通過後，再往下一層。
