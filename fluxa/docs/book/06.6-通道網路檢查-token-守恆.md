# 6.6 通道網路檢查：token 守恆

### 6.6.1 一條通道其實有兩份契約

對通道 `c`，至少要同時回答兩個問題：

1. **介面契約**：兩端的方向與元素型別是否完全相符？
2. **流量契約**：整段執行的送出 token 數與接收 token 數是否一致？

第 4 章已說明方向與型別契約。本節關注第二個問題。

若一條通道送出 10 個 token，卻只接收 9 個：

- 若差額可放在 FIFO 裡，接收端可能永遠不讀最後一個 token；
- 若差額大於 FIFO 深度，傳送端會卡在 `send`；
- 若接收端比送端多等 1 個 token，接收端會永遠卡在 `recv`。

這些都是排程無關的結構問題，不必靠碰巧的執行順序才能發現。

### 6.6.2 用線性式描述 token 數

Fluxa 的通道守恆分析把端點操作次數寫成：



$$
c+\sum_i k_iT(ch_i)
$$



其中：

-  $c$  是固定次數；
-  $T(ch_i)$  是某條通道的 token 數；
-  $k_i$  是該通道被讀寫的倍率。

例如：

```fluxa
task Gen(n: u32, out: out chan<u8>) {
    for i in 0..n {
        out.send(1);
    }
}
```

`out` 的送出次數是  $T(n)$ ，其中 `n` 若是 task 參數，執行期常數會被帶入分析；若呼叫端固定傳入 10，便得到 10。

另一個 task：

```fluxa
task Pass(x: in chan<u8>, y: out chan<u8>) {
    for v in x {
        y.send(v);
    }
}
```

`x` 接收  $T(x)$  個，`y` 也送出  $T(x)$  個。因此在完整網路中，來源、Pass 與消費者之間必須形成一致的代換。

分析器會對每條區域通道建立：



$$
sent(c)=received(c)
$$



若某個一側仍含未知 token 數，方程可能無法求解，此時不會勉強下結論。

### 6.6.3 一個刻意失敗的案例

```fluxa
task Gen(n: u32, out: out chan<u8>) {
    for i in 0..n {
        out.send(1);
    }
}

test receive_too_many {
    let (tx, rx) = chan::<u8>(depth = 2);
    spawn Gen(10, tx);

    for _ in 0..11 {
        let value = rx.recv();
    }
}
```

通道只會收到 10 個 token，測試卻要求 11 個。`reda check` 會以 E0501 報告守恆失敗，證據類似：

```text
channel `tx->rx`: 10 token(s) sent, 11 received:
the counts differ for some inputs
```

「counts differ for some inputs」很重要：檢查器不是只說「可能死結」，而是指出送收計數不相等。執行期通常會再看到接收端卡在空 FIFO；兩份證據互相補足。

### 6.6.4 剩餘 token：W0503 與 E0501 並非同一件事

假設來源送 10 個，測試只收 9 個，通道深度是 2。

差額只有 1，剛好可以留在 FIFO 中，所以系統不一定立即死結；但那 1 個 token 永遠不會被接收，是明顯的契約缺口。Fluxa 會以暫定代碼 W0503 報告：

```text
channel `tx->rx`: 10 token(s) sent, 9 received:
1 token(s) are left in the channel, never received
```

若 FIFO 深度只有 0——但目前語言不允許零深度——或差額大於容量，傳送端就會因 FIFO 滿而阻塞，後果升級為 E0501。

可用一張表區分：

| 情況 | 診斷 | 硬體後果 |
| --- | --- | --- |
| 收多於送 | E0501 | 接收端等待一個永遠不會出現的 token |
| 送多於收，差額可放進 FIFO | W0503 | 留下未取 token；端點何時關閉可能仍被阻塞 |
| 送多於收，差額超過容量 | E0501 | 傳送端卡在滿 FIFO |
| 計數無法求解 | 不報 | 需要更強的契約或人工推理 |

### 6.6.5 守恆分析的盲點

通道守恆不是完整的死結證明。以下情況可能無法檢查或不會被判定：

- 同一輪從通道再接收一次，使每輪數量不再等於  $T(rx)$ ；
- 根據資料內容決定送多少 token；
- 無界迴圈的 token 數未知；
- 呼叫關係或分支次數無法靜態化；
- `broadcast` 與複雜網路的代換關係超出目前模型。

例如：

```fluxa
for v in x {
    if v > 3 {
        y.send(v);
    }
}
```

`y` 的送出數取決於資料值，不能只用 `T(x)` 表示。檢查器可能無法建立可解方程，於是保持沉默。這不代表設計安全，只代表這個模型沒有足夠證據。

### 6.6.6 從數量不守恆回到拓樸規格

修正 E0501 時，不應只把接收次數「改成剛好能過」。先回答三個問題：

1. 哪一端是 token 的真正生產者？
2. 消費契約是一進一出，還是一進零、一進多？
3. 來源如何表示結束：關閉送端，還是額外送摘要 token？

若規格本來就要求一進一出的 FIR，則 FIR 應對每個輸入送一個結果，消費者也應接收相同數量。若規格只要求「送出大於門檻的樣本」，數量就是資料相依的；此時不應硬套固定守恆式，而應在契約中明說資料相依行為並以測試驗證。
