# 4.9 等待、排序與背壓

### 4.9.1 背壓是沿著 FIFO 向上游傳遞的

當接收端尚未呼叫 `recv()`，FIFO 會逐漸填滿；填滿後，傳送端的 `send()` 必須等待。這種「下游沒空間，上游就停住」的現象稱為**背壓（backpressure）**。

以三段鏈路為例：

```text
Source --send--> FIR FIFO --send--> Consumer FIFO
```

若 Consumer 不讀取資料：

1. Consumer FIFO 填滿；
2. FIR 的輸出 `send()` 阻塞；
3. FIR 無法繼續處理下一筆輸入；
4. FIR 的輸入 FIFO 填滿；
5. Source 的 `send()` 阻塞。

因此背壓不是只停留在相鄰的兩個 task，而會沿著資料流鏈一路傳回來源。這個機制防止了無限快生產資料所帶來的無限記憶體需求，也讓硬體只需配置固定深度的 FIFO。

### 4.9.2 FIFO 深度改變等待時間，不改變 token 序列

假設兩個程式的產銷速率不同：

```text
Producer: 每 3 個時間單位送 1 個 token
Consumer: 每 1 個時間單位取 1 個 token
```

短期內 Consumer 較快，長期則 Producer 較慢。FIFO 深度 1 與深度 8 的差別主要是：

- 深度 1：Producer 幾乎立即被 Consumer 的節奏反壓。
- 深度 8：Producer 可以先累積最多 8 個 token，之後仍須等待。

在邏輯上，兩者的輸出序列都必須相同。深度只改變「誰會在什麼時候阻塞」，不應改變資料值、順序或數量。這也是 KPN 確定性的重要結果。

更精確地說，FIFO 深度改變的是等待關係與可達的暫存狀態；在沒有死結的網路中，它不應改變任何通道的邏輯 token 序列。

### 4.9.3 深度不是越大越好

較深的 FIFO 有三個代價：

1. **面積**：每個 token 槽位都要保存資料，連同控制位元。
2. **延遲**：資料可能要在 FIFO 中停留較久。
3. **時序與功耗**：大型 FIFO 可能需要 block RAM 或更複雜的控制。

較淺的 FIFO 也可能造成問題：若測試主體一口氣送入大量資料，輸出端又沒有足夠空間，就可能形成測試主體與元件互相等待。因而測試中的通道深度不是可有可無的常數；它必須足以讓測試 harness 能完成自己的工作。

例如，`fluxa/examples/fir.fx` 特意讓輸入 FIFO 深度為 4、輸出 FIFO 深度為 32。原因不是 FIR 需要記住 32 個樣本，而是測試一次送入整段脈衝響應；若輸出空間不足，測試主體會在送輸入時被阻塞，FIR 又在等待測試主體取走輸出，形成死結。

### 4.9.4 排序由 FIFO 保證，不由等待時間保證

假設 Producer 依序送出 `A`、`B`、`C`，Consumer 無論多快或多慢，都只能依序收到 `A`、`B`、`C`。阻塞可能改變每個 token 的抵達時間，卻不能顛倒 token。

這點在多通道網路中尤其重要：不要用「哪個 task 先被排程器喚醒」來猜資料順序。應直接根據通道契約寫出期望序列。
