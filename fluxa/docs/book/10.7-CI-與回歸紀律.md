# 10.7 CI 與回歸紀律

## 10.7.1 把驗證變成閘門

驗證只有在每次變更都被執行時才有價值。最小的 CI 閘門可以是一條命令：

```sh
./ci.sh
```

`ci.sh` 依序執行：

```sh
set -e
cargo build --release -p rueda
reda check fluxa/examples/fir4.fx
reda sim fluxa/examples/fir4.fx
reda emu --top Fir fluxa/examples/fir4.fx
reda synth --top Fir fluxa/examples/fir4.fx
reda gatesim opt --top Fir fluxa/examples/fir4.fx
```

若任何一步失敗，CI 就阻擋合併。這比「有空再跑」可靠得多。

## 10.7.2 分層排程

不是每個提交都需要跑最慢的閘級模擬。可以分成：

- **快速層**：`check` + `sim`，每次提交。
- **中速層**：`emu` + `synth`，每次提交或每日。
- **完整層**：目標 FPGA／ASIC 閘級模擬，合併前或發版前。

這種分層讓回饋速度與驗證強度可以同時兼顧。

## 10.7.3 保存失敗案例

每次失敗都應該留下：

- 觸發失敗的輸入與 seed；
- 使用的命令；
- 工具版本；
- 預期與實際輸出；
- 最小重現檔案。

失敗案例是最有價值的回歸測試。修好之後，把它加入矩陣，確保同樣的問題不會再次出現。

## 10.7.4 不要讓 CI 變成形式

若 CI 只看「有沒有 exit 0」，很容易出現：

- 測試被註解掉；
- 錯誤案例被當成「預期失敗」而忽略；
- 閘級模擬沒有真的執行；
- 報告沒有被比較。

因此，CI 應該輸出可讀的摘要，並在失敗時指出「哪一層、哪個案例、哪個欄位不同」。

## 10.7.5 可重現性

一個可重現的驗證流程應該讓別人能在自己的機器上得到相同結果：

- 固定工具版本；
- 固定測試輸入與 seed；
- 固定輸出格式；
- 不使用未記錄的外部服務。

這也是本書反覆強調「命令、證據、版本」的原因。沒有可重現性，CI 通過與否都只是當下的偶然。
