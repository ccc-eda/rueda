# 6.4 E0301：讓窄化在落點現形

### 6.4.1 從一個窄化案例開始

現在回到第 3 章的範例：

```fluxa
test implicit_narrowing {
    let a: u8 = 200;
    let b: u8 = 100;
    let c = a + b;
    let d: u8 = c;
}
```

`a + b` 的完整來源值域是  $0..=510$ ，目標 `u8` 只能容納  $0..=255$ 。因此 `reda check` 會報告 E0301，並附上最小容納型別：

```text
err_narrow.fx:6: warning[E0301] in `test implicit_narrowing`:
the value's range 0..=510 does not fit u8 (range 0..=255)
    fix: declare it as u9 or convert explicitly:
         .sat::<u8>() / .wrap::<u8>()
```

這則診斷有三層資訊：

1. **位置**：第 6 行，也就是窄化真正發生的落點。
2. **證據**：來源是 `0..=510`，目標是 `0..=255`。
3. **修正方向**：至少要改成 `u9`，或者明確決定如何把 `0..=510` 壓進 `u8`。

最小容納型別是 `u9`，因為  $2^9-1=511\ge510$ 。若來源區間包含負數，工具會改用有號型別；例如 `[-300,300]` 至少需要 `i10`。

### 6.4.2 E0301 不表示「每次執行都會壞掉」

若測試剛好永遠傳入 `a = 0`、`b = 0`，那麼 `c = 0`，窄化在該路徑上不會出錯。E0301 關心的不是「這個測試是否已失敗」，而是：

> 介面型別允許某些值，而這些值無法在沒有明確轉換語意的前提下被目標型別容納。

因此，E0301 的修正不能只是讓某個測試變綠。你必須先回答規格問題：超出範圍時應回繞、飽和，還是根本不允許發生？

若外部介面固定為 `u8`，可以選擇：

```fluxa
let d = c.sat::<u8>();   // 0..=255，超過 255 就停在 255
let e = c.wrap::<u8>();  // 模 256 的位元回繞
```

前者改變數值語意，後者改變代碼點語意。兩者都可能比擴寬介面更符合產品規格，也可能都不符合。工具只能證明範圍不相容，不能替你決定產品語意。

### 6.4.3 分支收窄：條件也是證明

區間分析會利用控制條件收窄值域：

```fluxa
fn divide_guarded(a: u8, b: u8) -> u8 {
    if b == 0 {
        0
    } else {
        a / b
    }
}
```

在 `else` 分支，分析器知道 `b != 0`。由於 `b : u8` 的完整值域是 `0..=255`，扣除零後可收窄為 `1..=255`。除數不再包含零，E0102 不會出現。

同樣地：

```fluxa
if index < 6 {
    table[index]
}
```

若 `index : u4`，`index < 6` 會把索引範圍收窄為 `0..=5`，因此可以安全地索引長度 6 的陣列。若沒有這個 guard，`u4` 的 `0..=15` 會超出陣列，檢查器會報告 E0703。

這種推論只依賴控制流，不需要尚未實作的 `assume`。但若不變量藏在自訂資料結構、難以分析的條件或跨 task 副作用中，分析可能無法證明安全。工程師可以嘗試把不變量轉成更明確的局部型別與 guard，而不是忽略 finding。

### 6.4.4 E0102：除零也是值域問題

E0102 的意思是「除數的值域包含 0」：

```fluxa
fn divide(a: u8, b: u8) -> u8 {
    a / b
}
```

`b` 的值域是 `0..=255`，因此 `0` 是合法輸入。首選修法通常不是把 `b` 偷偷改成非零型別，而是先在契約上說清楚零代表什麼：

```fluxa
fn divide(a: u8, b: u8) -> u8 {
    if b == 0 {
        0
    } else {
        a / b
    }
}
```

如果「零除數是系統錯誤」，可以加入 `assert`。但要分清楚：`assert` 是模擬期契約，不是自動產生的硬體錯誤埠。若產品需要即時回報零除數，必須另加 `error` 輸出、狀態位或握手指令。

診斷證據會直接指出根源：

```text
the divisor's range 0..=255 includes 0
    fix: narrow the divisor's type so it excludes 0, or test it first
         (`if d != 0`)
```

### 6.4.5 保守分析的正確解讀

Fluxa 的區間分析採保守近似。對某些無法建模的值，它會保留「上界未知」，而不是報出假精確的數字。

假設分析得到 `source range: 0..=255`、`target range: 0..=255`，這表示「在可分析的整數路徑中，來源可放入目標」。它不表示每一條執行路徑都已被形式驗證，也不表示外部世界一定遵守介面契約，更不表示時序、面積或功耗符合目標。

靜態檢查是語意安全的第一道閘門，不是交付晶片的唯一條件。
