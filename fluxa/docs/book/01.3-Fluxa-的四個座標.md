# 1.3 Fluxa 的四個座標

接下來用四個詞建立 Fluxa 的共同語言。它們不是四個彼此獨立的語法功能，而是理解任何 Fluxa 設計時應該同時問的四個問題。

### 1.3.1 值域：每個值到底能被表示到什麼範圍

在 Fluxa 中，型別不只是程式碼裡的名字；它還承載值的合法範圍。以 8 位元有號整數為例，合法值域是  $[-128,127]$ ；以 8 位元無號整數為例，合法值域是  $[0,255]$ 。更一般地，範圍型整數可以寫成封閉區間 `int<lo..=hi>` 的概念形式：每個值都必須落在允許範圍內。

這個約束看似嚴格，卻直接解決硬體最常見的錯誤之一：軟體中的 `int` 常常讓人忘記乘法、累加或窄化會不會超出實際位元。Fluxa 要讓設計者先回答：

> 這個訊號的最小與最大合法值是多少？如果它超出型別允許範圍，應該報錯、回繞，還是飽和？

本章先用「值域」這個概念描述 FIR 的介面，不急著計算 FIR 的確切位寬；第 3 章會把乘法、累加與定點數的推導完整展開。

### 1.3.2 Task：哪一段行為是獨立程序

`task` 是 Fluxa 中可以參與程序網路的一段行為程序。它不是作業系統執行緒，也不必然對應一個 CPU core。task 可以在自己的控制流程中等待、計算與傳送 token，並且透過通道與其他 task 溝通。

把 FIR 拆成一個「取樣任務」、一個「濾波任務」與一個「輸出任務」，有幾個好處：

- 每個 task 的責任單一，容易閱讀與測試；
- 資料流邊界變得明確，知道誰擁有誰；
- 排程器可以依通道的可用性安排啟動，而不是猜測陣列與迴圈；
- 未來可以把某個 task 映射到獨立硬體區塊，也可以讓它與別的 task 共用排程資源。

「task 是程序」不代表「task 必須同時執行」。Kahn 程序網路的重點是每個程序只依賴自己擁有的狀態與通道，不依賴另一個程序何時剛好更新某個共享變數。

### 1.3.3 Channel：程序之間以什麼 token 契約通訊

通道不是把任意物件丟進共享記憶體的捷徑。它是帶有端點、元素型別、容量與生命週期的資料流邊界。通道中的一個 `token` 可以代表一個樣本、一個控制訊息或一個已完成的工作結果。

一個通道契約至少要回答：

1. 誰是唯一或線性的擁有者，誰可以傳送，誰可以接收？
2. token 的元素型別與值域是什麼？
3. token 的順序與數量語意是什麼？
4. 通道何時關閉，關閉後尚未取出的 token 如何處理？
5. 容量多大；接收端暫時無法接收時，傳送端如何施加背壓？
6. 發生型別或狀態錯誤時，程序應該阻塞、回報，還是進入可診斷的失敗狀態？

在硬體中，通道通常對應 FIFO、握手暫存器或某種可推導的緩衝結構。容量有限不是缺陷，而是誠實地表達「晶片資源不是無限的」。

### 1.3.4 排程：一次迭代何時啟動，哪些操作形成時序邊界

排程回答的是時間問題：某個 task 何時可以開始處理下一個 token？它必須等待前一個結果嗎？哪些運算可以平行？資料何時跨過暫存器，形成新的時序邊界？

在 Fluxa 中，排程描述不應只是註解。它會影響：

- 每拍可以接受幾個輸入；
- 結果的延遲；
- 需要多少乘法器、加法器與暫存器；
- 背壓時資料如何停在正確的位置；
- 行為模擬是否能預測實際的 token 對應關係。

第 4 章會專門介紹 Kahn 通道的程序網路，第 7、8 章則把排程降階成 FSM、資料路徑與管線。本章先掌握一個原則：**來源程式的執行順序不等於硬體的啟動順序**。只要契約說清楚「哪個輸入對應哪個輸出」，兩者就不必相同。

| 問題 | Fluxa 的表達 | 它能幫我們看見什麼 |
| --- | --- | --- |
| 這個值能有多大？ | 範圍型別與值域 | 位寬、溢位與窄化風險 |
| 哪段行為是程序？ | `task` | 責任、狀態與程序邊界 |
| 程序如何交換資料？ | 通道與 token | 順序、關閉、背壓與所有權 |
| 什麼時候可以啟動？ | 排程與硬體排程描述 | 吞吐、延遲與時序邊界 |
