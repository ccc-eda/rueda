# 5.5 測試是硬體規格的一部分

硬體測試至少要回答四個問題：

1. **值**：每個 token 的內容是否正確？
2. **順序**：token 是否保持契約要求的次序？
3. **數量**：是否少送、多送或重複送？
4. **生命週期**：何時關閉，關閉前是否已把資料排空？

只檢查最後一個值，就像只檢查串列最後一個 frame，卻不知道中間是否掉資料。

### 5.5.1 一個合格 harness 的形狀

以 FIR 為例，測試通常包含四個部分：

```fluxa
test fir4_step {
    // 1. 建立外部通道
    let (tx, rx) = chan::<i8>(depth = 8);
    let (ty, ry) = chan::<i8>(depth = 8);

    // 2. 啟動待驗元件
    spawn Fir4(rx, ty);

    // 3. 注入已知輸入，並宣告輸入結束
    for _ in 0..6 {
        tx.send(64);
    }
    tx.close();

    // 4. 依序驗證輸出
    let want = [8, 32, 56, 64, 64, 64];
    for k in 0..6 {
        assert ry.recv() == want[k];
    }
}
```

這段 harness 同時扮演來源、觀察者與測試環境。`tx.close()` 不是清理工作，而是 FIR 契約的一部分：來源必須宣告不會再送 token，元件才能知道資料流何時結束。

### 5.5.2 `assert` 是立即式判定

Fluxa 的 `assert` 檢查當下布林條件：

```fluxa
assert condition;
assert condition, "message";
```

若條件為假，該測試立即失敗。比較型斷言失敗時，模擬器會附上左右值：

```text
assertion failed: ry.recv() == 8
      left:  7
      right: 8
```

加入訊息可以指出語意，例如：

```fluxa
assert ry.recv() == 8, "max-input output[0]";
```

目前沒有 `expect`／`catch` 形式的例外捕捉，也沒有能直接表達「某事件終將發生」的時序斷言。要驗證事件最終抵達，通常用阻塞式 `recv` 或 `for v in rx` 等待，再以計數與關閉行為判定。

`assert` 也可以放在 task 內。若子 task 的斷言失敗，模擬器會把錯誤歸因到該 task 與來源行號，而不是只說整個測試失敗。元件內部斷言適合保護局部不變量；測試 harness 適合驗證端到端契約。兩者角色不同，應避免把所有內容都塞進元件。

### 5.5.3 正常、邊界與錯誤案例

一份可用的測試矩陣通常包含：

| 類別 | FIR 例子 | 要證明的內容 |
| --- | --- | --- |
| 正常 | 固定輸入產生已知序列 | 演算法與順序正確 |
| 零值 | 全零輸入 | 初始歷史與乘法正確 |
| 上邊界 | `i8` 最大值 127 | 有效值域不被誤拒 |
| 下邊界 | `i8` 最小值 −128 | 負值、捨入與飽和正確 |
| 飽和 | 刻意讓結果超出輸出範圍 | 明確的 `sat` 策略生效 |
| 生命週期 | 關閉來源後等待輸出關閉 | end-of-stream 正確 |
| 數量 | 4 個輸入必須得到 4 個輸出 | token 守恆 |

執行期錯誤案例通常要由外部測試程序確認非零退出碼，而不是在 Fluxa 內部用另一個 `assert` 捕捉。靜態錯誤則交給下一章的 `reda check`；兩者都是測試矩陣的一部分，但證據來源不同。

### 5.5.4 測試向量與參考模型

測試 oracle 有兩種常見形式：

- **明確測試向量**：直接列出期望序列 `[8, 32, 56, 64]`，最容易審核，也最不容易和實作犯同一個錯。
- **獨立參考模型**：用另一種較簡單的語言或演算法產生期望值，適合大量案例，但要小心「同構錯誤」。

若參考模型只是把 `Fir4` 的程式碼逐行抄一份，兩者可能一起犯同樣的係數順序或歷史更新錯誤。好的 oracle 應用規格中最容易人工核對的形式：已知輸入、已知輸出、已知 token 數量。
