# 03 共通基礎建設：host service、決定性時間與語言不變量

> 狀態：提案。既有事實以「**既有**」標示，尚未實作的想法以「**提案**」標示。

## 0. 為什麼這份文件排在最前面

[01 推廣策略](01-推廣策略.md) 與 [02 相鄰領域擴張](02-相鄰領域擴張.md) 的所有路徑都會先卡在同一個地方：

- 嵌入式要跟真實感測器講話；
- 串流要從相機或檔案拿資料；
- 機器人要接感測器與執行器；
- agent 要呼叫工具與模型；
- 教學要能執行有 I/O 的範例；
- 形式驗證要能產生反例。

今天 Fluxa 的 task 沒有 I/O、沒有時間。所以這份文件描述兩塊必須先蓋的磚，以及一條絕對不能越過的線。

---

## 1. 磚一：host service（有型別的能力端點）

### 1.1 設計原則

**提案**：把一切與語言外部世界的互動，定義成**有型別的服務**，以通道端點交給 task。

```text
service fs_read(path: chan<u8> in, out: chan<u8> out)   // 型別化能力
service llm(prompt: chan<u8> in, out: chan<u8> out)      // 可 record/replay
```

**關鍵性質**：

| 性質 | 意義 |
| --- | --- |
| 能力即型別 | task 拿到的不是 root 權限，而是一條有型別的通道端點 |
| 服務即程序 | 服務端點由外部實作（OS、瀏覽器、sandbox、模型供應商）提供 |
| 可插拔 | 同一個 Fluxa 程式，可以在不同 host 上跑：模擬器、瀏覽器、MCU、容器 |
| 可記錄 | 服務的輸入輸出可以被記錄下來，成為可重放的證據 |

### 1.2 為什麼這是 capability security 的形狀

Rust 的 ownership 保證「誰擁有資源」；Fluxa 的線性端點保證「誰能讀寫這條通道」。兩者結合，得到的模型是：

> 一個 task 的能力，完全由它被交給的端點決定；它無法存取沒有拿到的東西，因為它根本沒有那條端點。

對 agent 執行環境而言，這正是「用 sandbox 跑不可信程式」所需要的最小語言基礎，而且比「把整個語言塞進 Wasm 再燒 fuel」更貼近問題本身——因為 agent 的瓶頸不是算力，是**副作用與不可重現**。

### 1.3 語法雛形

**提案**（細節待定）：

```rust
// 服務宣告：型別即契約
service fs_read(req: chan<FsRequest> in, resp: chan<FsResponse> out);

// 使用：端點用線性所有權傳入
let (req, resp) = chan::<FsRequest>(depth = 4);
spawn fs_read(req, resp);
```

要點：

- 服務端點的建立與 task 的 `spawn` 同一套所有權規則，不引入第二套語意。
- 服務宣告可以出現在 host 端（由外部實作），也可以在語言端（提供預設實作）。
- **硬體子集不包含服務**：`service` 在合成時必須明確報錯（像 `print` 一樣被丟棄，或更好：直接拒絕），避免出現「模擬有、硬體沒有」的隱性落差。

### 1.4 record / replay

**提案**：所有 host service 的輸入輸出可被記錄成一份「情景檔」（scenario），重播時不再真的呼叫外部世界。

這讓三件事成立：

1. **可重現**：同一份情景 + 同一份程式 → 位元級相同的結果。
2. **可審核**：情景檔就是證據，可以跟著程式進版本控制。
3. **可離線**：CI、bug 回報、論文複現都不需要真的連到網路或模型。

技術上需要決定的是：情景檔放在哪裡（檔案？git submodule？）、格式（JSON 事件流）、以及二進位 payload 的編碼。建議第一版用 JSON 事件流 + base64 payload，工具自己提供 dump／replay 子命令。

### 1.5 與既有工具鏈的關係

`agge` 已經是一個 agent 執行環境（有工具標籤協定、修補機制、429 退避）。**它就是 host service 層的第一個客戶**：把 `agge` 的 graph runtime 用 Fluxa 重寫（[02](02-相鄰領域擴張.md) §6），就能同時驗證「host service 設計是否夠用」與「Fluxa 是否真的適合做 agent 執行環境」。

## 2. 磚二：決定性時間

### 2.1 現況

**既有**：Fluxa 沒有時間概念。模擬器的 task 是執行緒／合作式 coroutine，沒有 tick、沒有 timeout、沒有 deadline；合成時的 `clk` 是後端產生的，不是語言的一部分。

**問題**：對嵌入式、串流、機器人、agent 而言，「何時發生」是語意的一部分。沒有時間，就只能寫「跑到結束為止」的程式。

### 2.2 設計原則

**提案**：時間由外部注入，且必須可重現。

```text
service tick(rate_hz: u32)          // 由 host 注入的時鐘源
```

語言端提供兩種時間相關的組合子，且**兩者都保持確定性**：

| 組合子 | 語意 | 確定性保證 |
| --- | --- | --- |
| `recv` | 阻塞直到有 token | 與排程無關（既有） |
| `recv_or(tick, default)` | 本 tick 內無 token 則取預設值 | 需要明確定義 tick 邊界 |

**重點**：這不是 `select` 的非決定性版本。`select` 在多個通道同時可用時會隨機選；Fluxa 的版本必須定義明確的優先順序（例如固定通道序號），否則就違反了 §7.7 的確定性。

### 2.3 為什麼不用「時間戳」

另一種做法是給每個事件加上時間戳，讓程式自己比較。但那會把時間判斷推給程式，產生「同一個 tick 內兩件事先後」的歧義。**由外部注入 tick、由語言決定邊界**比較符合既有排程器結構（task 每次被喚醒時看到一個明確的時間點）。

### 2.4 對硬體的影響

時間模型主要服務 host 側。硬體側對應的是 `clk` 與 `rst`（頂層埠），以及 §6.4 的 `valid/ready/close` 握手。兩者的對應關係需要寫清楚：

- tick 的軟體抽象 ↔ 硬體的握手事件；
- 硬體的 `clk` 頻率 ↔ tick 頻率（可由 `--param` 固定）。

**注意**：這條對應不必一對一。若要讓 host 端的 tick 與硬體的時脈嚴格同步，就是 cycle-accurate 的 `stage` 層（規格 §14 尚未實作），屬於長期工作。

## 4. 不可稀釋的語言不變量（底線）

### 4.1 誘惑

為了通用，很自然会想加：GC、例外、動態 dispatch、浮點、runtime spawn 數量、反射、全域可變狀態。每一項都會讓語言「更通用」。

### 4.2 為什麼不能直接加

Fluxa 的全部價值來自「受限」：

| 不變量 | 失去它會怎樣 |
| --- | --- |
| 整數是封閉值域 | 位寬不再是型別的一部分 → 退化成 C 的 `int` |
| task 層禁止 `try_recv`／`empty`／`len` | 行為依賴排程 → 閘級模擬與模擬器可能不一致 |
| 線性端點 | 通道可能有多個消費者 → token 守恆不再是命題 |
| 遞迴不支援、spawn 數量靜態 | 硬體拓樸無法靜態決定 |
| 浮點在硬體不支援 | 位寬與資源模型失效 |

**如果直接加這些，Fluxa 會變成「C/C++ + 合成子集」**，也就是 HLS 語言最被詬病的樣子：語言看起來很自由，但「哪些部分能合成」要另外查文件。

### 4.3 正確的做法：分層，但讓分層可機械判定

**提案**：

1. **硬體子集保持可機械判定**。檢查器能明確回答「這個程式可不可以合成」，而不是靠文件說明。
2. **simulation-only 擴充要顯式標記**，類似 Rust 的 `unsafe`／UnsafeCell：使用時需要明確的封裝或簽名，診斷會提醒「此處不可合成」。
3. **通用需求優先用 service 層解決**。真的需要動態行為時（例如 agent 決定要開幾個 worker），用「固定數量的服務 + task 內的動態迴圈」表達，而不是放寬 spawn 規則。
4. **浮點**：模擬器已有 `f64`；硬體維持不支援。若要硬體浮點，是一個獨立且長期的決策，不要順手加。
5. **每次擴充都要回答**：這個功能是否讓「可合成性」變得不可判定？如果是，它不該進核心。

### 4.4 一條自我檢查的問題

任何新功能提案，都先用這三個問題篩：

1. 它會讓位寬推導失效嗎？
2. 它會讓行為依賴排程嗎？
3. 它會讓拓樸無法靜態決定嗎？

三個答案都是「不會」的功能，幾乎都可以安全加入；三個之中有一個是「會」，就要小心；兩個以上是「會」，它屬於 host 層，不屬於語言核心。

## 5. 實作順序建議

| 步驟 | 內容 | 驗收 |
| --- | --- | --- |
| S1 | `service` 宣告與端點所有權的語法與型別檢查；host 提供一個 `print`／`tick` 服務 | 一個 Fluxa 程式能與 host 對談 |
| S2 | 情景檔 record／replay；`reda` 的 dump／replay 子命令 | 同一情景兩次執行結果位元級相同 |
| S3 | `tick` 與決定性 timeout 的語意定義與實作 | 以 tick 驅動的範例可重現 |
| S4 | 把 `agge` graph runtime 用 Fluxa 重寫（dogfooding） | graph 執行可重播、留下 token 紀錄 |
| S5 | 把 S1–S3 的能力寫進 spec（新增章節）與 `../book/` | 文件與實作同步 |

**注意**：S1–S3 全部屬於 simulation／host 側，不應影響硬體子集；S4 是驗證手段；S5 是把新的語意（service、tick）正式化——這一步要更新 `../spec/Fluxa語言規格v1.0.md`，並考慮版本號（v1.1）。
