# 01 推廣策略：讓 IC 設計領域的人用 Fluxa

> 狀態：提案。既有事實以「**既有**」標示，尚未實作的想法以「**提案**」標示。

## 0. 前提判斷

**語言品質不是能不能推廣的決定因素，「在哪個環節被需要」才是。**

IC 設計師不會為了語言而換掉簽核流程（Synopsys/Cadence 的 signoff、DV 的 regression、DFT/APR 的流程）。所以推廣要從「插進既有流程」開始，而不是「取代既有流程」。

Fluxa 現在最容易被忽略的風險正是這個：它的抽象與價值都長在「寫硬體」上，而「寫硬體」在既有流程中只佔工作流的一小段。**若不能讓設計師在不動既有流程的前提下用到 Fluxa，所有推廣都會停在興趣階段。**

## 1. 選一個灘頭，不要全面推廣

**提案**：以下三個領域的「價值 / 導入成本」比最好，建議以它們為主線，其餘（傳統控制邏輯 RTL、類比、布局）不主動推廣。

### 1.1 主打 A：驗證（最快見效）

**為什麼**：Fluxa 的 `chan` + 確定性 + 三層等價 + `--format json`，對 DFV／驗證工程師是「測試台終於不會有隱性握手 bug」。驗證工程師天天在寫 testbench，而 testbench 正是握手協定最容易出錯、卻最缺乏型別保護的地方。

**現成的東西**：

- `reda sim` / `reda gatesim` 跑同一組測試（`../spec/synthesis-plan.md` §2）；
- 診斷一律三段式：位置、證據、可行修正（規格 §13.2）；
- `reda --format json` 讓輸出可被腳本與 agent 消費。

**要補的**：把測試台語言這條路單獨包裝（見 [03](03-共通基礎建設.md) 的 host service），以及與既有 DUT 共模擬的可行性評估（目前 `fluxa/` 側沒有 cocotb/Verilator 共模擬，只有 `veryl/synth` 的 `cosim.py` 技術可借用）。

**聽眾**：DVCon、DV 社群、CI 與 regression 團隊。

### 1.2 主打 B：AI 產生的硬體（最有話題）

**既有**：`../spec/ai-bench.md` 是目前少見的、可重現的「LLM 寫硬體」實驗：同一個便宜模型、同一份規格、同一套回饋工具，Fluxa 5/5 完成、Veryl 2/5；程式碼少 2.2–6.8 倍；兩者都完成的硬體面積與頻率同一個量級。

**為什麼有價值**：這是天然的新聞稿素材，而且回答的是所有 EDA 從業者的共同焦慮（2026 年最熱的話題之一）。**但它的價值完全來自可重現性**——一旦 nightly 榜單變紅，敘事就沒了。

**要補的**：多模型、多輪次的公開排行榜（§3.1）。

### 1.3 主打 C：參數化硬體生成器（最有說服力）

**既有**：`std::SystolicMatmul::<N, AW, CW>` 與 `std::Window3x3::<W, H, PW>`（`../spec/std.md`）；實驗中 `mm4` 從模型手寫的 319 行、37,233 LC，變成 33 行、18,008 LC（`../spec/ai-bench.md` §6.6）。

**為什麼有說服力**：設計師只為**面積、頻率、工時**付錢。語言優雅不會讓人換流程，但「同一個 block 的接線與 sizing 交給標準庫」會。這個故事不需要解釋語義，只出示三個數字。

**要補的**：把 block 庫擴到一個可用的規模（conv、matrix、filter bank、DMA descriptor 之類），每個都附面積／頻率／資源表。

### 1.4 不要主打

- 傳統控制邏輯、I/O 密集、狀態機密集的 RTL：Fluxa 的抽象優勢最小，且既有工具（Verilog + 商用 IP）最強。
- 類比、混合訊號、DFT、APR：完全在射程外。
- 「取代 Verilog/SystemVerilog」：這是十年尺度的命題，而且沒有必要（見 §2.1）。

## 2. 把導入摩擦降到最低

### 2.1 P0：「不取代流程」的出口——可讀的 RTL 輸出

**提案**：把 Fluxa 當成**前端生成器**，輸出可讀的 SystemVerilog／Verilog RTL，下游直接餵既有的合成與簽核流程。

**現狀**：`reda synth --verilog OUT.v` 只輸出結構化閘級網表（`../spec/synthesis-plan.md` §1 的匯流點設計），對接既有流程不夠；可讀 RTL 輸出在規劃裡被列為「需要先決定的事」第 3 點。

**為什麼這是分水嶺**：Chisel／FIRRTL 之所以能被業界接受，正是因為它們輸出 Verilog，並不要求你改 signoff。Fluxa 若能輸出可讀 SVRTL，設計師的心智負擔會從「換語言 + 換流程」降到「換前端」。

**成功判準**：一個第三方團隊用 Fluxa 產生 RTL，餵進既有的 VCS + Verdi / Spyglass 流程並通過。

### 2.2 P0：與既有 DUT 共模擬

**提案**：Fluxa 測試台 + 既有 Verilog DUT（cocotb 或 Verilator），可以在不改動既有 regression 的前提下使用。

**可借用的技術**：`veryl/synth/fpga/cosim.py` 把繞好的位元流用 `icebox_vlog` 轉回 Verilog，與映射後的網表逐 cycle 比對輸出；這個「把產物轉回 Verilog 再對拍」的思路可泛化到 Fluxa 的 RTL 輸出（§2.1）與 DUT 共模擬。

**成功判準**：一個使用既有 RTL IP 的團隊，用 Fluxa 寫 testbench 並接進他們既有的 CI。

### 2.3 P1：編輯器外掛（LSP）

**提案**：把診斷做成 LSP 的 `codeAction`。

**為什麼特別值得做**：Fluxa 的診斷已經是「位置 + 證據 + 可行修正」三段式（規格 §13.2），這幾乎就是 `codeAction` 的資料結構。「工具告訴你怎麼改，按一下就改好」是把診斷品質轉成生產力的唯一途徑。

**現狀**：只有瀏覽器內的 VS Code 風格 IDE（`web/PLAN.md` M11/M16），沒有真正的 LSP 或桌面外掛。

**附帶效益**：hover 顯示「這個值的範圍是什麼、位寬幾、為什麼是這個型別」，等於把位寬推理變成教學。

### 2.4 P1：10 分鐘上手

**提案**：一個指令產生第一個位元流（hello FIFO），附一張截圖與一段 90 秒錄影。

```sh
cargo install rueda
reda init my-first-design
reda sim hello.fx
reda fpga --top Hello --pcf pins.pcf --bin hello.bin hello.fx
```

配套：GitHub Action、Docker image、prebuilt binary（CI 每次產出）。

### 2.5 對照表頁面

**提案**：一頁式比較矩陣（Fluxa vs Verilog/SV vs Vitis HLS vs Chisel vs SpinalHDL vs Veryl），維度固定：位寬推導、握手協定、確定性、跨層驗證、產生 RTL、後端、學習曲線。

**注意**：這頁的每個格都必須能指到 repo 內的事實或可重現的實驗，不能靠印象填。

## 3. 把證據做成聲譽資產

### 3.1 公開排行榜（AI 實驗）

**提案**：把 `fluxa/bench/` 做成 nightly CI，跑多模型 × 多輪，公開輸出成功率、耗時、程式碼行數、LC/LUT4/BRAM、Fmax。

**理由**：硬體領域只認可重現的表格。單次執行的 5/5 vs 2/5 是 anecdote；跨模型、跨輪次的分布才是證據。

**現成的可重現性**：`../spec/ai-bench.md` §7 已列出完整重現命令。

### 3.2 與商用 HLS 的 apples-to-apples

**提案**：拿同一份規格（例如 FIR、conv3x3），同時交給 Vitis HLS 與 Fluxa，比較面積、頻率、驗證工時、程式碼行數。

**理由**：這張表比任何語言特性清單都有說服力，而且直接打「IC 設計師最熟悉的替代品」。

**注意**：商用工具的授權與版本要在文中寫清楚，比較條件要能被第三方重現。

### 3.3 真實 tape-out

**提案**：用 Fluxa 寫一個 block 進 SKY130 shuttle。

**既有**：16 階 FIR 已能產出 SKY130 GDS（38 MHz、DRC 0、LVS 相符，見 `../spec/synthesis-plan.md` F6 進度）。只差送片與回片驗證。

**理由**：「Fluxa 寫的東西真的進過晶片」是終極信任憑證；這件事沒有捷徑，但它的說服力也沒有替代品。

### 3.4 開源 IP 庫

**提案**：讓第三方用 Fluxa 寫的 block 被別人使用（一個 RISC-V 核心、一個顯示控制器、一個 DMA）。

**理由**：IP 被採用 = 語言被採用。這比任何 benchmark 都更接近「社群形成」。

## 6. 不要做的事

1. **不要想著全面取代 Verilog/SystemVerilog。** 那是十年尺度，而且沒有必要（§2.1 的路徑就夠了）。
2. **不要用「語言更優雅」當訴求。** IC 設計師為面積、頻率、工時、可驗證性付錢；美學是文青議題。
3. **不要在 token 額度或模型不穩定時做宣傳。** `ai-bench` 的可重現性就是它的全部價值，公開榜單必須每天綠燈，否則傷害大於幫助。
4. **不要把 book、paper、spec 當行銷素材而不同步維護。** 三者現在是同一份語意的三種投影，版本一旦漂移，社群的第一個印象就是「不嚴謹」。
5. **不要為了「看起來通用」而擴充語言。** 見 [03](03-共通基礎建設.md) §4 的兩層陷阱。

## 7. 衡量整體進展的指標

| 指標 | 為什麼重要 |
| --- | --- |
| 外部貢獻者數（非作者本人） | 語言被當成社群資產的訊號 |
| 非硬體領域的 Fluxa 案例數 | 語言抽象的可攜性（見 [02](02-相鄰領域擴張.md)） |
| 第三方用 Fluxa 產生並簽核的晶片 | 最強的信任憑證 |

| bench 榜單的穩定度 | 可信度的溫度計 |
