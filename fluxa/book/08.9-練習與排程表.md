# 8.9 練習與排程表

## 8.9.1 把 FIR 改成 `pipeline(ii = 1)`

以第 7 章的 4 階 FIR 為基礎，加入排程要求：

```fluxa
pipeline(ii = 1) for s in input {
    let p = (0..4).unrolled()
                    .map(|k| window[k] * COEF[k])
                    .tree_sum();
    out.send(p);
}
```

完成後回答：

- 這個迴圈一輪使用了哪些通道？每個通道幾次？
- 四個乘法是否真的形成平行路徑？
- 若把 `.tree_sum()` 改回依序累加，行為結果是否相同？資源與 II 的期望差異是什麼？

## 8.9.2 比較平衡樹與 `carry`

把 FIR 的總和分別用 `.tree_sum()` 與 `carry` 實作：

```fluxa
carry acc: i32 = 0;
for k in 0..4 {
    acc += window[k] * COEF[k];
}
out.send(acc.sat::<i16>());
```

比較兩者的資料路徑深度、運算器數量與可達成的 II。注意 `carry` 的型別必須能容納最壞情況的四項乘積總和；若用 `i16` 累加，E0301 應該在合成前就指出問題。

## 8.9.3 完成一個 BRAM 友善的模組

設計一個含 ROM 的簡單模組：用常數陣列儲存八個係數，依序對輸入樣本做乘加。要求：

- 常數陣列使用 `--param` 固定成 ROM；
- 記憶體只以 `m[i]` 形式存取；
- `reda check` 沒有未解釋的資源或值域錯誤；
- `reda synth` 報告中能看到預期的記憶體或 ROM 結構。

## 8.9.4 讀懂一份排程表

為你的 FIR 版本填寫下列表格：

| 迭代操作 | 使用的資源 | 每輪次數 | 對應 II 限制 |
| --- | --- | ---: | --- |
| `input.recv()` | 通道 `input` | 1 | 每拍最多 1 token |
| 四個乘法 | 4 個乘法器 | 4 | 可平行則不限制 II |
| 加法樹 | 3 個加法器 | 3 | 組合延遲 |
| `out.send()` | 通道 `out` | 1 | 每拍最多 1 token |
| 歷史樣本更新 | 4 個正反器 | 4 | 迭代邊界提交 |

這張表就是設計者對排程的承諾。若合成結果與表中假設不同，應該能指出差異來自哪一列，而不是只說「工具沒有最佳化」。

## 8.9.5 章末產物

完成本章後，你應該留下一份可交付的排程摘要，至少包含：

- FIR 的迭代操作與每個通道的使用次數；
- 選擇的 II 與理由；
- 使用的暫存器種類（`@reg`、`carry`、一般 `let mut`）；
- 記憶體大小與埠數；
- 預期瓶頸與量測方式；
- 若 II = 1 不可達，下一個要嘗試的結構修改。

下一章會把這份摘要接到實際的 FPGA／ASIC 後端：當網表產生後，這些排程承諾會變成資源、時序與產物報告上的證據。
