# 5.14 章末實作與自我檢核

### 實作練習 5.1：建立雙排程 CI

把 `fir_behavior.fx` 放入專案，執行：

```sh
reda sim fir_behavior.fx
reda sim --coop fir_behavior.fx
```

要求兩個命令都以零退出碼結束。嘗試把 FIFO 深度從 4 改成 1，再跑一次；輸出值、順序與數量應相同，`max-occ` 可能不同。

### 實作練習 5.2：加入脈衝與交錯序列

為標準 `Fir4` 增加兩個測試：

1. 只送一個 `64`，期望第一個輸出為 `8`；
2. 送 `[127, -128, 127]`，先用 `--trace --stats` 找出正確期望值，再把它寫成明確斷言。不要直接以「目前程式輸出」當 oracle；先用 FIR 數學定義人工核對。

### 實作練習 5.3：還原死結等待環

執行：

```sh
reda sim --test circular_wait fluxa/examples/err_deadlock.fx
```

畫出等待圖，回答：

- 哪個 task 最後仍可前進？答案是沒有。
- 增加 FIFO 深度能否解除循環等待？答案是否定的。
- 若要讓測試完成，必須補上什麼來源或改變什麼依賴？

### 實作練習 5.4：讓測試同時證明數量與關閉

不修改 `Fir4`，只在 harness 增加觀察器：它接收 FIR 輸出、逐項轉發，並在輸入關閉後送出計數。證明即使來源只送兩個 token，觀察者仍能在輸出排空後收到 `count == 2`。

### 自我檢核

讀完本章後，你應該能回答：

1. AST 直譯器、共享世界狀態與排程器各自不能做什麼？
2. 原生與合作式排程的等待機制不同，為何 token 結果仍必須相同？
3. 哪些順序由 Kahn 語意保證？哪些跨通道順序沒有保證？
4. 為什麼 task 層不能使用 `try_recv`、`empty` 與 `len`？
5. 一個 FIR oracle 為何至少要分別檢查值、順序、數量與關閉？
6. `--stats` 中哪些欄位適合跨排程比較，哪些主要是診斷資訊？
7. 收到 E0701 後，如何從報告建立循環等待圖？
8. 五個 FIR 測試通過後，仍有哪些風險沒有被排除？

若你能用一個失敗案例說明「第一個偏離點」如何被 trace 與 stats 逐步縮小，本章最重要的除錯能力就已經建立。
