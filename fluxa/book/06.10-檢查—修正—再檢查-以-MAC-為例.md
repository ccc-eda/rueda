# 6.10 檢查—修正—再檢查：以 MAC 為例

### 6.10.1 起始設計

```fluxa
task Mac(a: in chan<i16>, b: in chan<i16>, out: out chan<i24>) {
    carry acc: i24 = 0;
    for _ in 0..8 {
        let x = a.recv();
        let y = b.recv();
        acc += x * y;
    }
    out.send(acc);
}
```

`reda check` 會指出累加值域太大。最小安全型別是 `i34`，原因已在 6.5 節推導。

### 6.10.2 第一種修法：保留完整精度

```fluxa
task Mac(a: in chan<i16>, b: in chan<i16>, out: out chan<i34>) {
    carry acc: i34 = 0;
    for _ in 0..8 {
        let x = a.recv();
        let y = b.recv();
        acc += x * y;
    }
    out.send(acc);
}
```

這是最直接的正確版本，但它也把輸出介面擴成 34 位元。若外部只需要較窄結果，就可能在最後明確飽和；若規格容許模  $2^{24}$  回繞，才使用回繞。

### 6.10.3 第二種修法：縮小演算法範圍

若規格只允許 8 個非負 `u16` 元素，且外部結果只需 `u18`，可以改用：

```fluxa
task MacNonnegative(
    a: in chan<u16>,
    b: in chan<u16>,
    out: out chan<u18>
) {
    carry acc: u18 = 0;
    for _ in 0..8 {
        let x = a.recv();
        let y = b.recv();
        acc += x * y;
    }
    out.send(acc);
}
```

此時：



$$
65535^2\times8 = 34{,}358{,}689{,}800 < 2^{36}
$$



所以這個特定算式其實需要 `u36`，不是 `u18`。這個例子再次證明：**修改型別前必須重新推導，不能把前一個答案機械搬過去。**若只需要 `u18`，就必須把元素或迭代次數限制得更小，並在規格中明說。

### 6.10.4 第三種修法：改變排程，不改語意

若 MAC 真正需要 `pipeline(ii = 1)`，每拍處理一組輸入，累加器就必須跨迭代存在。此時 `carry` 正是正確表達：

```fluxa
pipeline(ii = 1) for _ in 0..8 {
    acc += a.recv() * b.recv();
}
```

但更寬的累加器會增加加法器與暫存器面積；第 8 章會比較平衡加法樹與循序累加器。

### 6.10.5 驗證不只是「檢查變綠」

修正後應依序問：

1. `reda check` 是否無 finding？
2. 原有測試是否仍通過？
3. 新增的邊界測試是否涵蓋最小值、最大值與迭代上限？
4. `reda sim` 與 `reda emu` 的結果是否相同？
5. 合成後的資源與時序是否仍符合規格？

靜態檢查證明語意安全；行為與硬體驗證則證明修正沒有只在分析模型裡成立。
