# 12.4 高品質 prompt 的必要欄位

## 12.4.1 任務與非目標

一個好的 prompt 不只說「做什麼」，也說「不要做什麼」：

- 任務：把 FIR 改成 `pipeline(ii = 1)`。
- 非目標：不要改動通道型別、不要改變飽和策略、不要新增外部依賴。

非目標可以防止 agent 為了「順手改善」而擴大變更範圍。

## 12.4.2 可用 API 與版本界線

prompt 應明確列出：

- 使用哪個語言版本與工具版本；
- 哪些函式或標準庫可用；
- 哪些功能尚未實作，不能使用；
- 遇到規格缺口時應提問，不得臆造 API。

例如：

> 只使用 Fluxa v1.0 已實作功能；`stage` 與 type generic 合成尚未實作，不要使用。

這句話可以直接阻止一類常見的幻想。

## 12.4.3 型別、通道與排程限制

agent 需要知道硬體約束，而不只是功能：

- 輸入輸出通道的元素型別與方向；
- 每輪最多使用每個通道幾次；
- FIFO 深度上限；
- 目標 II 與時脈；
- 記憶體埠限制。

這些限制會直接影響實作結構。若 prompt 沒寫，agent 可能產生一個語意正確但無法合成的設計。

## 12.4.4 必須提供的證據

prompt 應要求 agent 交付：

- 修改的檔案清單；
- `reda check` 與 `reda sim` 的輸出；
- 合成或閘級模擬的結果；
- 已知限制與未驗證項目。

這比只要求「寫好程式」更能產生可審核的結果。

## 12.4.5 可執行的驗收命令

最後，prompt 應包含可以直接執行的命令，例如：

```sh
reda check fir.fx
reda sim fir.fx
reda gatesim ice40 fir.fx
```

如果 agent 無法執行，至少要求它說明預期輸出與如何驗證。沒有驗收命令的任務，通常會以「看起來完成了」收尾。

## 12.4.6 一個模板

```text
任務：<一句話>
非目標：<不要改什麼>
版本：Fluxa v1.0，rueda 0.7.0
介面：<通道與型別>
限制：<通道次數、FIFO 深度、II、時脈>
必須提供：<檔案、check、sim、gatesim 輸出>
驗收命令：<可執行命令>
若規格不足：先提問，不要臆造 API
```
