# 7.11 刻意失敗案例：把等待藏進條件

考慮：

```fluxa
task Bad(x: in chan<i8>, y: out chan<i8>) {
    for v in x {
        if v > 0 {
            y.send(v);
        }
    }
}
```

它在行為模擬中完全合理：只送出正數，負數不送。問題出在硬體排程語意，而不是功能值。

對一般 FSM 而言，這不是錯誤：條件會形成分支，`send` 形成等待狀態；正數走傳送路徑，非正數跳回接收狀態。真正困難的是高吞吐排程：若要求每拍處理一個樣本，「本輪是否送出」會隨資料改變。若輸出沒有握手，可能發生：

- 本輪沒有輸出，迭代已前進；
- 下一輪卻有輸出，形成同通道操作不一致；
- 或某個 token 被保留，導致輸出速率不固定。

因此，像 `pipeline(ii = 1)` 這種要求每輪通道操作固定的排程，會拒絕「通道操作放在條件分支中」的結構，要求設計者改寫：

```fluxa
for v in x {
    let out = if v > 0 { v } else { 0 };
    y.send(out);
}
```

但這兩者功能並不相同：前者不送非正數，後者仍送一個零。因此不能把改寫當成無代價的技巧。正確做法通常是先由規格決定語意：

- 若非正數真的不應出現在輸出，應使用能表達稀疏事件且可證明速率的介面或排程；
- 若外部契約要求一進一出，就明確傳送零；
- 若只要求基本 FSM，條件分支是合法的。

這個案例說明兩件事：

1. 行為正確的控制流，不一定支援某種高效排程；
2. 排程限制不是工具任意禁止，而是為了維持可分析、可等價的硬體結構。

另一個刻意失敗案例是把 `send` 寫在值語境：

```fluxa
let n = y.send(v);  // send 回傳什麼？
```

Fluxa 的 `send` 是通道操作，不是值級函式。降階器只允許把它放在陳述句位置，因為傳送會等待、會改變通道狀態，也沒有一般值語意。工具若遇到這類寫法，應清楚拒絕，而不是捏造一個回傳值。
