# 6.7 端點所有權：每條連線只有一個 owner

### 6.7.1 `spawn` 是所有權轉移，不是複製

```fluxa
task Sink(rx: in chan<u8>) {
    for _ in rx { }
}

test use_after_move {
    let (tx, rx) = chan::<u8>(depth = 2);
    spawn Sink(rx);
    let value = rx.recv();  // 錯誤：rx 已交給 Sink
}
```

`spawn Sink(rx)` 會把接收端所有權移給 `Sink`。從這一行之後，測試主體不再擁有 `rx`，因此不能接收。靜態檢查以 E0702 報告：

```text
`rx.recv()`: the endpoint `rx` was given to the task spawned on line 4
    fix: an endpoint has one owner: use another channel, or keep the endpoint here
```

診斷證據同時指出：

- 違規使用的端點；
- 端點交給誰；
- `spawn` 發生在哪一行。

這比籠統的「use after move」更適合硬體除錯，因為讀者能直接回到接線位置。

### 6.7.2 為什麼不能用複製端點修正

若 `rx` 可以複製，以下程式看似能讓兩個 worker 同時工作：

```fluxa
spawn Worker(rx);
spawn Worker(rx);
```

但這不是廣播，而是兩個接收者競爭同一 FIFO。誰先拿到 token 取決於排程，輸出也可能被任意瓜分，違反第 4、5 章的 Kahn 確定性。

正確需求要分成兩種：

- 每個 worker 都要看到完整序列：使用 `broadcast`；
- 每個 worker 只處理一部分：用明確的靜態分割或工作協定。

線性所有權迫使工程師先回答拓樤問題，而不是把不確定性藏在「複製看看」裡。

### 6.7.3 端點方向與元素型別也必須完全相符

通道 task 參數的方向站在 task 自己的角度：

```fluxa
task Worker(input: in chan<i8>, output: out chan<i8>) {
    for value in input {
        output.send(value);
    }
}
```

把傳送端交給 `in chan<T>`，屬於方向不符；把 `chan<i8>` 交給 `chan<i16>`，屬於元素格式不符。即使 `i8` 的每個值都能放進 `i16`，通道跨元件邊界仍必須使用同一固定格式，否則 FIFO 中每個 token 究竟佔 8 還是 16 位元便失去契約。

這些連線錯誤可能在模擬器 `spawn` 時或合成時被拒絕，不一定由目前 `reda check` 的通道守恆模型回報。閱讀任何通道診斷時，都要先問：**它是值域問題、端點所有權問題，還是連線格式問題？**
