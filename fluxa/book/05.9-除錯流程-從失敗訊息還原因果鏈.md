# 5.9 除錯流程：從失敗訊息還原因果鏈

行為模擬最常見的誤用，是看到 assertion failed 就開始猜演算法。更好的方法是沿著「契約 → token 序列 → 通道事件 → 等待關係」逐層縮小問題。

### 5.9.1 第一步：固定範圍

假設 FIR 測試失敗，先不要立刻執行整個程式集：

```sh
reda sim --test fir4_step fluxa/examples/fir4.fx
```

這能排除：

- 其他測試輸出干擾；
- 測試之間的殘留狀態；
- 不相關的元件初始化錯誤。

若失敗只在某些機器出現，也要先確認工具版本、來源版本與命令完全相同。行為模擬器不應依賴未固定的隨機種子，因為 task 層本來就沒有隨機排程語意。

### 5.9.2 第二步：寫下預期 token 序列

不要只看 assertion 的左右值。先用純文字寫出預期：

```text
輸入：64, 64, 64
輸出：8, 32, 56
數量：3 進、3 出
關閉：來源在第 3 個輸入後關閉；FIR 排空後關閉輸出
```

這份小契約會告訴你下一個觀察應該回答什麼：

- 若第一個輸出就是 7，問題在第一個係數乘加或初始狀態；
- 若前兩個對、第三個錯，問題在 history 更新；
- 若三個值都對但還沒結束，問題在關閉；
- 若 trace 顯示少了一個 recv，問題在資料流或端點，而不是 FIR 算術。

### 5.9.3 第三步：沿通道找第一個偏離點

用 `--trace` 找出第一個不符合預期的 token，再往回追它的來源：

```text
result[0] = 8   正確
result[1] = 32  正確
result[2] = 55  錯誤，預期 56
```

接著查看 FIR 接收到的第三個樣本。如果 trace 顯示它收到 63，而來源原本要送 64，根因在來源或 FIFO；若來源確實送了 64，才檢查 FIR 的 history 與係數。

這種「找第一個偏離點」的方法比從整段 waveform 或所有 assertion 往回猜更省時間，也讓修正範圍保持局部。

### 5.9.4 第四步：用 stats 區分值錯與數量錯

假設 assertion 顯示期望 56、實際 55。先看 stats：

- 若 `sent = recv = 3`，數量守恆，優先查值；
- 若 `sent = 4`、`recv = 3`，多送了一個 token，優先查來源；
- 若 `sent = recv = 2`，元件少產生一個結果，優先查 FIR 迴圈或關閉；
- 若 `max-occ = depth`，來源曾把 FIFO 填滿，確認目前看到的等待是否只是正常背壓。

數量與內容是兩條不同的證據鏈。硬體除錯時也常有類似二分法：先確認控制與資料，再確認資料內容。

### 5.9.5 第五步：比較兩種排程器

若原生通過、合作式失敗，優先尋找：

- task 層的非確定操作；
- 未受通道契約保護的共享狀態；
- 依賴「另一 task 剛好先跑」的假設；
- 不同通道間被誤當成有全域順序的關係。

若兩種排程器都失敗在相同斷言，通常是語意或契約錯誤，而不是 OS 競態。若兩者以不同方式失敗，再用兩份 trace 比較每條通道的投影，而不是比較跨通道事件行。

### 5.9.6 第六步：縮小成最小程式

最小重現應保留：

- 一個能產生錯誤的元件；
- 必要的上下游；
- 一個能重現的測試向量；
- 一個失敗的斷言。

刪除與問題無關的 task、FIFO、廣播分支與數值案例。若刪掉某個 task 後錯誤消失，它可能是根因，也可能是改變了等待時序；因此縮小後仍應在原生與合作式排程器各跑一次。

### 5.9.7 一張除錯檢核表

| 問題 | 先問自己 | 第一份證據 |
| --- | --- | --- |
| 值錯 | 第一個錯誤 token 在哪裡？ | trace + 預期序列 |
| 順序錯 | 哪條通道的子序列反了？ | 逐通道 trace 投影 |
| 數量錯 | 誰多送或少送？ | `--stats` 的 sent/recv |
| 不結束 | 誰在等什麼？ | E0701 等待報告 |
| 偶發失敗 | 是否有非確定操作？ | 原生與 `--coop` 比較 |
| 只在合成後錯 | 行為與硬體哪條契約不同？ | 第 10 章的跨層差異矩陣 |

這張表的價值在於把「重新跑一次」換成可保存的證據。
