# 5.3 兩種排程器，同一份語意

Fluxa v1.0 提供兩種行為排程方式。它們的主要差異不是結果，而是如何把有限的執行時間分給各 task。

| 面向 | 預設原生排程 | `--coop` 合作式排程 |
| --- | --- | --- |
| task 承載方式 | 每個 spawned task 一條 OS 執行緒 | 同一條執行緒上的多個 future |
| 等待方式 | 阻塞等待條件變數 | future 回傳 `Pending`，稍後再 poll |
| 適用環境 | 一般原生工具鏈 | 單執行緒環境、WebAssembly |
| 主要風險 | OS 排程、競態與死結 | 輪流順序與等待點處理 |
| 必須保持的結果 | 同一通道的 token 序列 | 同一通道的 token 序列 |

### 5.3.1 原生排程器：每個 task 一條執行緒

預設模式下，`spawn` 會為 task 啟動一條 OS 執行緒。task 執行到 `recv` 時，如果 FIFO 為空，就阻塞在共享狀態的條件變數上；另一個 task 送入 token 後，模擬器喚醒等待者。

這種模型最接近一般多執行緒程式，也最容易暴露真正的競態問題。Fluxa 並不是把 task 當成「碰巧運作正常的執行緒」，而是用幾項規則消除排程依賴：

- 通道端點是線性資源，只有一個 owner；
- 一條 FIFO 只有一個送端與一個收端；
- token 只能阻塞式送收；
- 同一通道保持 FIFO 順序；
- task 的私有變數不與其他 task 共享。

通道操作還會更新共享世界的 epoch。每次送、收、關閉、task 結束或 spawn 都代表世界狀態改變；等待者被喚醒後會重新檢查條件，而不是假設「剛才被通知時事情一定已經可做」。這能避免通知先於狀態更新所造成的假覺醒。

原生排程器的死結偵測也很直接：若所有仍存活的 task 都已阻塞，且沒有任何狀態改變能喚醒它們，就沒有人能再前進。模擬器會報告 E0701，而不是無限等待。

### 5.3.2 合作式排程器：所有 task 輪流前進

`--coop` 把每個 task 表示成一個非同步 future。某個 task 在通道上等待時，不會阻塞整個執行緒，而是讓出控制權。排程器輪流 poll 測試主體與各 task 的 future；某個 future 回傳 `Pending` 時，先放到一輪之後再試。

合作式排程器的優點是：

- 不依賴 OS 執行緒，因此在瀏覽器與 WebAssembly 中也能執行；
- task 切換點明確，更容易重現；
- 不會因為 OS 過度排程而讓除錯輸出過度交錯。

代價是排程器必須正確處理「等待點」。若 task 在 future 裡忘記回傳 `Pending`，單執行緒就會卡死；若等待邏輯錯誤地重複前進，也可能破壞計數。因此合作式排程不是把原生排程刪掉執行緒就完成，而是用另一種機制實現同一個世界模型。

在 WebAssembly 環境中，模擬器會自動使用合作式模式；命令列則可用 `--coop` 強制啟用它：

```sh
reda sim --coop fluxa/examples/fir4.fx
```

### 5.3.3 為什麼兩種排程器都必須通過

考慮一個簡單的轉發網路：

```fluxa
task Copy(x: in chan<i8>, y: out chan<i8>) {
    for v in x {
        y.send(v);
    }
}
```

若輸入序列是 `[5, -7, 0]`，輸出序列必須是 `[5, -7, 0]`。原生排程器可能執行成：

```text
Copy 接收 5
Copy 送出 5
Copy 接收 -7
Copy 送出 -7
```

合作式排程器也可能執行成：

```text
Copy 接收 5
Copy 送出 5
Copy 接收 -7
Copy 送出 -7
```

即使兩者碰巧相同，也不代表它們被證明等價。真正的要求是：無論排程器先安排來源、Copy 或觀察者，只要網路能完成，下列 token 對應關係就不能改變：

```text
第 0 個輸入 5    -> 第 0 個輸出 5
第 1 個輸入 -7   -> 第 1 個輸出 -7
第 2 個輸入 0    -> 第 2 個輸出 0
```

因此，一份合格的 CI 至少應在原生與合作式排程器各跑一次同一組測試。兩者都通過，才表示目前案例符合預期的排程無關語意。
