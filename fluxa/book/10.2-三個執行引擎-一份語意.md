# 10.2 三個執行引擎，一份語意

## 10.2.1 行為直譯器

`reda sim` 直接解讀 Fluxa 的 AST 與語意。它通常最接近規格文件，適合：

- 建立可讀的 oracle；
- 快速嘗試邊界案例；
- 在改動硬體結構前確認演算法。

直譯器的優點是可觀察性高，缺點是速度慢，且與硬體實作之間仍隔著一層語意映射。

## 10.2.2 編譯後執行器

`reda emu` 把 task 降階成狀態式執行器：直線程式碼放在 64／128 位元暫存器上，通道則用環形緩衝區實作。它的目標是比直譯器快，適合較大的測試集。

對 Fluxa，`reda emu` 會執行同一組測試，並要求結果與直譯器一致。它也可以輸出 WebAssembly 模組與 JSON 中介資料，供外部 harness 使用：

```sh
reda emu --top Fir fir.fx
reda emu -o fir.wasm --top Fir fir.fx
```

編譯後執行器驗證的是一個關鍵假設：**把行為編譯成狀態機後，語意沒有改變**。這個假設若成立，後續的硬體降階才有可靠的基礎。

## 10.2.3 閘級模擬

`reda gatesim` 把合成後的網表放回測試中。以 Fluxa 為例，程式的測試會以 `--top` 指定的 task 之合成網表執行，通道連到網表的串流埠；沒有指定 `--top` 時，每個可合成的 task 都會以閘級執行。

支援的網表種類包括：

```sh
reda gatesim opt  fir.fx
reda gatesim ice40 fir.fx
reda gatesim ecp5  fir.fx
reda gatesim asic  fir.fx
reda gatesim sky130 fir.fx
```

不同種類代表不同的技術映射。它們都應該對同一組測試給出相同結果。

## 10.2.4 同一份語意，三種投影

可以把它想成同一個函數在三種表示法上的投影：

$$
f_{\text{sim}}(x) = f_{\text{emu}}(x) = f_{\text{gates}}(x)
$$

對所有測試輸入 $x$ 都應成立。實務上我們只能用有限的測試集檢查，因此「等價」是「在這組測試上一致」，而不是數學上對所有輸入的形式證明。

這個區別不削弱工程價值：只要測試集涵蓋正常、邊界與錯誤案例，三層一致就是很強的證據。但文件與審核時必須誠實說明證據的範圍。
