# 1.4 從需求到 token 契約

現在把前面的直覺整理成一份可以拿給同事、拿給測試人員、拿給工具鏈看的規格。先不要急著寫 task；先問清楚資料流的邊界。

### 1.4.1 一份契約的骨架

我們可以用以下八個欄位描述一個硬體介面：

- **來源與目的地**：誰產生 token，誰消費 token？
- **元素型別與值域**：token 代表什麼？可表示的數值範圍是什麼？
- **數量與順序**：一筆交易對應幾個 token？順序是否有意義？
- **對應關係**：第幾個輸入產生第幾個輸出？
- **生命週期**：何時關閉？關閉前是否要清空或沖刷狀態？
- **背壓與容量**：接收端忙碌時如何等待？有限容量由誰擁有？
- **速率目標**：希望每拍、每若干拍或以何種外部協定完成一筆工作？
- **錯誤行為**：型別錯誤、溢位、非法握手或狀態錯誤怎麼處理？

這份清單看起來比「寫一個函式」麻煩，但它把最容易被忽略的硬體問題放到了明處。軟體 API 可以先假設呼叫者最後會呼叫關閉；硬體元件則必須把關閉與背壓當成可發生的事件。

### 1.4.2 FIR 的第一版 token 契約

現在用四階 FIR 填入這張表。以下是**概念契約**，不是本章要背的 Fluxa 語法；型別細節與實際通道操作會在後續章節展開。

| 契約欄位 | FIR 的第一版選擇 | 為什麼要這樣定 |
| --- | --- | --- |
| 來源 | 樣本來源 task | 來源只負責產生樣本，不知道濾波內部狀態 |
| 目的地 | 結果消費者 task | 消費者只接收已完成的結果 token |
| 輸入元素 | 一個有號樣本，暫定 16 位元 | 先固定語意；實際係數格式與乘積位寬待推導 |
| 輸出元素 | 一個濾波結果，型別必須容納累加結果 | 不能直接沿用輸入型別 |
| 數量與順序 | 每次輸入對應至多一個結果，結果保持輸入順序 | 下游可把 `y[n]` 對回 `x[n]` |
| 初始狀態 | 歷史視窗以零初始化 | 明確規定第一筆結果，避免「第一個樣本」有特例 |
| 關閉語意 | 來源關閉後，濾波器消耗剩餘輸入，並依規格沖刷尾端結果 | 不能在仍有待處理 token 時直接關閉輸出 |
| 背壓 | 通道為有限容量；傳送端等待，接收端決定何時取用 | 不丟樣本，也不隱藏資源限制 |
| 速率目標 | 目標 II = 1；延遲上限另列 | 這是產品需求，不是程式自然產生的結果 |
| 錯誤 | 中間值不得窄化；最終輸出採飽和策略 | 溢位處理必須在契約中先決定 |

若選擇「來源每送一個輸入，必須得到一個輸出」，FIR 的狀態與對應關係可以畫成：

```text
來源                 FIR task                    消費者
 x[0]  ───────────>  [產生 y[0]]  ───────────>  y[0]
 x[1]  ───────────>  [產生 y[1]]  ───────────>  y[1]
 x[2]  ───────────>  [產生 y[2]]  ───────────>  y[2]
 x[3]  ───────────>  [產生 y[3]]  ───────────>  y[3]
                         ...
```

但這張圖還不完整。若 FIR 的四個係數都要貢獻，輸入 `x[0]`、`x[1]`、`x[2]` 之後，歷史狀態仍會影響 `y[3]` 之後的結果。當來源在 `x[3]` 之後關閉，FIR 可能仍需要把尚在延遲線中的樣本算完。因此，契約還要明確選擇：

- **純串流語意**：每個輸入只產生一個即時結果，關閉後不再沖刷尾端；
- **完整濾波語意**：來源關閉後，額外送入三個零（或明確的 flush token），使每個輸入樣本都得到一個對應結果。

兩種語意都可以合理，但對方必須知道。這個選擇會影響通道關閉、消費者等待的條件，以及測試應該期待幾個輸出 token。

### 1.4.3 刻意讓契約失敗一次

很多硬體錯誤並不是演算法錯，而是契約少寫了一個條件。考慮以下看似合理的描述：

> FIR 接收連續樣本，並將計算結果送到消費者。來源會一直送資料，通道足夠大時不必擔心。

這句話有三個漏洞。

第一，「連續」沒有速率。來源可能每拍送一個，也可能送得太快，連有限 FIFO 也無法吸收。第二，來源若忽略接收端的背壓，就可能丟棄樣本或破壞順序。第三，「通道足夠大」不是可落地的硬體參數；通道深度越大，通常需要更多暫存器、延遲與時序余量。

另一個常見漏洞是只寫「每次輸入產生一次輸出」，卻沒有說明來源關閉時怎麼辦。若實作者把「來源已關閉」誤當成「所有輸出都已送出」，消費者可能永遠等待最後幾個 token；若實作者過早關閉輸出，則會丟失尾端結果。

在 Fluxa 中，這些問題會逐漸變成可以定位的診斷：值域不合法會在型別落點被指出，通道所有權與關閉關係會在靜態檢查中被指出，資源或背壓問題則會在檢查與排程分析中顯現。第 6 章會示範如何解讀這類訊息。
