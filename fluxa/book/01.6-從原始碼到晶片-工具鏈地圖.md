# 1.6 從原始碼到晶片：工具鏈地圖

Fluxa 原始碼不是直接變成 bitstream 的黑盒子。整條路徑可以先用下列地圖理解：

```text
Fluxa 原始碼
     │
     ├─ 解析、名稱解析、型別與值域推導
     │
     ├─ reda check ──> 靜態診斷（值域、通道、資源、所有權）
     │
     ├─ reda sim ────> 行為 oracle（token 順序、assert、trace）
     │
     ├─ 展開、降階、排程、FSM 與資料路徑
     │
     ├─ Rueda 網表 IR ──> 通用網表
     │                         ├─ reda emu / gatesim
     │                         ├─ FPGA：位元流
     │                         └─ ASIC：GDS
     │
     └─ 資源與時序報告 ──> 回頭修正契約或排程
```

各工具的責任不同：

- **`reda sim`** 先證明「這份行為契約是否合理」。它適合快速建立測試、追蹤 token、檢查通道關閉與數值結果。
- **`reda check`** 在模擬或合成前找出語意問題。它可以提醒某個值無法放進目標範圍、通道端點所有權不合法，或資源安排無法滿足需求。
- **`reda synth`** 把設計降到可合成的網表，並提供資源與時序資訊。合成成功不等於所有介面都已完成驗證。
- **`reda emu`** 是較接近編譯後硬體的模擬路徑，可用來觀察排程後的行為與資源模型。
- **`reda gatesim`** 在閘級網表上做模擬，將邏輯錯誤與實體網路錯誤一起暴露出來。
- **FPGA／ASIC 後端**分別把通用網表轉成可載入裝置的位元流或晶片實體資料，並產生各自的資源與時序報告。

例如在本書主線的 FIR 專案中，一個合理的日常順序是：

```sh
reda sim fluxa/examples/fir4.fx
reda check fluxa/examples/fir4.fx
reda emu fluxa/examples/fir4.fx
reda synth --top Fir fluxa/examples/fir4.fx
```

這個順序的重點不是命令本身，而是每一層都在回答不同問題。sim 問「行為對不對」；check 問「能不能被接受並安全地排程」；emu 問「降階後的排程是否仍符合契約」；synth 問「在目標資源與時序限制下是否做得出來」。

Rueda 的網表 IR 位於語言前端與 EDA 後端之間，是這個流程的匯流點。前端保留足夠的語意資訊來產生可檢查的行為與硬體結構；後端則把共同網表映射到不同裝置與實作流程。這也提醒我們，「用 Fluxa 寫」不等於「不需要 EDA 知識」：你仍然需要讀懂資源報告與時序報告，才能把語言契約轉成產品決策。
