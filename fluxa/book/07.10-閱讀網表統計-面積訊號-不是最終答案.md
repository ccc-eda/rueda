# 7.10 閱讀網表統計：面積訊號，不是最終答案

### 7.10.1 先看結構，再看總數

網路報告會列出：

- task 實例，例如 `scale0`、`offset0`、`count0`；
- FIFO，例如 `fifo ta (2 x 11 bits)`；
- 各部分在最佳化前的 cell 數；
- 總 cell 數；
- 警告。

這種 per-part 報告非常有用，因為總數只告訴你「大了」，分解後才知道是：

- 某個 task 的資料路徑太大；
- FIFO 深度造成大量 entry FF；
- 廣播器複製了資料；
- 某個 task 的 FSM 狀態過多；
- 某個 task 忘了使用通道，因而多出警告。

例如，若 FIFO 閘數占總閘數至少 30%，目前工具會警告內部 FIFO 面積過大，並指出最大的幾個通道。深度若只是為了讓行為模擬不那麼容易死結而被一路加大，這個警告就是在提醒設計者：程式可能通過模擬，卻不代表拓樸合理。

### 7.10.2 通用閘數不是 FPGA LUT 數

通用網表中的 cell 可能是：

- 單一 bit 邏輯；
- 加法器；
- 比較器；
- 多工器；
- FF；
- 乘法器或其他高階組合；
- 尚待目標技術映射的 cell。

一個通用 cell 在 iCE40、ECP5 或 ASIC 標準單元庫中，可能對應一個 LUT、一組 LUT、專用 DSP、一條 standard cell，甚至被分解成多個 cell。因此：

> 通用閘數是比較不同設計與偵察異常膨脹的相對指標，不是 FPGA 資源報告，也不是時序報告。

真正的 LUT／FF／BRAM／DSP 用量，要等目標裝置映射；真正的最高頻率，要等佈局繞線後的時序分析。第 9 章會完整走過這條流程。

### 7.10.3 報告中的警告是設計線索

幾種值得留意的警告包括：

| 警告 | 可能原因 | 應該回頭檢查什麼 |
| --- | --- | --- |
| 通道從未使用 | task 介面有多餘通道 | 是否宣告了錯誤介面？ |
| 記憶體退回暫存器陣列 | 存取形式不是簡單 `m[i]` | 是否值得改成 BRAM 友善形式？ |
| FIFO 占比過高 | 深度過大或通道太多 | token 契約真的需要這麼深嗎？ |
| 網路參數需以 `--param` 固定 | 拓樸含未固定的形狀 | 參數化邊界是否合理？ |

不要把警告當成雜訊。每一則警告都在提示某個語意與硬體形狀之間可能沒有完全對齊。
