# 12.3 代理式工作流中的四種角色

## 12.3.1 為什麼要分角色

一個 agent 可以同時做規格分析、實作、測試與審查，但不同角色的思考模式與驗收條件不同。把它們分開，可以減少「自己寫、自己說對」的盲點。

四種角色不是四個人，而是四種提示與檢查視角。

## 12.3.2 規格／拓樸分析者

責任：

- 讀懂需求與現有程式；
- 指出介面、型別、通道與排程假設；
- 找出規格缺口與版本界線；
- 產出可檢查的契約條款。

驗收條件：

- 每個假設都有來源（規格章節、程式行號或命令輸出）；
- 不明確的地方標成問題，而不是自行補完。

## 12.3.3 Fluxa 實作者

責任：

- 依契約實作 task 與網路；
- 使用已實作的語言功能；
- 保持型別、通道與排程意圖一致；
- 產生可讀的註解與參數說明。

驗收條件：

- `reda check` 沒有未解釋的錯誤；
- 行為模擬通過；
- 不使用未實作或不可合成的構造。

## 12.3.4 測試與 oracle 產生者

責任：

- 依契約產生正常、邊界與錯誤案例；
- 建立獨立 oracle；
- 設計可重複執行的命令；
- 保存失敗案例。

驗收條件：

- 測試能在乾淨環境重跑；
- 邊界案例真的測到邊界；
- oracle 不是直接呼叫被測實作。

## 12.3.5 驗證／code review 者

責任：

- 檢查實作是否符合契約；
- 比對三層驗證結果；
- 找出未覆蓋的行為與過度承諾；
- 決定是否可以合併。

驗收條件：

- 每個結論都有證據；
- 高風險變更有獨立審查；
- 失敗路徑有明確處置。

## 12.3.6 同一個 agent 也可以扮演多個角色

實務上，你可能用同一個模型依序扮演四個角色。關鍵不是角色數量，而是：

- 每次切換角色時，使用不同的提示與驗收條件；
- 不要讓實作者自己宣布「已充分驗證」；
- 讓審查者看到原始契約與證據，而不是只看到實作者的摘要。

這樣即使只有一個 agent，也能保留多視角的檢查效果。
