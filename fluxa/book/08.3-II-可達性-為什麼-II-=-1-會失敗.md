# 8.3 II 可達性：為什麼 II = 1 會失敗

### 8.3.1 單一管線狀態的結構限制

在目前 v1.0 合成器中，`pipeline(ii = 1)` 會嘗試把迴圈本體降成一個 `Pipe` 狀態。這個狀態在某個時脈邊界觀察：

1. 迭代需要的輸入通道是否都有 `valid`；
2. 迭代要送出的通道是否都有 `ready`；
3. 通道是否尚未關閉；
4. 若迴圈是計數式，還有沒有下一個迭代。

只有條件成立，迭代才會「發火（fire）」：輸入 token 被接收、資料路徑計算、輸出 token 被送出，並在迭代結束時提交暫存器寫入。

因此，下面這類迴圈能被目前管線狀態容納：

```fluxa
pipeline(ii = 1) for s in x {
    let a = left.recv();
    let b = right.recv();
    out.send(a + b);
}
```

它每輪從兩個不同通道各收一次，再送一次；每個通道的每拍流量仍是一個 token。

相反地，同一通道在一輪收兩次，會違反通道的硬體速率：

```fluxa
pipeline(ii = 1) for _ in 0..4 {
    let a = x.recv();
    let b = x.recv();     // 同一通道，本輪需要兩個 token
    y.send(a + b);
}
```

### 8.3.2 E0401：資源使用超過單一 bank 的容量

`reda check` 的 E0401 檢查每一輪對資源的使用量。Fluxa v1.0 的單一 bank 模型把通道視為每拍最多傳送一個 token，把一個記憶體視為一個讀埠與一個寫埠。若一輪使用的數量超過 `ii` 個時槽，就會報告 E0401。

概念上的檢查式是：



$$
\text{uses}(r)\le \text{capacity}(r)\times ii
$$



其中通道的 `capacity` 是每拍一個 token，記憶體讀取與寫入各有一個埠。這個檢查是保守的靜態模型：它能確定資源衝突，卻不能證明所有目標裝置上的實際時序都可行。

E0401 的證據應該包含：

- 哪個資源被超用；
- 一輪用了多少次；
- 單一 bank 的容量是多少；
- 程式行號；
- 可以採取的修正方向。

不要只把 `ii` 隨便加大。若一輪真的需要同一通道的兩個 token，增大 II 可能讓循序 FSM 有時間分兩次收，但這也會改變吞吐需求；應先確認產品允不允許這樣的速率。

### 8.3.3 E0412：合成器無法把要求排成管線

E0412 是 `pipeline(ii = n)` 的排程失敗診斷。它不是型別錯誤，而是「要求」與「目前可生成的硬體結構」不相容。下列片段會失敗：

```fluxa
pipeline(ii = 1) for _ in 0..4 {
    let v = x.recv();
    if v > 0 {
        y.send(v);          // 不同迭代可能有不同通道操作
    }
}
```

管線狀態要求每一輪都有固定形狀的通道操作；條件分支可能讓某些迭代送出、某些迭代不送出，因此無法用一個統一的每拍狀態描述。

另一個常見失敗是把接收放在送出之後：

```fluxa
pipeline(ii = 1) for _ in 0..4 {
    y.send(1);
    let v = x.recv();
}
```

目前後端的管線狀態只接受每輪固定、且以接收為先的通道操作順序；送出後再接收會使握手與迭代邊界無法直接表示。

還有目前實作的限制：`mem` 讀取在硬體中佔一個時脈，不能直接塞進同一個單週期管線狀態；因此直接含記憶體存取的 `pipeline` body 可能被拒絕。若要處理記憶體，通常要把它安排成獨立的 FSM 階段，或使用循序迴圈，而不是假設 `pipeline` 會自動把讀取拆成 stage。

一個 E0412 訊息的核心資訊可以像這樣：

```text
error[E0412]: pipeline(ii = 1) cannot be met:
  channel `x` is received twice in an iteration (one token a clock)
  note: one iteration must use a fixed channel-operation shape
  help: use separate channels, or restructure the loop as a sequential FSM
```

不同版本的文字可能略有差異，但診斷的讀法固定為三步：

1. **位置**：哪一個 `pipeline` 迴圈失敗？
2. **證據**：是哪個通道、存取或相依造成瓶頸？
3. **修正**：要分開通道、改成循序 FSM、放寬 II，還是改變演算法？

### 8.3.4 `ii >= 2` 的保守解讀

理論上，II = 2 表示相鄰迭代可以相隔兩個週期啟動，讓一輪有兩個時槽使用通道或記憶體資源。Fluxa v1.0 的靜態資源模型可以計算某些 `ii >= 2` 的容量，但目前硬體後端的處理必須保守解讀：

- `ii = 1` 才有明確的單一管線狀態路徑；
- 若目前管線降階不能表示某個 `ii >= 2` 迴圈，後端可能退回一般 FSM；
- 退回 FSM 保留了程式語意，卻不表示它已達成「每 n 拍啟動一次」的排程保證。

所以，設計文件不應只寫：

```text
pipeline(ii = 2) => 每兩個時脈啟動一次
```

比較誠實的寫法是：

```text
要求啟動間隔至少為 2；目前後端在不能直接形成模數管線時退回循序 FSM，
實際啟動間隔須由合成後網表或硬體量測確認。
```

若產品真的依賴精確的 n-cycle initiation，應把它列為額外驗收條件，並在第 9、10 章用網表與 gatesim 證據確認，而不是只看原始碼。

### 8.3.5 排程要求不等於時序通過

`pipeline(ii = 1)` 解决的是「每拍最多啟動幾次迭代」的結構問題；它不保證一輪的組合邏輯能在目標時脈週期內完成。假設 FIR 的四個乘法、加法樹與飽和轉換全部串成一條很長的路徑，II = 1 仍可能在 100 MHz 目標下時序失敗。

目前 Fluxa v1.0 沒有 `stage` 層，也沒有完整的自動 retiming 保證。要改善長路徑，工程師需要：

- 用 `comb fn` 或明確的資料路徑表達組合區段；
- 把狀態邊界放在需要暫存的地方；
- 針對目標裝置查看 LUT、DSP、FF 與時序報告；
- 若需要真正的多級資料管線，先確認目前語言與後端提供的表達方式，不能把 `pipeline` 當成自動插樁器。

這也是本章把「時序」與「資源」放在同一章的原因：管線切得愈細，通常時序愈容易，但暫存器與控制愈多；序列重用的算術愈多，面積愈小，但 II 與延遲通常惡化。
