# 2.7 第一個可測試硬體元件：8 位元飽和倍增器

現在把前面的觀念組裝成一個真正可測試的元件。

### 先寫契約

`SaturatingDouble` 的契約是：

- 輸入：每個 token 是一個 `u8`，值域 `0..=255`。
- 輸出：每個 token 是一個 `u8`，值域 `0..=255`。
- 順序：輸入第 `k` 個 token 對應輸出第 `k` 個 token。
- 轉換：輸出為 `min(2 × 輸入, 255)`。
- 關閉：輸入關閉後，元件不再產生新 token；輸出 task 結束時會關閉輸出端。
- 硬體代價：一條 8 位元乘法／移位資料路徑、一個飽和比較器，以及通道介面；FIFO 深度是系統整合時可選擇的參數。

這個例子選 8 位元，是為了讓「值域」與「硬體寬度」一眼可見。真正的 FIR 會在第三章與第十一章處理更複雜的乘積與累加寬度。

### 規格寫成註解

```fluxa
// SaturatingDouble
// 輸入／輸出：u8 token，順序一一對應。
// 輸出規則：min(input * 2, 255)。
// 關閉：輸入通道關閉且清空後，輸出不再增加 token。

task SaturatingDouble(
    x: in chan<u8>,
    y: out chan<u8>
) {
    for v in x {
        y.send((v * 2).sat::<u8>());
    }
}
```

這裡 `(v * 2)` 的值域是 `0..=510`，不是 `u8`。`.sat::<u8>()` 明確宣告轉換策略：低於 0 的值（本例不可能）映到 0，高於 255 的值映到 255。語法與行為都在同一處，不需另外口頭約定。

### 完整測試：建立通道、啟動、傳送、關閉、接收、斷言

```fluxa
test saturating_double_contract {
    let (tx, rx) = chan::<u8>(depth = 4);
    let (ty, ry) = chan::<u8>(depth = 4);

    spawn SaturatingDouble(rx, ty);

    let inputs  = [0, 1, 100, 127, 128, 200, 254, 255];
    let outputs = [0, 2, 200, 254, 255, 255, 255, 255];

    for v in inputs {
        tx.send(v);
    }
    tx.close();

    let mut got = [];
    for v in ry {
        got = concat(got, [v]);
    }
    assert got == outputs;
}
```

逐行讀這份測試：

1. `chan::<u8>(depth = 4)` 建立一個元素型別為 `u8`、容量為 4 的有界 FIFO，並回傳 `(tx, rx)`。
2. `spawn SaturatingDouble(rx, ty)` 把接收端與傳送端交給元件。測試主體保留 `tx` 與 `ry`。
3. `inputs` 與 `outputs` 是參考向量；參考答案不應呼叫待測元件本身產生。
4. `tx.send(v)` 依序送出輸入。FIFO 滿時，`send` 會阻塞，這是背壓而非錯誤。
5. `tx.close()` 表達沒有更多輸入。
6. `for v in ry` 一直收到輸出通道關閉；`concat` 把收到的 token 依序收集成陣列。
7. `assert got == outputs` 同時檢查 token 數量、數值與順序；少一個、多一個或次序不同都會失敗。

注意 `rx` 與 `ty` 在 `spawn` 後不可再使用。這不是可省略的 lint，而是端點所有權規則。

### 測試不應只測一個案例

如果測試只送 `10`，它無法證明 127、128、254、255 的邊界正確。更糟的是，若元件在 `128` 沒有正確飽和，普通測試仍可能通過。

好的最小測試至少包含：

- 零與一般值；
- 未飽和區間的上緣；
- 第一個會飽和的值；
- 最大輸入；
- 多個 token，確認順序沒有交換。

上面的八組向量正好覆蓋這些情況。

### 如何執行與檢查

把元件與測試放在同一個 `saturating_scale.fx`：

```sh
reda sim saturating_scale.fx
reda sim saturating_scale.fx --test saturating_double_contract
reda sim saturating_scale.fx --coop
```

`--coop` 應得到與預設排程器相同的結果。若預設排程器通過、合作式排程器失敗，或兩者只因印出訊息順序不同就失敗，那是實作問題，不是可接受的「測試太嚴格」。第五章會更深入討論 deterministic output。

下一章會用 `reda check` 在執行前找出值域問題。但現在可以先做一個刻意的錯誤：

```fluxa
// 錯誤：u9 的 300 不能落入 u8。
let a: u8 = 200;
let b: u8 = 100;
let c = a + b;
let d: u8 = c;
```

`c` 的推導值域是 `0..=510`，而 `d` 的落點只有 `0..=255`。這個錯誤會以 E0301 被攔下。修正不是把 `u8` 改成 `u9` 就結束，還要看元件契約：本例要的是 8 位元飽和輸出，所以正確修法是明確使用 `.sat::<u8>()`。

### 把元件與契約放在同一個檔案

本章的完整 `saturating_scale.fx` 可以是：

```fluxa
// 契約：
// - 輸入／輸出：u8 token
// - 順序：輸入第 k 個 token 對應輸出第 k 個 token
// - 輸出值：min(input * 2, 255)
// - 輸入關閉後，元件停止產生輸出。

task SaturatingDouble(
    x: in chan<u8>,
    y: out chan<u8>
) {
    for v in x {
        y.send((v * 2).sat::<u8>());
    }
}

test saturating_double_contract {
    let (tx, rx) = chan::<u8>(depth = 4);
    let (ty, ry) = chan::<u8>(depth = 4);
    spawn SaturatingDouble(rx, ty);

    let inputs  = [0, 1, 100, 127, 128, 200, 254, 255];
    let outputs = [0, 2, 200, 254, 255, 255, 255, 255];

    for v in inputs {
        tx.send(v);
    }
    tx.close();

    let mut got = [];
    for v in ry {
        got = concat(got, [v]);
    }
    assert got == outputs;
}
```

這份檔案很小，卻已包含四種重要證據：

- **型別證據**：輸入與輸出元素都是 `u8`。
- **值域證據**：乘法結果透過明確的飽和策略落到 `u8`。
- **序列證據**：輸出 token 的數量與順序符合參考向量。
- **關閉證據**：測試明確關閉輸入；`for v in ry` 只有在元件關閉輸出且 FIFO 清空後才結束。
