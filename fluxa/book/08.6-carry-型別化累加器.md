# 8.6 `carry`：把累加器契約寫進型別

## 8.6.1 為什麼累加器需要專門的宣告

第 3 章談值域推導時，我們看過一個容易低估的風險：單次加法安全，不代表整段迴圈安全。若每一輪都把一個值加進累加器，最終值域會隨次數成長：

```fluxa
let mut total: i8 = 0;
for _ in 0..16 {
    total = total + sample; // 單次加法可能安全，但 16 次未必
}
```

值的範圍不是「一次加法」的範圍，而是「初值 + 次數 × 每次增量」的範圍。`carry` 把這件事變成一種明確宣告，讓靜態檢查能沿著迴圈把次數與增量一起算進來：

```fluxa
carry total: i32 = 0;
for s in input {
    total += s;
}
```

## 8.6.2 型別化累加器的範圍規則

Fluxa v1.0 對 `carry x: T = initial;` 的靜態規則如下。設初始值域為 $[a,b]$，第 $s$ 個累加點的增量值域為 $[\ell_s,h_s]$，該點的迴圈次數上界為 $N_s$，則最終值域為：

$$
R =
\left[
a+\sum_s N_s\min(\ell_s,0),\ 
b+\sum_s N_s\max(h_s,0)
\right]
$$

這個區間必須完整包含於 `T` 的範圍。否則 `reda check` 會產生 E0301，並列出可容納該值的最小型別。

對具有明確型別的 `let mut` 累加器，檢查方式相同：

```fluxa
let mut total: i32 = 0;
for s in input {
    total = total + s;
}
```

也就是說，`carry` 不是新的算術，而是把「這個變數是迴圈攜帶的累加器」寫得更清楚，讓分析器知道要展開跨迭代的範圍，而不是只看單一運算式。

## 8.6.3 巢狀迴圈與次數相乘

若累加發生在巢狀迴圈中，次數上界會相乘。例如對 $M$ 列、每列 $N$ 個元素求和：

```fluxa
carry sum: i32 = 0;
for i in 0..M {
    for j in 0..N {
        sum += a[i][j];
    }
}
```

則總次數上界是 $M\times N$。若每個元素範圍是 $[0,255]$，總和上界就是：

$$
255\cdot M\cdot N
$$

這個上界若超過 `i32` 範圍，E0301 會在你還沒有合成之前就先指出來。把迴圈次數宣告成常數、讓陣列長度成為 const generic，都是讓這個分析可用的重要條件。

## 8.6.4 非加法自我更新不會被線性化

`carry` 與累加分析的強項是加法形式。對於乘法、移位這類非加法更新，檢查器採取更保守的方式。例如：

```fluxa
let mut x: u8 = 1;
for _ in 0..8 {
    x = x << 1;
}
```

分析器不會把「八次左移」線性化成一個總範圍，而是要求每一次左移的結果都能放進 `x` 的型別。若你確實需要反覆更新後才允許溢出，應改用明確的回繞或飽和操作，把意圖寫出來，而不是仰賴隱含溢位。

## 8.6.5 `carry` 不是「自動加大位寬」

`carry` 宣告的型別是設計者給的承諾，不是工具替你選的最佳位寬。工具會檢查承諾是否安全，但不會因為你寫了 `carry` 就偷偷把 `i8` 換成 `i32`。這個設計決定仍然屬於工程師：

- 以最壞情況的總和範圍選擇位寬；
- 若位寬太大，改用分段累加、飽和輸出或改變演算法；
- 把最終型別與理由寫進設計文件，而不是只留在程式碼裡。

換句話說，`carry` 讓「累加器多大才夠」從模糊的直覺，變成可被靜態檢查與審核的契約。
