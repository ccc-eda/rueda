# 4.4 task 與線性端點所有權

### 4.4.1 端點是線性資源

`chan::<T>` 建立的 `tx` 與 `rx` 都不可複製。一次只允許一個 owner 使用端點。把端點交給子 task 時，所有權會被移轉：

```fluxa
task Echo(x: in chan<i8>, y: out chan<i8>) {
    for v in x {
        y.send(v);
    }
}

let (tx, rx) = chan::<i8>(depth = 4);
let (ty, ry) = chan::<i8>(depth = 4);
spawn Echo(rx, ty);

// 從這裡開始，不能再使用 rx 或 ty。
```

`spawn Echo(rx, ty)` 不是把兩個端點「借給」Echo，而是把它們交給 Echo。原來的執行範圍不再擁有它們，因此不能再讀 `rx`，也不能送 `ty`。

這和 Rust 的 move 語意相似：資源只有一份，所有權轉移後，舊 owner 不可再用。差別在於 Fluxa 的檢查同時存在於靜態檢查與模擬器：

- `reda check` 可以在可行時提前找出所有權違規；
- 若未先經過靜態檢查，模擬器會在使用端點時報告 E0702，訊息包含 `task does not own the rx endpoint`。

以下程式是刻意失敗的：

```fluxa
task Sink(rx: in chan<u8>) {
    for _ in rx { }
}

test use_after_move {
    let (tx, rx) = chan::<u8>(depth = 2);
    spawn Sink(rx);
    let v = rx.recv();  // 錯誤：rx 已交給 Sink
    assert v == 0;
}
```

這個限制看似嚴格，卻讓網路中的通道關係非常清楚：每條通道都有唯一傳送者與唯一接收者，不會出現「兩個人同時從同一 FIFO 競爭 token」而使結果依賴排程的問題。

### 4.4.2 為什麼不用可複製端點？

若能輕易複製 `rx`，最直覺的 fan-out 寫法會是：

```fluxa
spawn Worker(rx);
spawn Worker(rx);
```

但這會讓兩個 worker 競爭同一批 token。誰先收到 `10`、誰先收到 `20`，取決於排程；這不是廣播，而是競爭式消費者。線性所有權迫使設計者明確回答：

- 我要**複製每個 token 給所有分支**嗎？那是 `broadcast`。
- 我要**把工作分散給不同 worker** 嗎？那需要明確的靜態分割或工作分配協定。
- 我只是要轉發資料嗎？那就保留唯一接收端。

Fluxa v1.0 沒有提供動態 work stealing 通道。固定數量的實例仍可由靜態迴圈建立，但複數 token 應如何分配，必須寫進協定，不能靠複製端點碰運氣。

### 4.4.3 方向由 task 的角色決定

任務參數上的方向是站在 task 自己的角度描述：

```fluxa
task Worker(
    input: in chan<i8>,
    output: out chan<i8>
) {
    for v in input {
        output.send(v);
    }
}
```

| 參數 | task 擁有的端點 | 可以執行的操作 |
| --- | --- | --- |
| `in chan<T>` | 接收端 | `recv()`、以 `for` 迭代 |
| `out chan<T>` | 傳送端 | `send()`、`close()` |

方向錯與元素型別錯是兩種不同問題。把傳送端交給 `in chan<T>` 參數，屬於方向不符；把攜帶 `i8` 的通道交給 `chan<i16>` 參數，則是元素型別不符。
