# 6.5 累加器：把跨迭代的不變量攤開

### 6.5.1 為什麼單次運算安全仍可能不夠

下列片段的每一步看起來都很安全：

```fluxa
let mut sum: u16 = 0;
for x in samples {
    sum += x;
}
```

若 `x : u8`，單次加法的結果只需要 `u9`；然而整個迴圈可能累加 1000 個 `u8`。真正的問題不是「加法器會不會立刻溢出」，而是：



$$
0 + 1000 \times 255 = 255000
$$



這個總和放不回 `u16`。若迴圈次數本身也由外部資料決定，規格上還要回答最壞情況。

### 6.5.2 `carry` 把累加器契約寫進型別

Fluxa 提供 `carry`，明確表達一個跨迭代攜帶的值：

```fluxa
task Sum(samples: in chan<u8>, out: out chan<u32>) {
    carry total: u32 = 0;
    for x in samples {
        total += x;
    }
    out.send(total);
}
```

`carry total: u32` 同時表達：

- 硬體需要一個跨迭代保存的狀態；
- 每輪的增量是 `x : u8`；
- 最終總和必須放得進 `u32`。

`carry` 與一般 `let mut` 並非只有語法差異。`carry` 把「每輪增量」與「跨迭代初值」交給累加器分析；一般型別化 `let mut` 若在迴圈內被重新賦值，也會被保守地視為累加器，但 `carry` 更清楚地表達硬體意圖。

### 6.5.3 有界迴圈：把次數乘上去

考慮 MAC：

```fluxa
task Dot(a: in chan<i16>, b: in chan<i16>, out: out chan<i48>) {
    carry acc: i48 = 0;
    for _ in 0..8 {
        let x = a.recv();
        let y = b.recv();
        acc += x * y;
    }
    out.send(acc);
}
```

`x * y` 的值域是：



$$
-32768\times32767 \ldots 32767\times32768
= -1073709056..=1073741824
$$



每輪增量需要 32 個有號位元。8 輪後，最壞總和需要：



$$
8\times1073741824 = 8589934592 = 2^{33}
$$



因此最小安全累加器是 `i34`，而不是直覺上的 `i33`：`i33` 最高只能到  $2^{32}-1$ ，連單輪最大值都放不下。

如果宣告成 `i24`，檢查器會把初值、每輪增量與 8 個迭代次數一起列入證據：

```text
carry `acc`: i24 is too small:
init 0..=0 + 8 × -1073709056..=1073741824 reaches
-8589672448..=8589934592
    fix: declare it as i34 (or saturate explicitly)
```

這裡最重要的是「8 ×」這個證據。它能區分兩種完全不同的問題：

- 單輪乘積太寬：即使只迭代一次也會溢出；
- 單輪正確但總和太寬：需要增加累加器位元。

### 6.5.4 巢狀迴圈：次數會相乘

若外層執行 4 次，內層每次執行 8 次，總累加次數是：



$$
4\times8=32
$$



分析器會把內層迴圈次數乘到外層次數，再乘上每輪增量。對設計者而言，這提醒我們：

> 「每次乘積用 32 位元」不等於「整個點積用 32 位元」。

乘加器的結果寬度、累加次數與系統最大值必須分開推導。

### 6.5.5 無界串流：不是直接報溢出，而是報無法證明

對 `for x in rx`，通道長度在編譯期未知：

```fluxa
task Count(x: in chan<u8>, out: out chan<u16>) {
    carry count: u16 = 0;
    for _ in x {
        count += 1;
    }
    out.send(count);
}
```

檢查器不能證明 `u16` 一定足夠，因為對手可以送入 65536 個 token。它會以「無法證明累加和可容納」的形式報告 E0301，而不是假裝來源值域是零。

首選修法取決於契約：

1. 若系統保證最多 65535 個 token，應把這個界線寫進介面或使用更有表達力的型別。
2. 若系統真的可能超過，讓 `count` 使用更寬型別。
3. 若只計算飽和次數，必須明確使用飽和語意，而不是讓一般加法暗中回繞。

### 6.5.6 非加法更新採更保守規則

跨迭代變數若不是簡單加法或減法，例如：

```fluxa
acc = acc * 2;
```

工具不會把一般乘法展開成「迭代次數的次方」，因為那可能需要任意大的中間值。它採保守策略：先要求這個更新本身能放入累加器型別，再把後續增量從已知起點推導。

這是一個合理取捨：區間分析擅長加法，卻不應在大型狀態空間上假裝精確。對指數運算、指數曲線或狀態編碼，設計者通常需要更明確的不變量或不同的資料表示。
