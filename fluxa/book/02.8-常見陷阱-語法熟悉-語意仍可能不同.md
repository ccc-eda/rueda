# 2.8 常見陷阱：語法熟悉，語意仍可能不同

### 把函式回傳值誤當成硬體串流

`fn` 的一個回傳值適合「計算一欄資料」或「做一次判斷」；`task` 的通道適合「不知道何時結束的一串資料」。若元件需要持續接受資料，就不要只回傳一個值。

### 在 `spawn` 後繼續使用端點

```fluxa
// 錯誤：rx 的所有權已交給 Worker。
spawn Worker(rx, ty);
rx.recv();
```

這會違反線性所有權。正確做法是由 worker 接收，測試保留另一端的 `tx`。

### 隱含窄化

```fluxa
let sum = a + b;   // 推導寬度可能比 a、b 大
let small: u8 = sum; // 若 sum 不能保證放得下，E0301
```

不要把 E0301 視為工具在挑剔。診斷是在指出你的元件契約缺少一個決定：究竟要回繞、飽和，還是加寬資料路徑。

### 看到 `task` 就以為所有東西都能並行

`spawn` 啟動程序，但 channel token 仍受 FIFO 順序約束。若元件的邏輯需要先後關係，就用 channel 的順序；若真的彼此獨立，才把它們拆成不同 task。

### 混淆 `fn` 與 `comb fn`

兩者都能做值級計算，但 `comb fn` 額外表達「展開為組合邏輯、零週期」的硬體意圖。把明顯是資料路徑的邏輯寫成 `comb fn`，會讓未來排程與時序分析更清楚。

### 過早依賴尚未實作的泛型或 `stage`

`type generic` 目前不能合成；`stage` 目前會直接報錯。可以用 const generic 表達固定位寬、固定長度與固定拓樸，不必先使用尚未完成的語言功能。
